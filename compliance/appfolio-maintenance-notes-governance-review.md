## 1. Is this a compliance build under GOVERNANCE.md?

**Yes, plainly, and it should be stated that way rather than treated as a borderline case.** `CLAUDE.md`'s own trigger is "stores someone's personal information" — this build takes free text about real owners and properties (already stored inside AppFolio, but never before stored or surfaced anywhere in Rincon's own Hub/Supabase schema) and puts it in front of Hub staff for the first time. That alone is enough. On top of it: this is staff-typed narrative text about real people's property arrangements, going back years, that has never been through any content check — the exact category GOVERNANCE.md Rule 9 and the Fair Housing Standard exist to police. Route through both gates, in full: **Asimov (this document) and Mason (Fair Housing substance, in parallel)**, per `CLAUDE.md`'s explicit instruction and per the precedent both sibling specs already followed. Neither gate is skippable even though the field's *source* (AppFolio, not a Rincon staffer) is new — GOVERNANCE.md's trigger is about what the data is and who it's about, not who typed it first.

One scoping note worth stating precisely: this review and Mason's should treat `property_directory.maintenance_notes` and `work_order.instructions` as **two different risk shapes**, not one. See Section 2 — the "backlog" framing in Oracle's research and in Peter's question is accurate for one field and not quite accurate for the other, and the build design has to reflect that difference or it will under-protect one of them.

## 2. The backlog question — two fields, two different problems, one reused mechanism

### 2a. `property_directory.maintenance_notes` — a genuine backlog problem

This field is property-level, persistent, and populated on 194 of 379 properties today, some of it years old. This is the field Oracle's research and Peter's question correctly describe as "a retroactive-scan problem, not an ongoing-ingestion-filter problem" — **for this field specifically.**

**Required before any of the 194 rows are shown to anyone:**

1. **Layer 1 — reuse `scanText()` directly, unchanged, exactly as `safeTicketTitle()` already does for ticket title/description.** Do **not** route this corpus through `content-check.js`'s Tier A/Tier B branching. Tier B's six-term contextual classifier was built and calibrated against a *specific, backtested* corpus — 340 real `maintenance_claims` records with a known-correct human determination for each (redesign spec Section 8, Step 0). There is no equivalent backtest for AppFolio's property-notes language, which is a different register entirely (approval-authority rules, vendor names and phone numbers, owner preferences) from AI-extracted maintenance-claim narrative. Applying an un-backtested classifier to a new corpus and trusting its accuracy is exactly the assumption Asimov's own review of the redesign spec flagged as unverified for `maintenance_snapshot_events` (that spec's Open Item #4) — this review makes the same objection here, prospectively, rather than letting it become a second unexamined gap discovered after the fact. Plain, full-list `scanText()` — recall-oriented by design, per its own header comment — is the right tool until real data says otherwise.

2. **Layer 2 — new, small, classification-only model call, run at sync time, not reused from `extract-claims.js`.** There is no existing extraction step reading this text today (unlike `maintenance_claims`, where Layer 2 piggybacks on the extraction model that's already reading the source text for another reason). This is the identical gap `owner-tenant-operational-notes-SPEC.md` Section 5 already found for its own manually-typed notes, and its answer is the right template here: *"For manual notes there is no model already in the pipeline to self-report... this spec recommends Q add one small, new, cheap classification-only Claude call... rather than relying on Layer 1 alone."* Build the AppFolio equivalent, triggered once per property per sync run (or only when the field's value actually changes since the last sync — cheaper, and sufficient, since an unchanged value was already checked). This is genuinely new code — say so plainly to Q, don't let it be assumed to fall out of Tier B's existing call for free.

3. **A hit on either layer flags the row. Neither layer may clear a flag on its own — only a human can.** This directly implements Peter's standing instruction from tonight's other work: AI Fair-Housing judgment narrows what a human has to look at, it never unilaterally declares something safe. Concretely: Layer 1's *absence* of a match is the same deterministic, non-AI "nothing matched" default every other content check in this codebase already uses (not a new AI-clears-content pattern) — but the new Layer 2 model call may **only add** a flag Layer 1 missed, mirroring `content-check.js`'s own documented rule ("Layer 2 still only adds, never vetoes") exactly. No code path may take a flagged row and make it visible without a `PRIVACY_REVIEW_ROLES` human action.

4. **Because this corpus has never been reviewed by anyone — not even the "clear" side — validate more than the flagged side alone.** This is a real, specific way this differs from the Tier B rollout, which had 340 already-human-reviewed records to backtest against. Here, Oracle's own spot check (6 of 194 rows) was explicitly non-exhaustive and said so directly — *"this document does not claim the corpus is clean... it should not be treated as screened just because none of the examples reviewed here happened to be sensitive."* Before this feature is treated as validated: Mason or another `PRIVACY_REVIEW_ROLES` holder must look at (a) every row either layer flags, and (b) a real, meaningful sample of the rows **neither layer flags** — not zero, the way a clean Tier B kill-switch rollout could lean on its backtest instead. A reasonable floor: all flagged rows, plus a random 40–50 of the ~180+ unflagged rows (roughly a quarter of the corpus, feasible given the small total size). This is a one-time validation step specific to this backlog's total lack of prior review, not a permanent audit cadence — Section 5 below covers the ongoing audit separately.

5. **Human review queue and disposition vocabulary — reuse the mechanism, not the `maintenance_claims` vocabulary verbatim.** A flagged `maintenance_notes` row is not a claim about a work order; it doesn't have a `claim_type`, an `outcome_level`, or a ticket to tie back to, and — critically — Rincon does not own this text. AppFolio is the system of record; the Hub only ever mirrors whatever AppFolio returns on the next nightly sync. That makes `correct` the wrong disposition to offer here (unlike `maintenance_claims.reviewed`'s `correct` action, editing this field in the Hub would create a copy that silently diverges from AppFolio's own value on the very next sync). Recommend a narrower, two-outcome vocabulary reflecting that reality: `released` (a human looked at this and it's fine to show, at the audience described in Section 4) and `suppressed` (a human looked at this and it should never render here — if staff need the underlying text corrected, that happens in AppFolio itself, not in the Hub). Final column/table shape is Neo's call; the illustrative shape below is a starting point, not a spec:

   ```sql
   -- Illustrative only — Neo to finalize. Additive, nullable, same
   -- pattern as the existing year_built/maintenance_limit migration.
   ALTER TABLE properties
     ADD COLUMN maintenance_notes                        TEXT,
     ADD COLUMN maintenance_notes_flagged_protected_class BOOLEAN NOT NULL DEFAULT FALSE,
     ADD COLUMN maintenance_notes_flagged_category        TEXT,
     ADD COLUMN maintenance_notes_review_status           TEXT NOT NULL DEFAULT 'unreviewed'
       CHECK (maintenance_notes_review_status IN ('unreviewed', 'released', 'suppressed')),
     ADD COLUMN maintenance_notes_reviewed_by              TEXT,
     ADD COLUMN maintenance_notes_reviewed_at               TIMESTAMPTZ;
   ```

   Displayed to staff only when `flagged_protected_class = FALSE OR review_status = 'released'`; otherwise render the same **"A note here is pending compliance review"** placeholder `owner-tenant-operational-notes-SPEC.md` Section 5 already established for exactly this situation — not the blunter, permanent-exclusion `APPFOLIO_TEXT_PLACEHOLDER` string `safeTicketTitle()` uses, because a `maintenance_notes` flag genuinely is queued for a human look here, not permanently hidden the way an un-reviewed flagged ticket title is today.

6. **This is not a one-time-only mechanism — the same two-layer check must run on every future sync, not just tonight's backlog.** AppFolio staff can edit `maintenance_notes` at any time; the next nightly sync would otherwise pull a never-screened new value straight past this whole design. Run the identical Layer 1 + Layer 2 check inside `sync.js`'s `buildRow()` for `property_directory` on every sync, resetting `review_status` to `unreviewed` whenever the incoming value differs from what's already stored (so an edited note gets a fresh human look, not a stale `released` disposition carried forward for text that no longer matches it).

### 2b. `work_order.instructions` — not really a backlog problem; extend the existing live check instead

This field is per-ticket, and the `work_order` report **only ever returns currently-open tickets** (confirmed live by Oracle: all 132 real rows pulled were open, none historical). There is no static 194-row backlog to clean up here the way there is for `maintenance_notes` — the population of visible `instructions` values rotates continuously as tickets open and close under the existing nightly sync. That makes this an ongoing, per-sync/per-render screening problem, structurally identical to what `title`/`description` already get today — **not** a one-time historical cleanup.

**Recommendation: extend `safeTicketTitle()` itself, don't build a second mechanism.** That function already exists, is already live, already scans raw AppFolio ticket text (`title` + `description`) with `scanText()`, already swaps in a placeholder on a hit, and already writes a deduplicated `audit_log` entry per ticket (`maintenance_history.appfolio_text_excluded`). Add `instructions` into the scanned string:

```js
// Illustrative — Q to finalize. router.js:544, extending the existing scan.
const scan = scanText(`${ticket.title || ''} ${ticket.description || ''} ${ticket.instructions || ''}`);
```

This reuses the already-proven pattern exactly, with no new table, no new review queue, and no new UI beyond rendering the (already-existing) placeholder behavior one field wider. Given `instructions` differs from `job_description` on 82% of real tickets (per Oracle), most of that additional text will now get scanned for the first time — which is the entire point.

**One asymmetry this creates, stated plainly rather than left implicit: `maintenance_notes` gets a real human review queue with a reversible disposition; `instructions` gets `safeTicketTitle()`'s lighter, keyword-only, immediate-and-permanent exclusion with no review path at all, exactly like `title`/`description` get today.** That's a real difference in rigor between two fields on the same page, and it should be an explicit, blessed choice — not a silent inconsistency. The justification: `maintenance_notes` is persistent, property-level, and sits next to the owner's name/phone/email in the page header, which argues for a higher bar; `instructions` is transient (gone once the ticket closes, never resurfaced), and Rincon already accepted this exact rigor level for the two adjacent fields (`title`, `description`) on the same object without incident. If Mason disagrees and wants `instructions` routed through a real review queue too, that's a reasonable call to make, but it should be made explicitly, not defaulted into.

## 3. Where this surfaces on Property 360 — fold into Maintenance, not a new card, not into Operational Notes

**Recommendation: `work_order.instructions` renders inline inside the existing Open Tickets row (per Oracle's own Section 6 suggestion); `property_directory.maintenance_notes` becomes a short, clearly-labeled, read-only line inside the existing Maintenance card — not a new card, and not a note type inside Owner & Tenant Operational Notes.**

Oracle flagged the real risk correctly: Property 360 is about to have two things called "notes" if this isn't placed deliberately. Here is the concrete reasoning for resolving that, not just restating the risk:

- **Authorship and consent model don't match.** `operational_notes` (per its SPEC Section 4) is built entirely around who *authored* a fact — `source IN ('manual', 'ai_proposed')`, an `author_team_member_id`, an approval workflow for AI-drafted notes, a correction mechanism that assumes Rincon owns and can edit the text. AppFolio's `maintenance_notes` fits neither `source` value: it's not staff-typed, and it's not an AI draft awaiting human approval — it's a third authorship model (an external system's own operational field, authored by whoever manages that property's AppFolio record over the years) that this table was never designed to hold. Forcing it in would mean adding a third `source` value and quietly weakening every place that table's design assumed Rincon-owned, editable text (see Section 2a's point about why `correct` doesn't fit either).
- **The access-tier model doesn't match either.** Operational Notes' three tiers exist specifically to hold content that is *inherently* sensitive even after a human confirms it belongs there — a Fair Housing complaint, a discriminatory owner instruction, litigation strategy. AppFolio's `maintenance_notes`, once a human has confirmed a given row isn't protected-class-adjacent, is ordinary maintenance-operations context (who approves a work order, which vendor to call) — the same tier of information the rest of the Maintenance card already shows. Folding a lower-stakes, AppFolio-sourced field into a three-tier system built for genuinely restricted material either over-restricts something that doesn't need it, or quietly widens what "Operational tier" on that system means. Neither is a good outcome — see Section 4 for the actual access recommendation.
- **The Maintenance card is the right home structurally, not just by elimination.** It already hosts exactly this shape of thing — AppFolio-sourced, read-only, ticket- and property-level maintenance context (`spend_by_category`, `appfolio_maintenance_spend`, the AppFolio general-ledger figures) sitting alongside a "Needs Privacy Review" subsection built on the identical two-layer-check-plus-human-queue pattern this document recommends reusing. A one-line "From AppFolio" note at the top of the card, and an instructions line inside each open ticket row, both read as continuations of what's already there, not a new concept staff have to learn.

Label it explicitly as **"From AppFolio"** wherever it renders, distinct from the Operational Notes card's own staff-authored framing — this is the concrete mechanism that keeps staff from wondering which "notes" section is authoritative for what: Operational Notes is Rincon's own factual record; this is a read-only mirror of what AppFolio itself already shows on that property's Maintenance tab.

## 4. Access tiering

**No — this does not need Operational Notes' three-tier model, with one condition.** The content, once a human has cleared it (Section 2a), is ordinary maintenance-operations information — approval authority, vendor contacts, owner preferences about maintenance handling. That's structurally the same sensitivity level as the rest of the Maintenance card, which today is visible to anyone with any Maintenance History role (`requireMaintenanceHistoryAccess` — the broad access check, not the narrower `PRIVACY_REVIEW_ROLES`). Recommend the same audience for the cleared display: whoever can already see the Maintenance card sees this too, once it's `released`. No new tool value, no new role, no portfolio-wide-access review question of the kind Operational Notes had to work through — this rides on an access population that already exists and was already evaluated.

**The condition:** this is a call to make *after* Section 2a's validation pass, not before it. If that pass turns up a meaningful share of the 194 rows carrying genuinely Fair-Housing-relevant material — a discriminatory owner instruction, a disability accommodation detail stated as more than a bare operational instruction — that finding should go back to Asimov and Mason as a real trigger to reconsider tiering for *those* rows specifically, the same way Tier B's classifier accuracy was only trusted after its own backtest produced real numbers. Don't decide this blind today; decide it once the validation pass has actual findings, and say so to Peter as an open item rather than quietly assuming the six spot-checked examples represent the other 188 rows.

## 5. Audit logging

Lighter than Operational Notes' regime, matching the lighter access-tier conclusion above, but not absent:

- **Ingestion-time flag logging — required.** Every time either layer flags a `maintenance_notes` row (new value, on sync) or `safeTicketTitle()`'s extended scan flags an `instructions` value, write an `audit_log` entry, mirroring the two already-existing patterns exactly: `maintenance_history.appfolio_text_excluded` (already covers `instructions` for free once the scan is extended — no new action needed there) and a new `properties.maintenance_notes_flagged` action for the new field, same shape as `maintenance_claims.protected_class_excluded` (`actor_type: 'system'` for the Layer 1 hit, `'ai_agent'` for the Layer 2 hit, `risk_level: 'high'`, `details` carrying category and matched layer — never the flagged text itself, per `protected-class-terms.js`'s standing rule and its one narrow named exception, which does not extend to this new field).
- **Human disposition logging — required.** `released`/`suppressed` actions on a `maintenance_notes` row each write one `audit_log` entry (`properties.maintenance_notes_reviewed`), reviewer email, previous/new `review_status`, never the note text — same restraint every other disposition-logging action in this codebase already uses.
- **No new blanket read/view logging required** — unlike Operational Notes, this isn't creating any new, broader access population to justify tracking who looked at what (Section 4). If Section 4's condition triggers a tiering reconsideration later, revisit this too at the same time, not before.
- **Rule 4 data inventory** — required for the new columns regardless of whether Neo ships them as columns on `properties`/`maintenance_requests` or a separate table: `pii_fields` (`maintenance_notes` itself — flag that some real values carry a named vendor's personal cell phone number, e.g. the "Ezequiel 805-212-6184" example Oracle quoted — worth noting even though a vendor contact isn't a tenant or owner), `agents_with_access` (Claude, for the new Layer 2 call; Hub users with Maintenance-card access, per Section 4), `privacy_category`, and `retention_policy` as a documented **PLACEHOLDER pending Mason**, matching this schema's own standing practice for every other new sensitive-content table shipped this cycle.
