## Scope

Three tables, all created fresh by the migration named above (none exist live today):

1. **`missive_conversation_significance`** — new. One row per (mailbox, conversation); the merged Call 1/Call 2 significance and triage record.
2. **`complaints`** — evolved from the never-applied 2026-09-10 design. One row per actionable finding (AI-driven or manually reported).
3. **`missive_message_links`** — new. One row per (message, resolved subject) pair; the address/content match record Section 4 of the spec keys subject resolution off of.

`complaint_tracking_config` (also created by this migration, carried forward unchanged from the never-applied design) is out of scope for this inventory — it holds no personal data (three integer thresholds, a version number, an approver email), exactly as the original inventory already classified it, and that classification does not change here.

## Data Inventory (GOVERNANCE.md Rule 4 format)

### `missive_conversation_significance`

- **`pii_fields`:** `why` (the AI's stated reasoning — can reference real correspondence content); `protected_class_category`/`keyword_check_flagged_category` (could indirectly reveal a sensitive topic without containing it verbatim); `owner_instruction_note_text` (the highest-risk field on this table by design — stores an AI-drafted, potentially adverse characterization of a named owner's past conduct, permanently, for both live and historical mail); `blocked_party` (identifies whether an owner or tenant is the one refusing/unresponsive, without naming them directly — the row itself is keyed to a conversation, not a person, until joined through `missive_message_links`). `mailbox_key`/`missive_conversation_id` match `missive_message_intake` by value only (Rule 9 firewall, restated in the migration) — this table carries no name, email, or other direct identifier of its own; identity is only reachable by joining to `missive_message_links`.
- **`pii_fields` — `owner_instruction_rejected` (own entry, added 2026-09-13 per Asimov's final clearance pass; previously folded silently into the `owner_instruction_note_text` bullet above):** A tri-state AI assessment of whether a specific owner instruction looks discriminatory — `NULL` (Call 2 hasn't run yet, or `category != 'owner_instruction'`, per the `missive_conversation_significance_owner_instruction_requires_category` constraint), `'true'`, `'false'`, or `'uncertain'` (the third value applies to historical mail only, per the migration's column comment). This is a materially different risk from `owner_instruction_note_text`, not a restatement of it: it is a structured, indexed column — `idx_missive_conversation_significance_owner_instruction_rejected` is a partial index specifically on rows where this equals `'true'` — so a plain `WHERE owner_instruction_rejected = 'true'` query surfaces every AI-concluded discriminatory-owner-instruction finding without reading any free text at all. Queryable/filterable by the same `searcher`-tier population as the rest of this table (see `agents_with_access` below) — the widest read access of any table in this inventory. **`ccpa_deletable` for this column specifically: open, and not the same operation as redacting `owner_instruction_note_text`.** No redaction mechanism exists in this migration for this column either, but unlike a free-text field, "redacting" a tri-state flag means resetting it to `NULL` — a schema-level UPDATE, not a text-substitution convention — and that raises its own question this document does not resolve: does a CCPA request from the named owner require clearing this flag too, not just the note text it's paired with, and does doing so erase a real compliance-relevant finding in the process. Flagged for Asimov/Mason, not decided here.
- **`agents_with_access`:** the merged Call 1/Call 2 pipeline (Claude, via `ANTHROPIC_API_KEY` — already resolved for this exact use per the DPA/Commercial-Terms answer the 2026-09-10 inventory cites, unchanged here since it's the same direct-API credential); `checkClaim()`'s independent Tier A/Tier B layer (`maintenance-history/lib/content-check.js`), called on every row per spec Section 5; Hub users holding `searcher` for `tool='archive_search'` — **the widest read access of any table in this inventory**, per spec Section 7's own stated reason for keeping this a separate table from `complaints`: `searcher`-readable, dismiss/reinstate-only, versus `complaints`' admin/`director_of_operations`-only tier. `human_confirmed_big_issue*` is written only by a human via the "Needs a Human Call" queue — never by either AI call.
- **`privacy_category`:** A significance/triage judgment about real tenant/owner/vendor correspondence — closest existing analog is `operational_notes`' "owner/tenant operational record," widened here to cover every conversation in the archive rather than only ones a human chose to note. Distinct from `complaints`' category (below) in one load-bearing way: this table is reachable by a much larger, `searcher`-tier population, over the **entire** historical archive, not just the actionable subset.
- **`retention_policy`:** **Not separately set by this migration — inherits the source archive's existing posture.** No new retention decision is made for this table; it is a derived index over `missive_message_intake`, whose own Mason-set retention policy (4 years from `delivered_at`, gated on Tier 2 HELD status — `20260905020000`) already governs the underlying correspondence. Whether a significance row should ever outlive, or be forced to expire with, its source message is not addressed by the spec and is not decided here — flagged as open, not assumed.
- **`ccpa_exportable`:** TRUE — this table plainly holds AI-generated content about identifiable tenants/owners once joined through `missive_message_links`, and `owner_instruction_note_text` can name a specific owner's conduct directly in its own text.
- **`ccpa_deletable`:** **Open — this is the CCPA-cascade question the spec's own Section 11, Item 9 names as unresolved, and this document does not resolve it either.** Quoting the spec directly: *"if a tenant/owner record is redacted, does `missive_message_links`/`missive_conversation_significance`/`complaints` content naming them need sweeping too? Still not solved here."* No redaction mechanism, targeted or otherwise, exists in this migration for `why`, `owner_instruction_note_text`, or any other free-text column on this table. This is a real gap, not a placeholder awaiting a routine confirm-at-build-time note — it is a genuinely open product/legal question about whether a redaction on `tenants`/`owners` needs to cascade into AI-generated derivative text, and if so, how a cascade would even find every affected row (this table has no `tenant_id`/`owner_id` column of its own — the only path to a subject is via `missive_message_links.subject_id`, which is a many-rows-per-conversation join, not a direct column).
- **RLS:** enabled, zero permissive policies at creation — same "locked down until a tool explicitly asks for access" default as every table in this schema.

### `complaints`

- **`pii_fields`:** `description` (AI summary or manual reporter's own text — highest density by design, unchanged from the original inventory); `resolution_note`; `blocked_reason`/`blocked_party`/`blocked_since`; `flagged_category`; `subject_id`/`subject_type` (identifies a specific tenant/owner/team member directly); `source_missive_conversation_id` (traces back to real correspondence, plain-text pointer, no FK); **new in this merge:** `owner_instruction_note_text` — carries the same permanent, potentially-adverse-characterization risk as its counterpart on `missive_conversation_significance`, now on the admin/DO-only table specifically, for the subset of findings serious enough to reach this table at all.
- **`pii_fields` — `owner_instruction_rejected` (own entry, added 2026-09-13 per Asimov's final clearance pass; previously folded silently into the `owner_instruction_note_text` bullet above):** The same tri-state AI assessment as its counterpart on `missive_conversation_significance` — `NULL` unless `category = 'owner_instruction'` (`complaints_owner_instruction_requires_category`), otherwise `'true'`/`'false'`/`'uncertain'` — carried onto this table for the subset of findings serious enough to reach it at all. No dedicated partial index exists on this table's copy of the column (unlike `missive_conversation_significance`'s `idx_missive_conversation_significance_owner_instruction_rejected`), but it is still a directly filterable structured value — a plain `WHERE owner_instruction_rejected = 'true'` query finds every such finding without touching `owner_instruction_note_text` or `description`. Queryable/filterable by the same admin/`director_of_operations`-only tier as the rest of this table (see `agents_with_access` below), not the wider `searcher` tier `missive_conversation_significance` grants. **`ccpa_deletable` for this column specifically: open, and distinct from the note-text redaction question already named below.** The existing `"[REDACTED]"` text-substitution convention (below) does not apply to a tri-state column — actually removing this finding on a CCPA request means resetting the value to `NULL`, a schema-level UPDATE the migration does not implement and this document does not resolve. Whether the same `held_legal_fair_housing` categorical exception should govern that reset is Asimov's/Mason's call, not assumed here.
- **`agents_with_access`:** the merged pipeline (same credential as above, when `source = 'email_ai'`); Hub users holding `admin` or `director_of_operations` for `tool='complaint_tracking'` (**already a legal `team_member_tool_roles.tool` value live today** — see the migration's own header finding: an earlier, actually-applied migration added it even though the migration that "originally" owned it was never run; who actually holds it is still Peter's call, not set by any migration); any active team member, write-only, for their own manual report (`source = 'manual_staff'`, unchanged from the original design).
- **`privacy_category`:** Complaint/dispute record about a tenant, owner, or team member — unchanged classification from the 2026-09-10 inventory. The category vocabulary itself changed (the old 6-value complaint-tracking-only enum is retired in favor of the shared 8-value taxonomy — see the migration's own flagged gap on `is_big_deal` below), but the privacy classification of the table does not.
- **`retention_policy`:** **RESOLVED, carried forward — indefinite retention**, per the original design's "never delete" stance (`complaint-tracking-v1-scope.md` Section 4), unchanged by this merge. Distinct from deletion policy (below).
- **`ccpa_exportable`:** TRUE — unchanged.
- **`ccpa_deletable`:** TRUE for ordinary rows, via the same targeted `description`/`resolution_note` → `"[REDACTED]"` convention the original inventory specified, **now also covering `owner_instruction_note_text`** (not part of the original inventory, since that column is new to this merge) — same redaction target, same `held_legal_fair_housing = TRUE` categorical exception (hard-refuse, route to a fresh per-request determination), unchanged reasoning. **Not yet resolved by this migration or this document:** whether redacting `owner_instruction_note_text` on a historical, AI-drafted finding about a named owner raises a different question than redacting `description` on an ordinary complaint — the note's entire evidentiary value is that it exists and says what it says; redacting it on a CCPA request from the very owner it describes is a real tension this inventory is naming, not resolving. Flagged for Asimov/Mason, not decided here.
- **RLS:** enabled, zero permissive policies at creation.

### `missive_message_links`

- **`pii_fields:`** none directly in the row's own text — this is the deterministic/AI-matching *link*, not correspondence content. But `subject_id` is a direct identifier (a real tenant/owner/vendor row), and `source_reference` (content-extracted rows only) quotes or paraphrases the specific sentence a match was based on, which can itself be a short excerpt of real correspondence.
- **`agents_with_access`:** the deterministic address-match step (no AI, free — Section 4 of the spec); the content-extraction step (Prompt B, AI-driven, only when no address match exists) for the same Claude credential as above; readers wherever `subject_type`/`subject_id` are joined — Property 360's per-property card, and `complaints.subject_type`/`subject_id` population (address-match rows only, per the spec's own "email-match only, no AI free-text fallback" discipline, restated as a CHECK-adjacent comment in the migration).
- **`privacy_category`:** Identity-resolution record — links a conversation to a specific tenant, owner, or vendor. Structurally narrower in kind than `missive_conversation_significance`/`complaints` (no free-text findings, no AI judgment about significance), but it is the one table in this merge that makes every other table's `subject_id` *reachable by name* — a query joining through this table is the actual mechanism by which a `searcher`-tier user could go from "this conversation is tagged `dispute`" to "this is about this specific tenant."
- **`retention_policy`:** Not separately set — inherits the source archive's posture, same open status as `missive_conversation_significance` above, for the same reason (derived index, not a new store of correspondence).
- **`ccpa_exportable`:** TRUE.
- **`ccpa_deletable`:** Not addressed by the spec and not resolved here. A CCPA deletion request against a tenant/owner/vendor would need to also find and act on every `missive_message_links` row where `subject_id` matches — the same "manual lookup by matching a known email/id" limitation `missive_message_intake`'s own inventory already accepts as a known, unsolved gap for that table, now inherited by this one at one further remove (via `subject_id`, not a direct email column).
- **RLS:** enabled, zero permissive policies at creation. **Dormant for `subject_type = 'vendor'`** until an AppFolio-to-Supabase vendor sync exists (spec Section 11, Item 10) — no vendor personal data can reach this table today regardless of what this inventory says about it.

## Access-Tier Summary (the distinction the spec itself establishes)

| Table | Read access | Population reached |
|---|---|---|
| `missive_conversation_significance` | `searcher` (Hub, `tool='archive_search'`) | Every conversation in the archive (~254,000+), not just actionable ones |
| `missive_message_links` | Same population as whatever joins to it — no independent grant of its own in this migration | Every message with a resolved subject |
| `complaints` | `admin` / `director_of_operations` only (`tool='complaint_tracking'`) | Only the actionable subset the trigger-logic condition (documented in the migration's own header) creates a row for |

This is the real reason the spec keeps these as separate tables rather than one (Section 7): the `searcher`-tier population is far wider than the two-role `complaints` population, and `missive_conversation_significance`'s own redaction posture is explicitly still open (above) in a way `complaints`' is not.

## The Real Quoted-Excerpt Risk — Named Directly, Per the Task Brief

Three fields across these tables store real, potentially verbatim tenant/owner/vendor correspondence text, permanently, in a queryable table, readable by a `searcher`-tier population in one case:

- **`missive_conversation_significance.why`** — the AI's one-sentence reasoning for its Call 1 classification. Not designed as a quote, but nothing prevents it from closely paraphrasing or lifting language from the thread.
- **`missive_conversation_significance.owner_instruction_note_text` / `complaints.owner_instruction_note_text`** — by design, an AI-drafted characterization of what an owner instructed, live or years ago, carrying (for historical mail) the mandatory "Automated historical assessment — not human verified" label as part of the same stored string. This is the single highest-permanence, highest-consequence text this merge introduces: it is not a quote, but it is a stored, adverse-leaning assessment about a named person's past conduct, created and shown with no human review before it exists.
- **`missive_message_links.source_reference`** — for content-extracted rows, "which sentence/field the reference came from," per the citation discipline `extract-claims.js` already requires elsewhere in this codebase. This is the field most likely to contain an actual excerpt, by design, since its entire purpose is to let a human check the AI's identification claim against real text.

Spec Section 11, Item 8 (carried from v1, "sharper now"): *"source_reference/why/note_text all store real quoted/paraphrased tenant/owner correspondence, permanently, in a queryable table — and now `complaints`, not just `significance`, carries some of this same content."* This inventory does not add a mitigation beyond what the spec already names (the reliance-gate rule for consequential use, Section 6) — it is restating the risk plainly, per the task brief, not resolving it.

## Rule 9 — Housing-Decision Firewall

Restated from the migration's own header, not re-derived: `missive_conversation_significance` carries no FK into `properties`/`units`/`tenants`/`owners`/`vendors` at all (value-match only into `missive_message_intake`, per that table's own established Rule 9 convention). `complaints` and `missive_message_links` are **not** structurally firewalled the same way — both carry real foreign keys for ordinary tool operation. The firewall on those two is a written policy, not a structural absence of FK: any join from either table's subject-identifying columns into a screening, renewal, eviction, or adverse-action tool requires its own fresh Asimov/Mason review before it is written.
