## Finding 1 — The privilege-filter gap is real, and it is worse than "search doesn't need a filter." ATTORNEY REQUIRED.

The spec (Section 1 point 2, line 57; Section 7 item 7, line 353; Section 12, line 420) correctly identifies that retiring complaint-tracking's own pipeline also retires the only attorney-privilege check (`privilege-filter.js`'s `checkThread()`) that ever ran ahead of an AI reading this content for meaning. It correctly flags this as unresolved. Having read the actual code, I agree it is unresolved, and I think the spec understates how far the existing outside-counsel opinion is from covering it.

**What the existing opinion actually approved.** `compliance/archive-search-held-release-outside-counsel-opinion.md` is about *searchability* — whether making already-accessible shared-inbox mail easier for a trained employee to find, via a plain query box, requires a permanent privilege hold. Counsel's own framing, repeatedly: "Archive Search should not be Rincon's privilege-determination engine" (line 359), "the search system should simply be treated as an internal information-retrieval system" (line 107), and the risk table itself grades "Removing the blanket legal-matter filter" only "LOW TO MODERATE RISK / REASONABLE" (line 346-347) — not "no risk." Every part of the opinion is reasoning about a human typing a query and reading what comes back.

**What this merge actually does, verified against the real code, is a different act.** As of `screening-pass.js`'s v5 change (lines 167-211, 459-476), `checkThread()` still runs (line 476) but its `.held` result no longer excludes anything — every conversation, including one that would have tripped a Tier 2 law-firm-domain or `HOLD_TERMS` hit under `privilege-filter.js`, now flows into `handleNonHeldConversation()` and gets `screening_result = 'clear'` once it clears the Fair Housing self-report. That `clear` population is exactly what this merged pass reads (`missive_message_intake_search_safe`). So the merged pass will run Call 1 and, on a large fraction of conversations, Call 2 — an AI actively reading for `legal_exposure`, drafting a `why` field, and in the `owner_instruction` case drafting `note_text` — directly against correspondence that includes real attorney/litigation-flagged content, at bulk scale, with nothing upstream ever having looked at it for privilege at all.

This is not "using an already-approved search tool." It is Rincon's own AI system reading potentially privileged material and **generating new written analysis of it**, then **writing that analysis into a new, permanent, more widely-surfaced business record** — `missive_conversation_significance.why` (readable by every `searcher`-tier Hub user, Section 7 line 341) and, for actionable results, `complaints.description`/`owner_instruction_note_text` and a proposed `operational_notes` row (admin/DO-tier, but still a new artifact). Counsel's own Section 8 caveat — "unnecessary distribution of genuinely privileged legal advice can create avoidable arguments concerning confidentiality" (quoted and treated as load-bearing in `compliance/archive-search-held-release-mason-confirmation.md`, finding 2) — was written about a human reading raw text in a search result. It was never asked about, and does not obviously extend to, an AI system *creating a new derivative document* — a categorization, a risk read, drafted note text — out of that content and storing it as a fresh, independently-discoverable record. A generated summary that says "legal_exposure: tenant's attorney sent a demand letter re: habitability, unresolved" is Rincon's own new writing, not the original email — and it is exactly the kind of record that, if Rincon is ever in a dispute over that same tenant relationship, reads badly regardless of whether the underlying email was privileged.

There's a second, narrower, code-level problem underneath the policy one. `categorize-complaint.js`'s own `legal_compliance` category text — carried into this merge's shared vocabulary — says outright: "an actual formal Fair Housing/HUD/CRD complaint or real attorney/legal correspondence **should already have been pulled out before you ever saw this thread** (a separate mechanical hold check runs first) — **if you are seeing this thread at all, it already cleared that check**" (`categorize-complaint.js` line 62). That sentence is the model's own operating assumption, and this merge makes it false: no privilege check of any kind runs before this content reaches either call. The prompt design was built on a precondition the merge quietly removes. At minimum, that sentence needs to be rewritten before this ships regardless of what else is decided — leaving it in tells the model something untrue about its own input, in exactly the category (`legal_exposure`) where that matters most.

**This is a new legal question, not a scope extension of an answered one.** Whether an AI drafting written analysis off potentially-privileged correspondence — at 250,000-conversation bulk scale, unsupervised, and storing the output permanently — creates a materially different privilege/confidentiality exposure than passive searchability was never asked of outside counsel. It needs to be. This is squarely "requires a licensed attorney in California" territory, not something Mason can clear on the strength of an opinion written to answer a different question.

**Recommendation, pending that opinion:** at minimum, gate Call 2 (and arguably the `legal_exposure` category path in Call 1) behind a reinstated, narrow privilege pre-check — reusing `privilege-filter.js`'s existing law-firm-domain and `HOLD_TERMS` layers (not the removed archive-search hold behavior; a *tag*, not an exclusion) — so that a thread carrying a real Tier-2-shaped signal routes to human review before the AI drafts anything about it, rather than being silently processed like any other conversation. This is a cheap reuse of code that already exists and already works; it does not require rebuilding the retired hold.

## Finding 2 — The retroactive `owner_instruction_rejected` wording fixes one problem and doesn't fix the one that matters more. Needs further restriction.

Section 3 (line 101) and Section 5 (lines 229-239) rework the template so historical mail is worded as a present-day AI assessment ("AI-assessed in 2026: this 2022 owner instruction, if acted on, would require Rincon's standard refusal — no record confirms what was actually communicated...") rather than a false factual claim about what staff actually said. That fix is correct and necessary — the original v1 template, applied retroactively, would have fabricated a specific historical event ("Rincon's response was: ...") that may never have happened. Good catch, keep it.

**But that fix addresses only the narrower of two problems, and the wording change doesn't touch the wider one.** The wider problem: this is an AI, running unsupervised at bulk scale with no human review *before the record is written* (Call 2's write happens in the same batch pass that generates it — Section 5's fail-closed posture describes what happens on a parse failure, not a case where the parse succeeds and the AI is simply wrong), generating and permanently storing a legal characterization of a real, named owner's historical conduct as discriminatory. Reword it however carefully you like — "AI-assessed," "no record confirms" — the record still asserts, as Rincon's own system's conclusion, that a specific owner gave a specific discriminatory instruction. If the AI misreads an ambiguous instruction (plausible at this category's edges — e.g., a legitimate, lawful screening preference that superficially resembles a protected-class reference), Rincon's own database now contains a false, adverse, AI-generated claim about that owner, sitting in a queryable table, that the owner never had a chance to contest before it was written. And even when the AI reads it correctly, the note itself has no protective value for a historical instruction the way the live version does — the live template documents a real, current corrective action Rincon actually took (refusing to comply, going forward); the historical template documents nothing except that Rincon's AI, in 2026, formed an opinion about something that happened in 2022 and did nothing about at the time. There is no operational upside to auto-generating that text that offsets the downside of getting it wrong, because — unlike the live case — nothing needs to happen right now as a result of it.

Note also that the reworded template only hedges the *response* half of the claim ("no record confirms what was actually communicated") — it does not hedge the *categorization* half. It states "this instruction... would require Rincon's standard refusal" as if the discriminatory read itself is settled, with no equivalent "this AI categorization has not been reviewed" qualifier on the part most likely to be wrong.

**Recommendation:** adopt the more restrictive alternative the spec itself raises as an open question rather than decides (Section 11, item 6, line 421) — for historical mail, Call 2 should set `owner_instruction_rejected` (true/false/uncertain) and route the conversation to human review, but should **not** auto-generate `note_text` at all. Let a human — Peter or the DO — decide whether any note gets written, and write it themselves if so. This mirrors the fail-closed-to-human-review posture the spec already applies elsewhere (Section 5's Call 2 parse-failure handling, Section 6's bounded checklist) to a case that is arguably higher-stakes than either: a *confident* AI assertion is more dangerous unreviewed than an *uncertain* one, because nothing downstream is built to double-check a confident answer the way `needs_human_call` forces a look at an uncertain one. If Peter wants the note auto-drafted anyway for efficiency, that's his call to make explicitly — but it should be made knowing this is what's being traded away, not folded into "we changed the wording, so it's fixed."

## Finding 3 — Keep the Fair Housing self-check as genuine defense-in-depth. One real gap to close first: what does a `true` flag actually *do*?

Section 5 (lines 153-160) keeps complaint-tracking's own protected-class self-check on Call 1, reused verbatim from `categorize-complaint.js` line 73. The spec frames this as an open question — redundant now that content only reaches this pass after clearing archive-search's own Fair Housing self-report (`fair-housing-batch-self-report.js`), or genuine defense-in-depth.

**My recommendation: keep it, and treat it as real defense-in-depth, not redundant.** Two independent reasons:

1. **It's not the same question, asked twice.** Archive-search's self-report (`fair-housing-batch-self-report.js`, prompt at lines 79-125) answers one narrow gatekeeping question at one point in time: is this thread ever searchable at all. It runs once, at screening time, on `low` effort with a 512-token budget (line 168-169) — a cheap, single-purpose call. Complaint-tracking's self-check runs inside a fuller categorization read, with a differently-scoped question and a different downstream consequence (feeding `protected_class_flag`/`protected_class_category`, which historically fed `checkClaim()`'s own Tier A/B combination in `content-check.js` — see below). Two independently-erring checks, asked differently, on the same content, catch different false negatives. Given this pass runs once, unsupervised, at 250,000-conversation scale with no re-run schedule, that redundancy is worth more here than it would be on a five-email-a-day trickle, not less.

2. **The two checks serve different populations even after the merge.** Archive-search's self-report gates *eligibility into this pass at all* — a `flagged_protected_class` conversation from that layer never reaches Call 1 or Call 2 in the first place (it's held in `missive_message_intake_flagged_review_safe`, not `_search_safe`). Complaint-tracking's self-check is the only Fair Housing signal that ever runs on content *this pass itself* is reading right now, in the context of *this specific* legal/triage read — a materially different moment than the original archive-wide screen.

**The real gap: the spec doesn't say what a `true` self-check flag from Call 1 actually causes to happen.** `categorize-complaint.js`'s own header text, reused verbatim into this merge's prompt (line 154, "independent of, and in addition to, an automated keyword scan that also runs on your output"), refers to `content-check.js`'s `checkClaim()` — the real Tier A (keyword) + Tier B (AI classifier) combination that `process-pending-messages.js` actually calls today (lines 273-277) to populate `complaints.flagged_protected_class`/`flagged_category` and drive an `audit_log` entry (lines 357-381). The v2 spec's schema for `missive_conversation_significance` (Section 7, lines 294-296) only shows the model's own self-check fields (`protected_class_flag`, `protected_class_category`) — there is no mention anywhere in this document of whether `checkClaim()` itself is still called as an independent second layer on top of the prompt's own self-report, the way it is today. If it's quietly dropped, the "defense-in-depth" framing is hollow — a self-check field that feeds no audit event and no review surface is decoration, not a safeguard. **Before Q builds this, the spec needs to say explicitly: is `checkClaim()` retained as a real, separate call on Call 1's output (as `process-pending-messages.js` does today), and does a `protected_class_flag = true` result trigger the same kind of `audit_log` entry / review surface complaint-tracking's design already built for it?** This is a concrete build-mechanics gap, not a policy disagreement — but it needs an answer before "keep the self-check" means anything operationally.

## Finding 4 — The `needs_human_call` review queue (not yet in the written spec) needs an actual bound, and it interacts with an existing gap in Section 6's checklist that should be closed at the same time.

I confirmed by direct search that "big issue" and the four-signal/`needs_human_call`-gates-review description do not yet appear anywhere in `archive-search-significance-technical-spec.md` or in `compliance/`. Evaluating the description as given:

**The core design — uncertain items go to human review before counting as a recognized issue, rather than defaulting to visible — is the right instinct**, and it's consistent with this codebase's own existing Fair Housing flagged-review pattern (held for human judgment, not silently either promoted or dropped). It is also consistent with GOVERNANCE.md's Fair Housing Standard Rule 7 (human-in-the-loop) in spirit, even though `needs_human_call` items aren't housing decisions per se.

**But "review before visible" and "no schedule for that review" combine into a real risk that is specific to this design, not a generic worry.** A `legal_exposure`/`owner_instruction`-categorized item, or one that trips one of the four escalation signals, is auto-recognized immediately under the stated rule — that part is fine; the AI's *confident* reads on the highest-risk categories are not stuck behind a human gate. The risk is narrower and concrete: an item where the AI itself says "I'm not sure" is precisely the population most likely to contain a real, serious, ambiguous issue (that's what "genuinely unsure" is *for* — see `categorize-complaint.js` line 69's own framing, "never force a confident category guess when the material doesn't clearly support one"). Parking that population behind a review queue with zero automatic schedule, in a codebase where "manually-triggered, no cron" is the standing pattern for everything (Section 10, and every pipeline reviewed here), means the safety net has no guaranteed check-in. Given Section 10's own back-of-envelope estimate (1,250-5,000 total flagged items expected from the historical run), the uncertain subset of that could itself run into the hundreds — sitting with no deadline is a real gap, not a hypothetical one.

**This compounds with an existing gap already in the written spec that should be fixed in the same pass.** Section 6's bounded, must-be-affirmatively-cleared checklist (line 266) only auto-includes historical rows where `category IN ('legal_exposure', 'major_money_property_risk') OR escalation_signal = 'blocked_resolution'` AND `resolution_status IN ('open','unknown')`. **`accommodation_related` is not in that list, and neither is a bare `needs_human_call = true` with no qualifying category or signal.** That means an old, apparently-unresolved disability accommodation thread — or a genuinely AI-uncertain item that doesn't happen to also carry one of the four escalation signals — falls through to "the plain, passive, dismiss/reinstate model" (Section 6's own closing sentence) with no mandatory human look at all, unless the new `needs_human_call` queue (not yet designed, not yet written into this document) is built to independently cover exactly that gap.

**Recommendation:** before this ships, the spec needs to state, in writing: (1) `accommodation_related` added to Section 6's bounded-checklist category list — a real, present gap, independent of the new `needs_human_call` proposal; (2) a real bound on the `needs_human_call` review queue for historical items specifically — not necessarily a hard SLA, but something more concrete than "reviewed whenever someone opens the tab" — e.g., tied to the same affirmative-clear mechanism Section 6 already built (`historical_review_cleared_at`/`historical_review_cleared_by`), so it's at least trackable as outstanding rather than invisible; and (3) an explicit statement of how the new `needs_human_call` queue and Section 6's existing bounded checklist relate — one merged review surface, or two separate backlogs a person has to remember to check both of. Right now they'd be two independently-invented, independently-unscheduled queues covering overlapping ground, which is worse than either alone.

## Finding 5 — `accommodation_related` and `legal_exposure` carry a materially higher downside from a wrong "still open" read on old mail than other categories — and the spec's general silence-context fix doesn't reach the specific mechanism that would misread them.

The spec's Section 5 fix (`historicalFraming`, lines 217-227) is scoped specifically to Call 2's `escalation_signal`/`blocked_resolution` read, driven by the real, code-verified silence-context bug in `computeSilenceContext()` (`process-pending-messages.js` lines 51-61). It's a real fix for a real bug, and it's correctly scoped to the field that bug actually touches — `resolution_status` and `tone_trend` are Call 1 fields that read thread content directly rather than wall-clock time, so they aren't vulnerable to the *same* mechanism.

**But the underlying real-world pattern this codebase itself documents — resolution frequently happens off-email (Section 3, line 103: "the fix got confirmed by phone, not email")** — doesn't just distort the silence-context date math; it systematically biases old threads toward *looking* unresolved or escalating on their face, independent of any date calculation, simply because the last email in a genuinely-resolved thread is disproportionately likely to be an unanswered "I'll take care of it" or an unresolved-sounding complaint that was actually closed by a phone call. `tone_trend` reads exactly this: a thread that ends on a frustrated message, with nothing since, reads as "escalating" whether it's three days old or three years old, and that read is accurate to the *text* even when it's wrong about the *outcome*. This isn't the silence-context bug — it's a separate, structural bias in what old resolved-off-channel threads look like on paper, and nothing in Section 5 or Section 6 addresses it directly for Call 1's own fields.

For most categories, a wrong "still open/escalating" read on old mail is a reviewer-time cost — it inflates the historical backlog a person has to look at, nothing more. For **`accommodation_related`** and **`legal_exposure`** specifically, the same wrong read is qualitatively worse: a permanently-stored, AI-generated, queryable record asserting that a disability accommodation request or a legal-exposure item looked unresolved is exactly the kind of artifact that reads badly if it ever surfaces in an actual HUD/DFEH complaint, a tenant's own Fair Housing claim, or litigation discovery years later — not because the underlying event was necessarily mishandled, but because Rincon's own system will have flagged it as looking that way and the record will show whether anyone did anything about the flag. That's a fundamentally different risk profile than an inflated parking-dispute count. (The inverse error — a genuinely still-open accommodation or legal matter misread as resolved because the AI took a closing-sounding message at face value — carries the mirror risk: a live, ongoing issue nobody is looking at, precisely because the tool concluded there was nothing to look at.)

This is the same mechanism as Finding 4's gap, from a different angle: it's a further, independent reason `accommodation_related` needs to sit inside Section 6's mandatory-human-review checklist for historical rows where `resolution_status IN ('open','unknown')`, not just an argument about prompt wording. I'd stop short of recommending a prompt-level fix beyond what Section 5 already does for the silence-context bug specifically — trying to teach the model to distrust its own tone read on old mail generically risks making it under-call `legal_exposure`/`accommodation_related` on genuinely still-open historical issues, which is the worse failure mode of the two. The safer fix is procedural: treat both categories as automatically requiring a human look on any historical item that isn't confidently `resolved`, regardless of what tone or escalation signal the model attached.

## Follow-up to Finding 3 — 2026-09-17. Confirmation, not a fresh review.

**What prompted this.** Peter has decided to remove Call 1's own protected-class self-check (`TONE_AND_PROTECTED_CLASS_BLOCK` item 5, `projects/hub/archive-search/lib/significance-pass.js`) — the check Finding 3 recommended keeping as defense-in-depth. I read the real code (`significance-pass.js`, `content-check.js`, the Section D schema in `supabase/migrations/20260913020000_archive_search_significance_complaint_merge_schema.sql`, and `archive-search/router.js`) rather than assuming.

**1. Does this change `checkClaim()`?**

`checkClaim()` (`projects/hub/maintenance-history/lib/content-check.js`) is untouched as a function — Peter did not ask to remove it, and nothing about it changes. It still runs two independent layers on this pass's own content, with zero dependency on Call 1's self-report: Tier A (deterministic keyword match, immediate flag) and Tier B (the six ambiguous terms — "white," "black," "blind," "diagnosis," "diagnosed," "too old"/"too young for" — routed through `classifyTierBTerm()`'s own contextual AI check, fail-closed to "ambiguous" on any error). So the answer to the real question — is there still at least one real check running on this pass's own content after Call 1's self-report is gone — is **yes**. `checkClaim()` alone is not "nothing standing between this pass and a miss"; it's a live, independent, code-verified second layer, exactly the mechanism Finding 3 confirmed should be retained.

What does go away is `checkClaim()`'s third input — Layer 2, `modelFlag`/`modelCategory`, fed today from `call1.protected_class_flag`/`call1.protected_class_category` (`significance-pass.js` lines 908-912). Once Call 1 no longer asks the question, Layer 2 has nothing to OR in, and `checkClaim()` degrades from a three-way check (Tier A + Tier B + Layer 2) to a two-way one (Tier A + Tier B). That is the real, and only, coverage loss — correctly scoped, and it's the same trade-off Finding 3 already named when it called this "defense-in-depth" rather than "the only thing standing between the pass and a miss."

**One implementation-correctness catch that isn't a policy question but has to be gotten right, or this backfires in the opposite direction.** `parseCall1Response()` (`significance-pass.js` line 234) fails closed to `protected_class_flag = true` whenever the field isn't a boolean in the model's response — deliberately, so a malformed field never silently reads as "clear." There's a dedicated test for exactly this (`archive-search/test/run-tests.js` line 1052). If the prompt question is deleted but that default and the `checkClaim()` call site aren't updated in the same change, the model will never return the field, the fail-closed default will fire on every single conversation, and `modelFlag` will be `true` on 100% of rows — not "no Layer 2 signal," but "Layer 2 always fires." That would flood `audit_log` with a `complaint_tracking.protected_class_flagged` entry on every conversation and bury the real Tier A/B signal in noise. Whoever builds this (Q) needs to remove the field from the response schema, the parse function, and the `checkClaim()` call site together — not just delete the prompt paragraph. This is a build note for Q, not a reason to withhold sign-off on Peter's decision.

**2. Any new consequence beyond what Finding 3 already named?** Checked the real code for every place `protected_class_flag`/`protected_class_category` is read, not assumed:

- `is_big_issue` (generated column, migration lines 680-687) is computed from `category IN ('legal_exposure','owner_instruction')`, `escalation_signal IN (...)`, and `human_confirmed_big_issue` only. Not touched.
- `shouldCreateComplaint()` (`significance-pass.js` lines 503-509) keys on `escalation_signal`, `needs_human_call`, `owner_instruction_rejected`, `category`. Not touched.
- The `complaint_tracking.protected_class_flagged` `audit_log` entry (`significance-pass.js` lines 946-958) is triggered by `keywordCheck.flagged_protected_class` — `checkClaim()`'s output — not by `call1.protected_class_flag` directly. Not touched.
- No DB `CHECK` constraint on `missive_conversation_significance` ties `protected_class_flag`/`protected_class_category` to any other column (confirmed by reading Section D of the migration in full — the only comparable constraint, `complaints_flag_requires_category`, is on a different table's different columns from the retired pipeline).
- The one real reader: `archive-search/router.js` line 1849, the admin-only significance-pilot CSV export, which lists `protected_class_flag` next to `keyword_check_flagged_protected_class` as a side-by-side comparison column for Peter's own pilot review. Once the question is removed (and the fail-closed catch above is handled correctly), that column just reads `false` for every row going forward — a cosmetic loss of one comparison column in a CSV only Peter looks at, not a functional break anywhere else.

No UI surface, review queue, or trigger reads this field to decide anything. Nothing silently breaks beyond the CSV column and the fail-closed catch above.

**3. Does this need a fresh Rule 6 record?**

My read: no — Peter's direct, on-the-record statement in this conversation, plus this dated follow-up entry itself, is sufficient for a change of this size, and it's a different situation from tonight's legal-hold removal. GOVERNANCE.md Rule 6 reserves owner-approval-plus-attorney-review-plus-shadow-mode for **Critical** changes — decision criteria, compliance logic, permission tiers, guardrails. The legal-hold removal (Finding 1's resolution) was Critical because it removed the *sole* check standing between this pipeline and privileged content — nothing else in the system was catching that.
