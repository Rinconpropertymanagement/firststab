## The Phase 2 Question

Peter has said, directly, "lets launch phase 2." I want to give him a real answer, not a restatement of a verdict that was never actually about Phase 2.

**Phase 1 and Phase 2 are not the same kind of decision, and my original clearance was explicit about which one it was making.** Phase 1 changed nothing about what data exists or who can see it — it widened constraints and added registry rows against zero real rows of applicant data. Phase 2, per spec Section 9, is the first point in this entire build where a real, live external API gets called with real credentials, real LeadSimple process records for real applicants get pulled, and real `claims` rows get written that name real people — even paraphrased, even citation-disciplined, even with `review_status` starting `unreviewed` and no auto-promotion path. That is a materially different act than anything Phase 1 did, and GOVERNANCE.md treats it that way on its own terms: Rule 7 requires shadow mode before any user-affecting agent goes to production, and the Delivery Pipeline names a governance review of runtime agent code (step 10) as a distinct gate from the pre-activation hard gate (step 17) — they're not the same checkpoint run twice, they're two different checkpoints because the risk changes shape between them.

So I'm answering this in two parts, because Phase 2 itself contains two different kinds of work with two different risk profiles, and collapsing them into one yes/no would be exactly the kind of "spec-level clearance quietly stretched to cover more than it said" I want to avoid here.

### Clear to start now: building the pipeline and running the accuracy test

Q may start building the Phase 2 connector, the extraction logic for the four registered claim types, the Layer 1 + Layer 2 content-check wiring (Section 4), and the `source_reference`/`claim_text`/`source_link` discipline (Section 5) — all of this was already inside what I found buildable at spec level, and none of it requires a further design decision from me. This includes running the Section 8 accuracy test itself: pulling the ~20 real Application Screening cases and ~15 real Delinquency cases the test calls for, having a human fill a sealed answer key from the live records first, and grading the extractor's output blind against it. That test necessarily touches real applicant data, but it is exactly the kind of bounded, human-supervised, pre-launch check GOVERNANCE.md's own pattern expects before anything wider — it is not shadow mode, and it does not create an ongoing flow of unreviewed claims accumulating against new applicants. I already cleared this design at spec level; nothing about Phase 1 going live changes that analysis, so I'm not holding it up now.

Two things stay binding on Q while building this, not because I'm adding new conditions but because they were never optional to begin with: Mason's three conditions in `compliance/leadsimple-fair-housing-review.md` (Layer 2 judgment pass on Application Screening, paraphrase-only `claim_text` with one-click link-through, `leasing_reviewer`-scoped access) are permanent build requirements, not a pre-launch checklist Q can treat as satisfied once Phase 1 shipped. And Open Item 5 — whether the LeadSimple API supports an incremental/updated-since pull — is Q's to verify live during this phase, exactly as the spec already says; I have no independent view on it and don't need one before Q starts.

### Not yet cleared: entering shadow mode

What I have not cleared, and will not pre-clear now, sight-unseen, is the moment Phase 2 stops being a bounded accuracy test against a fixed sample and becomes the "90-day, 100%-review shadow mode... scoped to this domain" that Section 9 describes as the second half of Phase 2. That's the point where the pipeline starts running continuously against new and updated real applicants — not a fixed, human-supervised sample anymore, but an ongoing feed. Three things gate that step specifically, and none of them existed for me to review at spec-review time:

1. **The accuracy test has to actually pass, at the bar the spec itself sets.** Section 8's recommended exit bar — 0% missed and 0% wrong-source — is not a formality; it's the condition the spec itself names as required "before either domain is allowed into shadow mode." I want to see the actual graded result, not assume it clears, before shadow mode starts. If it doesn't clear the bar, that's not a build problem for Q to quietly work around — it's a design or extraction-quality problem that comes back to Asimov and likely Mason before shadow mode is reconsidered at all.

2. **"100%-review" needs an actual reviewer and an actual review mechanism, and neither exists yet.** Phase 5 (Tron's Hub review-queue UI) is scheduled after Phases 2–4, and Neo's Phase 1 migration is explicit that it granted `leasing_reviewer` to no one — "who actually gets `leasing_reviewer` is Peter's call," deferred exactly like `pod_lead` was. A 100%-human-review shadow mode with no one holding the access role and no built review surface isn't shadow mode yet; it's unreviewed claims accumulating in a table. Before shadow mode starts, I want confirmation of who will hold `leasing_reviewer`, and what they'll actually use to review each claim — even if that's a direct, read-only query against `claims` ahead of Tron's Phase 5 UI, that's a legitimate answer, but it needs to be a stated one, not an assumption.

3. **Open Item 6 is still mine, and it's still open.** The spec itself flags whether Application Screening's and Delinquency's shadow-mode clocks can run concurrently as "Asimov's call." This doesn't block Application Screening's own shadow mode from starting on its own timeline — Delinquency is Phase 3, not Phase 2 — but I'm noting it here so it isn't quietly assumed resolved by momentum once Phase 2 is underway. I'll make that call when Phase 3 is actually on the table, not before.

None of these three are reasons to stop Q from writing code today. They're the reasons I'm not, in this same document, also waving through the moment this system starts producing a continuous stream of claims about real people. That moment gets its own checkpoint, the same way GOVERNANCE.md's pipeline gives pre-activation its own hard gate rather than treating an earlier review as having already covered it.
