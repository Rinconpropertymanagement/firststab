## Scope

One table, created fresh by the migration named above: **`work_order_note_alerts`**, one row per Latchel work order that has triggered (or attempted to trigger) an alert email to a property's pod team about a special-handling note on file. See `work-order-notes-alert-SPEC.md` Section 1 for the feature this supports and Section 4 for the table's own spec.

This is a much smaller inventory than this codebase's other Rule 4 addenda (`leadsimple-tasks-workflows-data-inventory.md`, `archive-search-significance-complaint-merge-data-inventory.md`) because the table itself is smaller in both shape and risk: one table, no tenant/applicant narrative text, no FK to `tenants`/`owners`/`contacts` at all — it is scoped to a property and a Latchel job, not to a person.

---

## Why this table's conclusion is genuinely low sensitivity, not just asserted to be

- **The free text it stores is a snapshot, not a new store of narrative.** `notes_snapshot` is a copy of `properties.maintenance_notes` exactly as it appeared in a sent email (or the fixed held-content placeholder, if the content check caught something). It does not introduce a new kind of content into this schema — `properties.maintenance_notes` already exists, is already displayed today on Property 360, and was already scanned once (2026-09-06, zero Layer-1 keyword hits across all 194 populated values, plus Peter's own manual review — `supabase/migrations/20260906000000_add_maintenance_notes_to_properties.sql`). What changes with this feature is the *use* of that field (unprompted outbound email vs. login-gated display), not its sensitivity as data — that use-change is exactly what spec Section 7 flags for Asimov, and this document doesn't re-litigate it.
- **No tenant, applicant, or owner identifier.** The table's only subject-linking column is `property_id`. There is no `tenant_id`, `owner_id`, or `contact_id` anywhere on it, unlike `maintenance_claims` (linked to a ticket, which links to a tenant) or `operational_notes` (owner/tenant narrative by design).
- **The realistic worst case is a vendor's name or phone number**, not a tenant's. `maintenance_notes` values seen live include things like "Call Zack for approval on any work order" or a vendor's personal cell number — property-operational routing information, not commentary about a resident. This is the same caveat `properties.maintenance_notes`' own migration and `appfolio-maintenance-notes-governance-review.md` already recorded for the source column; this table simply inherits it as a snapshot.
- **No AI-authored characterization of a person.** Unlike `missive_conversation_significance.owner_instruction_note_text` or `complaints.description`, nothing in this table is AI-generated commentary about anyone's conduct. `notes_snapshot` is either a verbatim copy of an already-reviewed operational field, or a fixed, identical-every-time placeholder string. `flagged_category` is a short category label, not a narrative.

## Data Inventory (GOVERNANCE.md Rule 4 format)

- **`pii_fields`:**
  - `notes_snapshot` — property-level operational text (vendor contacts, owner approval routing). Can incidentally carry a vendor's name or personal cell number; does not carry tenant narrative. See "Why this table's conclusion is low sensitivity" above.
  - `flagged_category` — could indirectly indicate what kind of sensitive topic a note triggered on, without containing the topic text itself (same caveat this schema uses for every `flagged_category` column — `maintenance_claims`, `operational_notes`, `missive_conversation_significance`).
  - `send_error` — free text from a mail-send failure; in practice an SMTP/API error string, not personal data, but not schema-constrained to exclude it either. Worth a glance if this table is ever exported wholesale.
  - No SSNs, no bank/financial account numbers, no government IDs, no protected-class data by design (GOVERNANCE.md Rule 9) — nothing in this table's column list is a place protected-class data would land, and `flagged_protected_class`/`flagged_category` exist specifically to catch and exclude it from `notes_snapshot` before send, not to store it.
- **`agents_with_access`:**
  - The webhook route (`POST /api/approval-briefing/internal/webhook`, new branch) and the reconcile-poll route (`POST /api/approval-briefing/internal/reconcile-work-order-notes`) — both system/service-role, no human in the loop at write time.
  - Layer 1's `scanText()` (`maintenance-history/lib/protected-class-terms.js`) — deterministic keyword match, no AI, no network call, read-only against the note text before a row is written.
  - A Layer 2 AI classifier (Claude), only if Asimov/Mason adopt it per spec Section 7 — not decided in this document.
  - Hub users, wherever spec Section 8's proposed Property 360 "Work order alerts" card surfaces this table's rows. Exact role/tier gating is Q/Tron's call at build time, not set by this migration or this document.
- **`privacy_category`:** Property-level operational record. Lower sensitivity than `maintenance_claims` (which routinely carries health-adjacent tenant narrative) or `operational_notes` (owner/tenant narrative by design) — this table carries neither. Not zero, per the vendor-contact caveat above, which is why this is a light-touch addendum and not a "no PII, skip Rule 4" conclusion.
- **`retention_policy`:** **7 years.** Set directly by Peter, 2026-09-21 — "7 years, same as everything else," matching Rincon's standing retention policy already applied to comparable tables (e.g. LeadSimple's Application Screening/Delinquency tables). Asimov had declined to set this figure unilaterally and flagged that the 7-year LeadSimple analog might not even fit a table with no tenant/applicant/owner identifier — Peter was told that distinction directly and chose to apply the same standing figure anyway, as a deliberate business decision, not a default.
- **`ccpa_exportable`:** TRUE (expected — no data type here is categorically excluded from export; confirm at build time, same as every other table in this schema notes for itself).
- **`ccpa_deletable`:** TRUE in principle, via the same targeted `notes_snapshot` → `"[REDACTED]"` convention this schema already uses (`audit_log.details`, `maintenance_claims.claim_text`), preserving `latchel_job_id`/`send_status`/`trigger_source`/timestamps for audit continuity. **Finding which rows to redact for a given person is a manual v1 step** — this table has no `tenant_id`/`owner_id`/`contact_id` column to query by; a name or phone number is only reachable by reading `notes_snapshot`'s free text. This is the same accepted limitation `properties.maintenance_notes` and `maintenance_claims.claim_text` already carry, not a new gap this table introduces.
- **RLS:** Enabled, zero permissive policies at creation — matches every table in this schema. All access denied until a tool explicitly grants it via a policy scoped to authenticated users.

## Rule 9 — Protected-Class Data

`flagged_protected_class`/`flagged_category` exist specifically so this table structurally records when Layer 1 (and, if adopted, Layer 2) catch protected-class-adjacent content in a note before it goes out — the exclusion itself (holding the note, sending the placeholder instead) happens in application code (Q's build), this table just durably records that it happened and why, same pattern and same column names as `maintenance_claims`. No protected-class category vocabulary is invented here; `flagged_category` is free text, same reasoning as `maintenance_claims.flagged_category`, so Mason can refine categories without a migration.

## Rule 10 — CCPA Cascade

Not built by this migration — application code, per Rule 4's own inventory requirement, not something a migration implements. See `ccpa_deletable` above for the real, current shape of the gap: a deletion request naming a vendor mentioned in a note would need a manual text search across `notes_snapshot`, the same limitation already accepted for the field it's a snapshot of.

## Addendum, 2026-10-15 (rewritten 2026-10-16 for the no-AI design) — optional job title and description in the email (GOVERNANCE.md Rule 4)

Added alongside the optional "What the work order is" block (`work-order-notes-alert-SPEC.md` Section 6A), which can quote a Latchel job's own title (`job.name`) and description (`job.description`) in the alert email after cleaning and a required local word-list screen. This addendum covers only what that block changes in the data inventory; the table inventory above is unchanged. Governance record: `compliance/work-order-note-alerts-description-governance-review.md`; owner decisions: `compliance/work-order-note-alerts-description-decision-resolution.md`.

- **No new storage in the table.** The title and description, and anything derived from them (excerpts, lengths, hashes, matched words, per-word counts, the screen result), are not written to `work_order_note_alerts` (`notes_snapshot` stays notes-only, `flagged_protected_class` stays FALSE, `flagged_category` stays NULL; those two columns describe the maintenance-notes snapshot and must not be reused for job text), any log line, or the failure email to Peter. The one audit event this adds (`work_order_note_alert.description_checked`) is counts-only: job id, trigger source, mode, result, cause, a yes/no for "only ordinary words matched", a version string and flags. Never matched words, text or category names.
- **No category name is stored (changed in the third fix round, 2026-10-16).** An earlier version of this addendum allowed category names (safety and violence, minors, health, immigration, legal and so on) in the audit row next to a job id and property id, and said to treat them like `maintenance_claims.flagged_category`. That is withdrawn. A category name next to a job id and a property is a sensitive inference about a household, `audit_log` keeps its rows indefinitely, and Peter's standing rule is that protected-class data is never stored in any table. The audit row now has no category name, no list of them and nothing derived from them; the screen knows in memory which kind of word matched, and nothing carries it out of the screen call. The shadow-week queries do not group by category. (Asimov R3-1, Sentinel S2-C.)
- **The email channel is an uncontrolled copy.** When the block is switched on, the sent email is the only copy of the title and description, and it lives in places this system does not control: the two pod shared inboxes (Solimar and Faria), Missive (which reads those inboxes), and the sent mail of the `noreply@` account. Job text is free text that a tenant, vendor or property manager may have written, so those inboxes can now hold it. Retention for those copies is not set by this system, and no retention figure is set here. Whether tenant-written text may lawfully be kept there, and for how long, are the two legal questions Mason would have answered; Peter overrode that review and they are recorded as "accepted by owner, not reviewed by counsel".
- **Not sent to Anthropic or any other processor. Scanned in memory on the Hub server only.** The screen is a word list (`lib/work-order-text-screen.js` and `lib/work-order-text-screen-terms.js`, plus the shared `scanText()` read-only) that runs in the Hub process. No model is called, no API key is used, no network call is made with the text, in `off`, `shadow` or `on` mode. This replaces the earlier design in which the text would have been sent to Anthropic for a show-or-hide check; Peter declined that on 2026-10-16. Three tests prove it (`approval-briefing/test/no-ai-proof.js`).
- **Agents and code with access (`agents_with_access`).** The scan functions `scanText()` and the feature-local screen, in the Hub process, with no AI. The Latchel connector's read-only `getJob` lookup (only when the job in hand has no `description` key at all). Nothing else reads the text.
- **Personal details typed into the description are NOT screened.** Tenant names, phone numbers, e-mail addresses, unit numbers and gate, lockbox and alarm codes pass through to the email. Peter accepted this in writing on 2026-10-16; the email says so in its last line ("Not checked for names, phone numbers or access codes. Internal use only.").
- **Deleting a description is a manual search.** A deletion request that involves something typed into a work order's title or description cannot be answered from this system's own tables, because it stores none of it. It needs a manual search of the pod inboxes, Missive and the `noreply@` sent mail (and Latchel itself, which stays the source of truth).
- **Condition for switching ON: the Missive intake must not copy these alerts.** The Hub's Missive intake (`storeMessage` in `email-intake/lib/shared.js`) copies every message from the two pod inboxes into `missive_message_intake` (`body_html`, `body_text`) and into `archive_search_corpus`, where Archive Search users can search it and the significance and severity passes send stored message text to Anthropic. Jarvis counted, read-only, on 2026-10-16: 153 of the 160 alerts sent so far (subject starts "Work Order Alert", from `noreply@rinconmanagement.com`; a domain-level count) were already copied; they predate the description and hold none. With the description in the email those copies would store tenant-written text in tables searchable by every Archive Search user, which contradicts the storage rule and Peter's decision that nothing from the job text goes to Anthropic. Peter's written acceptance covers the copy in the inboxes, Missive and the sent folder, not this. So `on` is blocked until the exclusion is deployed and verified: the exclusion lives on its own branch (`feature/email-intake-exclude-work-order-alerts`, commit `3f6922e`); per Jarvis, Peter said yes on 2026-10-16 and it was deployed on its own at about 15:10 local that day, and it has NOT yet been seen skipping a real alert. `WORK_ORDER_ALERT_INGESTION_EXCLUSION_VERIFIED=yes` is set only after a real alert is seen to be skipped. The 153 existing copies are left alone; any deletion is Peter's separate, explicit decision and must respect the table's retention rules.

### Second fix round, 2026-10-16 — what changed in this inventory

Nothing new is stored. These are the changes to what is read and how, after the tester, security, red-team, chaos, governance and judge reviews of the first no-AI build:

- **One more value is read from the Latchel lookup result: its own job id** (`job_id`, else `id`), once, only to confirm it is the job that was asked for. It is never shown, stored or logged. The lookup itself runs only for a job id that is plain digits (at most 12), so nothing but a number can be placed in the Latchel address; any other id, or an answer for a different job, is treated as "could not be retrieved" and nothing from that answer is read further.
- **The text is read twice, in memory.** The cleaner now produces two readings of each field (the shown one, and one in which each removed invisible character or tag became a space) and the screen reads both. Both exist only for the length of the call. Neither is stored, logged or returned; only the same counts-only audit event is written.
- **The printed pieces are checked again.** After the 100 and 300 character cut, the exact strings that would be printed are run through the link detector and, when something was cut, the screen again. Still in memory only.
- **More words, one version.** The local list is now `wo-supp-v2` (additions only; the third fix round extends it to `wo-supp-v3`, below). No category name is recorded for a hold (see above).
- **No attempt is counted when there is nobody to send to.** If no pod inbox is on file the block is not built, so no Latchel lookup is made and no `description_checked` audit row is written for that attempt. Fewer rows, not more.
- **Mail errors.** The original mail error text is kept in modes `off` and `shadow` (no job text is in the email); it is reduced to a short known code only in mode `on`.
- **Numerals are shown as typed.** Fractions, powers, degrees and similar marks are no longer rewritten by the cleaner. This changes what the email shows, not what is stored (nothing is).

### Third fix round, 2026-10-16 — what changed in this inventory

Nothing new is stored, and one thing that was stored is gone. These are the changes after the second round's tester, security, red-team, governance and judge findings:

- **The audit event no longer carries any category name.** The `work_order_note_alert.description_checked` row keeps only: job id, trigger source, mode, result, cause, the yes/no for "only ordinary words matched", the version string, and the flags (`truncated`, `fallback_getjob_used`, `pod_unassigned`, `on_downgraded`, `trace`). Rows written by an earlier build, if there were any, would have held category names; none are known to exist, because no earlier build was deployed with the block active (the review SQL in the SPEC no longer reads that key).
- **One new cause value: `unsettled_text`.** Text that the cleaner cannot settle (deeply nested entities or tags, or the cleaner's time budget) is held under this cause instead of being counted as a scanner error. It carries no text and no count of it; one constant log line is written.
- **More is read in memory, never stored.** The screen reads a third copy of the text (every run of characters that is not a letter or digit as one space) and a squashed copy (no separators at all), and the cleaner reports a yes/no "hold this block" for a sentence-break shape. All exist only for the length of the call.
- **More words, one version.** The local list is now `wo-supp-v3`: the 213 v2 terms plus 331 v3 terms (additions only; counts and a diff are in the build report and the governance review). They are the same kind of word list as before and hold the whole block.
- **Quotes.** A straight double quote typed in the title or description is shown as the double prime in the email so the text cannot close the quote around the description. This changes what the email shows, not what is stored.
- **Still true:** the text is not stored or logged anywhere, nothing is sent to any model or other service, personal details typed into the description pass through unscreened (Peter's written decision), and the sent email remains the only copy, in the pod inboxes, Missive and the sent mail of the `noreply@` account.

### Fourth fix round, 2026-10-16 — what changed in this inventory

Nothing new is stored. These are the changes after the third round's tester, security, red-team, governance and judge findings:

- **One new value of an existing field: the `cause` in the audit event can now be `link_shape`.** It is written when the cleaner itself asks for a hold (a sentence typed with no space after its full stop, which also looks like a brand-looking web address, or a web-like fragment that the 100 or 300 character cut leaves). No word list was involved, so it is counted apart from the sensitive-word holds (`local_screen`). It is a constant string. The row keeps exactly the same eleven keys and the trace; there is still no category name, no text, no length, no hash and no count per word.
- **The text is read up to four times, in memory.** Besides the shown reading and the reading in which removed invisible characters and tags became spaces, the cleaner now produces a reading in which each symbol that Unicode turns into letters became a space, and one with both changes, and the screen makes one more reading of its own (the same symbol rule, and the section sign read as the word "section"). All exist only for the length of the call; none is stored, logged or returned.
- **More words, one version.** The local list is now `wo-supp-v4`: the 213 v2 terms, the 331 v3 terms and 56 v4 terms plus three pair rules (additions only; the counts and a readable diff are in the build report). They are the same kind of word list as before and hold the whole block. Snapshots of the v3 and v4 lists are kept in the test fixtures next to the v1 and v2 snapshots, so a deleted word fails a test.
- **Still true:** the text is not stored or logged anywhere, nothing is sent to any model or other service, personal details typed into the description pass through unscreened (Peter's written decision), and the sent email remains the only copy, in the pod inboxes, Missive and the sent mail of the `noreply@` account.

### Fifth change, 2026-10-17 — the owner switch that turns the content screen off (`WORK_ORDER_ALERT_DESCRIPTION_SCREEN`)

Nothing new is stored. This addendum covers only what the owner's switch changes in this inventory; the decision record (Peter's words, the risks he accepted, how the override is recorded) is Asimov's and is in `compliance/work-order-note-alerts-description-decision-resolution.md`, section "Peter's decisions of 2026-10-17" (conditions and the switch-on steps: `compliance/work-order-note-alerts-description-governance-review.md`, Sections 19 and 20), not here. The switch is Peter's own choice, relayed by Jarvis from chat; it is an owner override of the content screen itself, never a met condition. Spec: `work-order-notes-alert-SPEC.md` Section 6A, "Owner switch".

- **The switch.** `WORK_ORDER_ALERT_DESCRIPTION_SCREEN`; only the exact lowercase value `off` turns the screen off. Unset or any other value leaves the screen on, and the behaviour is then byte-identical to the fourth fix round (a fixture proves it). `.env.example` names it and sets no value. It does nothing while `WORK_ORDER_ALERT_DESCRIPTION_MODE` is `off`.
- **What changes about the email copy (the uncontrolled copy described above).** With the switch off, the title and description are quoted without the word-list screen, so job text that the screen would have held is emailed word for word to the pod shared inboxes (Solimar and Faria; both, for a property with no pod), and from there it lives in Missive and the sent mail of the `noreply@` account, where it cannot be unsent. That text can include sensitive facts about a household (health, family, immigration status, violence, a child's name) and protected-class information. This system still stores none of it: the single copy it creates is the sent email. Whether such text may lawfully sit in those inboxes, and for how long, are the same two legal questions that were answered by Peter's override of Mason's review (recorded as "accepted by owner, not reviewed by counsel"); the switch makes the exposure larger, not different in kind.
- **The never-store mask (new, and the only content-based change to the text).** Before the email is built, a best-effort pattern list replaces with `[removed]` the known written forms of a Social Security number, a payment card number (and security code), a bank account, routing, IBAN or SWIFT number introduced by its word, and a password-like secret in the title or description (`maskNeverStore`, `lib/work-order-text-clean.js`). It exists so the email is less likely to carry the three things Peter's standing rule forbids in any file or table. It is a list of shapes, not a guarantee: the SPEC lists what it does not catch (an account number with no keyword, a card in an unusual grouping written next to another number, a passphrase with spaces, the last four digits of a number, text written after an IBAN, other words for a code or a login, look-alike letters) and its known false positives (updated after round 6, commit `c8e6c71`). Phone numbers, e-mail addresses, names and gate, lockbox and alarm codes are NOT masked (Peter's earlier decision).
- **What is still not stored or logged.** The audit event keeps exactly its eleven keys plus the trace: job id, trigger source, mode, result, cause, a yes/no for "only ordinary words matched" (always false for an unscreened row), the version string, and the flags. With the switch off the version string is the constant `unscreened-owner-override`, which tells a reader of the audit log that nothing was screened and the mask ran. There is still no text, no category name, no length, no hash, no matched word, and no count of masked items. `risk_level` is `medium` for every unscreened row.
- **One new value of an existing field: `cause` `unprintable_text`.** Written when the text cannot be made safe to print (the cleaner cannot settle it, or the value is not text); the block is then the neutral "could not be retrieved, see Latchel" line (`result` `unavailable`), the alert is still sent, and one constant log line is written. It is a safety fallback, not a content hold.
- **Agents and code with access.** Unchanged: the cleaner (now including the mask) in the Hub process, with no AI; the read-only Latchel lookup. With the switch off the word-list screen is not consulted at all.
- **Deleting a description.** Unchanged: a manual search of the pod inboxes, Missive and the `noreply@` sent mail (and Latchel, the source of truth); nothing in this system's tables holds the text.
