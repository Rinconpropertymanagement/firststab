## 0. Governance Track and Status

**This is a Core-track governance review, not Incremental, and it needs its own Asimov pre-check — not a reuse of LeadSimple's.** Four reasons, each independent of the others:

1. **This is the first Property Brain feature that originates outbound communication to a human.** Every domain built so far (`maintenance`, the three `leadsimple_*` domains) only ever reads and stores. Approval Briefing emails a Property Manager automatically and hands a drafted email toward an owner. `PROPERTY-BRAIN-ARCHITECTURE.md` §8's Core list (the shared safety layer, `claims`' core discipline, `claim_type_registry`, the version manifest) never contemplated a pipeline that sends anything — the design doc's own idea #6 says so directly ("This is the first Property Brain feature that sends anything — that's new"). GOVERNANCE.md Rule 8's three-tier permission model needs to be explicitly assigned here, not assumed: **Tier 1 — basically automatic, low-risk — is this pipeline's target end state for the PM briefing email, not its starting status.** No decision is made or executed by the act of sending it, which is why Tier 1 is the right goal to build toward; but that framing isn't earned yet, because it depends entirely on the content-check filter (Section 5) actually catching what it's supposed to catch before flagged AI text can ever reach an email, and nothing has demonstrated that in practice yet — proving that out in practice is the specific job of Phase 8's shadow-verification period (Section 12), not an assumption this spec gets to make in advance. Until Phase 8 closes, this pipeline should be treated as running under Tier 2 discipline — reviewed before being trusted as automatic — not presented as already-safe. Every step that could look like a decision — the risk assessment, the emergency match, the drafted owner email — is **Tier 2 (Ask First)**, matching the design doc's own ground rule: "Never decides anything. It presents facts, cited, for a person to act on." No output of this pipeline is Tier 3, because nothing here approves, denies, or conditions a housing decision — but that conclusion itself is exactly the kind of judgment call Asimov's pre-check exists to confirm, not assume.
2. **A new external credential and a new inbound trust boundary are required.** Per the webhook research: Latchel's webhook-delivery verification secret is not self-serve — it requires emailing `tech@latchel.com`, and it is a shared, repeated token rather than a cryptographic signature over the payload (no HMAC was found documented anywhere). §8's own text names exactly this as disqualifying for the Incremental track: *"a new external credential, a new source-of-content type the safety layer hasn't seen before... pushes it back to a full core-level review."* This domain also introduces the account's first genuinely **inbound, unauthenticated-until-verified** HTTP endpoint (Section 3) — every prior internal route in this Hub is either behind `requireLogin` or behind an outbound-only `CRON_SECRET` header this codebase itself controls. An endpoint the public internet can hit, gated only by a shared secret Latchel controls the delivery of, is a new attack surface this codebase hasn't had before. Sentinel's review — separate from and in addition to Asimov's — should treat this endpoint as a first-class target before it goes live.
3. **The Fair Housing Standard's own stated scope covers this literally, even though this domain never makes a housing decision.** GOVERNANCE.md: *"Any tool, agent, listing, or communication that touches an applicant, a tenant, a listing, or a housing decision MUST comply."* Approval Briefing's tenant-context category (Section 4) touches an existing tenant's maintenance-request pattern and, per the design doc's own explicit exclusion, deliberately leaves out rent-payment status — a decision the design doc frames as already having weighed a disparate-impact-shaped risk once. Nothing here screens, scores, or characterizes a tenant, and no applicant is ever in scope — this domain is structurally different from LeadSimple Application Screening's risk profile, and Section 0's own correction from that spec applies here too (a domain that *touches* tenant data isn't automatically Fair-Housing-disqualified from a lighter track the way a domain whose vocabulary is *itself* protected-class-shaped would be). But the Standard's literal text still triggers a review — Mason should read the tenant-context and risk-assessment prompt language (Sections 4–5) before this ships, specifically checking that "recent maintenance-request pattern" and "risk of property damage" framing can't read as a soft characterization of the tenant, the exact failure mode Rule 5 of the Standard names.
4. **The maintenance-limit mismatch finding is itself a governance-relevant fact, not just a product one.** The design doc's own resolved item records that Latchel's internal spending cap and AppFolio's real contractual maintenance limit disagree on 49 of 50 real properties checked, and that Peter's decision was to never write to Latchel to fix it — this tool only ever reads, from both systems, and reports AppFolio's number as authoritative for what a PM sees. That's a real, live, decided fact about data quality in a system this tool depends on, and it belongs in front of Asimov before a build starts, not discovered afterward.

**What this section does NOT require:** a second Fair Housing sign-off document the weight of `compliance/leadsimple-fair-housing-review.md`. That document exists because Application Screening makes decisions about prospective tenants under Rule 2. This domain makes no decision about anyone — Mason's review here is scoped to language and framing (item 3 above), not to a screening-criteria review, and should be sized accordingly.

## 1. Scope — What This Is, and Isn't

**This is a one-shot gather-plus-email-plus-log event per work order, not an accumulating knowledge base.** That's the single biggest structural difference from every domain built on this platform so far, and it drives most of Section 2's decision. `maintenance` and the three `leadsimple_*` domains all answer "what do we know about this property/process, cumulatively, over time" — a claim written today is still true and queryable a year from now. Approval Briefing answers a narrower, time-boxed question: "what did we tell the PM, when, and was the AI's read of the risk right" — for exactly one Latchel job's exactly one trip through "Needs Approval." The design doc's own resolved items already commit to this shape: separate email per work order (no bundling), a "last updated" timestamp instead of active re-watching, no auto-send to the owner ever.

**In scope for this spec:**
- Detecting a Latchel job entering "Needs Approval" (`state_id = 27`, confirmed live).
- Gathering the five briefing categories from Section 4, honestly marked where research found a gap.
- A cited AI risk assessment and an emergency-category match against a maintained list.
- A cost benchmark against Rincon's own real invoice history, where enough data exists.
- Two emails: a full briefing to the PM, and an editable draft toward the owner (PM copy/pastes it themselves — no owner-facing send path exists in v1).
- A reminder-then-escalate timer if nobody acts, and a record of who the escalation went to.
- An audit trail of what a given briefing said, and whether the PM agreed with the risk call.

**Explicitly out of scope, per the design doc's own resolved items — restated here so a future builder doesn't reopen them:**
- Writing anything back to Latchel, ever — including its cost-cap/`max_cost` field, even where it's demonstrably wrong (design doc, "Still to confirm," last item).
- Auto-sending the owner email. The PM always copies, edits, and sends it themselves.
- Deciding whether a genuine emergency needs owner approval before work starts — that PM judgment call is untouched; this tool only gets the facts in front of them faster.
- Bundling multiple concurrent work orders on the same property into one email.
- Actively watching a sent briefing for changes and re-sending — a "last updated" timestamp is the only freshness signal.
- Rent payment status anywhere in the tenant-context category — deliberately excluded per the design doc, not an oversight.

## 2. Data Model — Claims vs. Dedicated Tables

### 2.1 The honest answer: mostly not `claims`, and one deliberate exception

`claims`/`claim_type_registry` exists to solve a specific problem — described precisely in `PROPERTY-BRAIN-ARCHITECTURE.md` §1.3: a fact about **something that happened**, extracted once, cited, sitting in a shared store for a human to eventually review, correct, or confirm, and for a *different* future feature to query later ("everything we know about this property, across every domain"). Every claim in every domain built so far is append-only in that sense — a ticket's status changed, a process entered a stage, a task was completed. Nothing about those facts is time-boxed to one feature's own send-a-message-and-track-a-timer lifecycle.

Approval Briefing is structurally different in a way worth naming precisely rather than glossing over: most of what it does is **workflow orchestration state about one specific event**, not a durable fact about the world:
- "The PM briefing email was sent at 3:14pm to these three addresses" is not a fact anyone would ever need to dispute, correct, or re-review the way a claim is — it's a log entry about *this pipeline's own actions*, not an extraction from a source system.
- "A reminder fired because 48 hours passed with no response" is the same — pipeline state, not an extracted fact.
- The generated PM-briefing email body and the drafted owner email are **compiled documents**, not atomic facts — forcing either into `claim_text` (a single short sentence field, by every existing claim's own convention) would either truncate them meaninglessly or turn `claims` into a document store it was never designed to be.
- The PM's agree/disagree feedback on the risk call is a genuinely different kind of signal than `claims.review_status`/`correction_reason_code` already captures (Section 10 below draws this distinction out fully) — it isn't "was this claim accurate," it's "do I trust the AI's judgment here," a professional-judgment question `correction_reason_code`'s existing controlled vocabulary (`WRONG_SOURCE`, `HALLUCINATED_DETAIL`, etc.) has no category for.

Forcing all of this into `claims` would mean either inventing claim_types that don't behave like facts at all (an `email_sent` "claim" nobody will ever mark `confirmed`/`corrected`, silently bloating every reviewer's queue with rows that don't belong there) or building a second, parallel set of columns bolted onto `claims` just for this one domain's workflow state — which is precisely the kind of narrow-domain-reshaping-the-shared-table problem the architecture doc's own Section 1.2 rejected when it chose one shared table over domain-specific ones in the first place. The right call here is the mirror image of that reasoning: **this workflow state doesn't belong in the shared table, because it isn't a shared kind of fact.**

**The one deliberate exception: the risk assessment.** The design doc is explicit that this component is different in kind from the rest of the gather step — *"this is a judgment call the AI has to make by reading the ticket, not a field it looks up. It has to be cited and explained, not a silent yes/no the PM just trusts."* That sentence describes exactly what `claims` was built for: an AI inference over free text, sourced, confidence-scored, sitting behind a human review gate, with the same protected-class content-check discipline every other domain's free-text extraction already gets. It also has genuine value being visible cross-domain — a property's history of past risk assessments sitting alongside its maintenance claims in one future property-overview query is exactly the payoff `PROPERTY-BRAIN-ARCHITECTURE.md` §1.2 built the shared table to produce. So: **one new claim_type, `risk_assessment`, registered under a new domain `approval_briefing`** — nothing else in this feature becomes a claim.

**What was deliberately considered and rejected, named so it isn't rediscovered later:**
- A deterministic `event` claim for "job entered Needs Approval" (mirroring `maintenance`'s own deterministic event claims from Latchel state history). Rejected for now — this fact is fully captured as a field on the new table below (Section 2.3), and it isn't yet clear a second feature wants to query it cross-domain the way risk assessments plausibly are. **Concrete trigger to revisit:** the day a property-overview screen wants "approval history" listed alongside maintenance claims — cheap to add later as a second registered claim_type, not worth building ahead of that proven need today.
- The cost benchmark as a claim. Rejected — it's a **computed rollup** over invoice history (median, range, sample size), not an extraction from one cited source the way every existing claim is. Nobody will ever "correct" a median; if the underlying invoice-matching logic is wrong, that's a data-pipeline bug to fix in code, not a claim to mark `corrected`. It's stored as a field on the new table (Section 2.3), recomputed at gather time, not cached as a fact of record.

### 2.2 What this reuses from the platform, unchanged

- **`claim_type_registry`'s fail-closed foreign key.** The one new `(approval_briefing, risk_assessment)` row must be registered before any claim can be inserted using it — same enforcement, same migration convention (`INSERT ... ON CONFLICT DO NOTHING`) already used twice.
- **The two-layer content check** (`content-check.js` + `protected-class-terms.js`), unmodified, run on every `risk_assessment` claim's `claim_text` before insert — per the design doc's own ground rule, even though this isn't primarily a Fair Housing–sensitive domain. A risk-assessment prompt reading a ticket's free-text description is exactly the kind of place a stray health or disability mention (the same failure mode the original 10-ticket maintenance test surfaced) could show up.
- **The `source_reference`/`claim_text` citation discipline** from `PROPERTY-BRAIN-ARCHITECTURE.md` §1.2.1 and the LeadSimple spec's §5 extension of it: `source_reference` is a structural pointer only ("Latchel job 716584, description field + estimate_note field, read 2026-08-27"), never the ticket text itself; `claim_text` is the AI's cited reasoning in plain English, never a verbatim reproduction of tenant-written free text.
- **`claims.source_link`**, added in the LeadSimple migration for exactly this purpose — populated here with a constructed link back to the Latchel job (`https://app.latchel.com/...` — the exact deep-link shape needs the same live verification the LeadSimple spec did for its own `link` field; **flagged as an Open Item, not assumed**, since no research pass here confirmed Latchel exposes a job-level deep link the way LeadSimple's `Process.link` field does).
- **The `review_status`/`correction_reason_code` review gate**, with one addition — see Section 10 for why `correction_reason_code`'s vocabulary needs a new value for this domain specifically.

### 2.3 The new table: `approval_briefings`

One row per Latchel job's one trip through "Needs Approval" (a job that resolves and later re-enters approval — a rare but real path per Latchel's own two trigger conditions — gets a **second** row, not an update to the first; each is a distinct event with its own briefing, its own timer, its own outcome).

Fields, grouped by purpose (exact types/constraints are Neo's call in the Phase 1 migration — this spec states the requirements, not the SQL):

**Identity and linkage**
- `latchel_job_id` (always present — the one field guaranteed available the instant the webhook or poll fires)
- `latchel_property_id`, `appfolio_property_id` (raw join-key text, captured even when `property_id` below can't resolve yet)
- `property_id` (nullable FK → `properties`, RESTRICT) — resolved via `properties.latchel_property_id` at gather time; **nullable specifically because that column is confirmed live at 0% populated today** (Section 2.4)
- `maintenance_request_id` (nullable FK → `maintenance_requests`, RESTRICT) — resolved opportunistically via `latchel_job_id`; **nullable because only 47 of 483 tickets are matched today** (tenant/vendor research)
- `trigger_reason` (`new_job_no_estimate` | `estimate_exceeds_authorization`) — Latchel's own two documented paths into state 27
- `trigger_source` (`webhook` | `reconciliation_poll`) — which path actually caught this instance (Section 3)
- `entered_needs_approval_at` — from the webhook's `state_updated_at` when present, else resolved via `GET /jobs/{id}/history/state` (the confirmed-reliable fallback per the webhook research, since `state_updated_at` is documented on the webhook schema but was found **absent** from the live `GET /jobs/{job_id}` response)

**What was gathered (Section 4), captured as structured data only — never raw free text**
- A structured snapshot of the numeric/categorical Latchel fields read at gather time: `estimate`, `max_cost`, `issue_id`, `category`, `is_urgent`, `is_emergency`, `severity`, `state_name`. **Hard rule, matching the discipline `claims.source_reference` already enforces elsewhere in this schema: this snapshot column may never include `job.description`, `job.vendor_description`, or `job.estimate_note` verbatim.** Those free-text fields are read only by the risk-assessment prompt (Section 5), which is the one place in this pipeline that content-checks free text before it lands anywhere durable. A raw-JSON "just capture everything" column here would quietly recreate the exact unguarded-second-copy risk `PROPERTY-BRAIN-ARCHITECTURE.md` §1.2.1 named for email citations — the same failure mode, one column over. `job.access_instructions` is a fifth free-text field, deliberately outside this snapshot's scope — it isn't distilled into a citation the way `description`/`vendor_description`/`estimate_note` are, because it needs to reach both email templates as a literal instruction string. It is not exempt from content-checking for that reason; it has its own dedicated gate, run at gather time before either template can read it — see Section 4.4.
- `appfolio_maintenance_limit` (nullable — **field/report name unconfirmed, see Section 4.2**)
- `cost_benchmark` (nullable structured value: median, low, high, sample size, matched `issue_id`) or an explicit "insufficient history" marker — never a bare number with no sample size, per the benchmark research's own caution and the design doc's idea #4.
- `emergency_match` (structured: matched-category-or-null, the list version used, plus Latchel's own `is_urgent`/`is_emergency` flags carried separately — see Section 6 for why these must never be conflated).

**The risk assessment — self-contained on this row, not solely dependent on the `claims` join**
- `risk_assessment_text`, `risk_assessment_confidence` — always populated here directly, because Section 10's "keep a record of what the PM was actually shown" requirement (idea #6) must hold even in the case where `property_id` couldn't resolve and no `claims` row was written at all.
- `risk_assessment_claim_id` (nullable FK → `claims`) — populated only when the subject resolved and the claim was successfully written; the durable, reviewable, cross-domain-visible copy.

**What was sent**
- `pm_briefing_recipients` (email array), `pm_briefing_sent_at`, `pm_briefing_body` (the actual rendered text sent — the audit record idea #6 asks for)
- `owner_draft_text` (generated, never sent by this system)
- `last_data_refresh_at` — the "last updated" freshness stamp the design doc's resolved item calls for

**Reminder / escalation / outcome**
- `reminder_sent_at` (nullable)
- `escalated_at`, `escalated_to` (nullable email array)
- `resolved_state_name`, `resolved_at` (nullable) — captured by the reconciliation poll once the job's `state_id` moves off 27; see Section 9 for how this doubles as the "was it acted on" signal and Section 4.2 for why this is also the seed of a future, appropriately-caveated owner-decision history

**Feedback loop (Section 10)**
- `pm_risk_feedback` (`agreed` | `disagreed` | `not_recorded`, default `not_recorded`)
- `pm_risk_feedback_notes`, `pm_risk_feedback_recorded_by`, `pm_risk_feedback_recorded_at`

**What this deliberately does NOT include:** a separate `approval_briefing_events` append-only sub-log. Considered and rejected — every other domain in this codebase that needs a per-instance timeline (`security_deposit_cases`, for one) tracks it as timestamped columns on the case row itself, not a parallel event table, and the platform-wide `audit_log` (Section 10, Rule 1) already supports `entity_type = 'approval_briefing'` / `entity_id = approval_briefings.id` lookups for anything a summary column can't capture. A second table here would be exactly the kind of building-ahead-of-a-proven-need this codebase has consistently avoided.

RLS: enabled, zero permissive policies at creation — matches every table in this schema.

### 2.4 The property-matching prerequisite — a real blocker, not a formality

The tenant/vendor research confirmed live: Latchel's `ref_property_id` matches AppFolio's own property ID **directly**, no fuzzy address matching needed — but `properties.latchel_property_id` (the column that's supposed to store that match, added by the maintenance-history migration) is **confirmed at 0% populated across every property in Supabase today.** That means, as of this spec, `property_id` cannot resolve for a single real job — the risk-assessment claim's `claims_has_a_subject` requirement (property_id OR maintenance_request_id, both currently unreliable for a brand-new job) would fail for effectively every real briefing until this is fixed.

This is why Section 2.3's design keeps the pipeline **fully functional without it**: `risk_assessment_text` lives directly on `approval_briefings` regardless, so the emails go out and the PM gets a real briefing even before this backfill runs. What's lost until it's fixed is only the `claims`-store benefit — cross-domain visibility and the reviewer queue. **This backfill is a named Phase 1 prerequisite (Section 12), not a someday-nice-to-have:** a small, mechanical reconciliation job populating `properties.latchel_property_id` from the already-confirmed 1:1 `ref_property_id` match, using the exact matching logic the tenant/vendor research already proved out live.

## 3. Trigger: Webhook Receiver + Polling Backstop

### 3.1 Why this domain does NOT use the architecture doc's Stage 0→3 pipeline

`PROPERTY-BRAIN-ARCHITECTURE.md` §2's pipeline (privilege filter → Fair Housing scan → multi-label understanding → content check + store) is built for one specific problem: an email thread of unknown relevance that might touch any number of domains, needing a privilege gate before an AI ever reads it. Nothing about Approval Briefing's trigger is that shape — it's a single, structured, already-known-relevant Latchel API event, not an inbox full of correspondence needing routing. Reusing that pipeline here would bolt a privilege/multi-label classification step onto something that was never ambiguous about what it is. What this domain *does* reuse from that architecture — the content check on free text, the citation discipline, the fail-closed registry — is exactly the machinery that generalizes; the routing pipeline itself does not, and isn't force-fit here.

### 3.2 Primary path: Latchel webhook

Confirmed live (webhook research): registration is dashboard-only (Account Settings → Integrations → Webhook), and because `Model`/`Event` are each single-select, **two separate subscriptions are needed, both pointed at the same URL** — `Job / created` and `Job / updated` — since a job can enter "Needs Approval" either fresh (no estimate yet) or via an update (a vendor's estimate now exceeds what's authorized). Both were confirmed live in the current "Needs Approval" queue: 4 of 10 real jobs checked had `estimate: null` (the `created` path), 6 had `estimate > max_cost` (the `updated` path) — e.g. job 726301 (`estimate: 2827.80` vs `max_cost: 100`) and job 714415 (`estimate: 12500` vs `max_cost: 75`).

**Every delivery must be filtered by the receiver itself, not trusted as pre-scoped.** Latchel's `Job/updated` webhook fires on *any* tracked field change — a description edit, a vendor reassignment, a rescheduled appointment — not just an approval-status change, and Latchel has no server-side filter for "only tell me about state changes." The receiver's first and only real logic is: does `object.state_id === 27` (or `state.name === "Needs Approval"`)? If not, acknowledge and discard — do nothing else.

**A second, unrelated Latchel "Needs Approval" exists — for invoices, not jobs.** Confirmed in the webhook research and worth a hard callout here so it never gets conflated in Q's build: Invoice-object "Needs Approval" is a different `object_type`, a different trigger (a pre-payment hold, auto-approving after 3 days unless a PM intervenes), entirely out of scope. The receiver only ever processes `object_type === "Job"`.

### 3.3 Endpoint location, shape, and the new credential

This is the same shape of problem the Hub's existing internal routers already solve — `insuranceInternalRouter`, `securityDepositInternalRouter`, `maintenanceHistoryInternalRouter`, `callStatsInternalRouter`, `contentEngineInternalRouter` are all mounted in `server.js` **before** `app.use(requireLogin)` specifically so an external caller can reach them without a browser session. A new `approvalBriefingInternalRouter`, mounted the same way, is the natural home — `server.js` already binds to `127.0.0.1` with Sally's nginx proxy in front (per the `e3eec18` commit), so a new route here is reachable at the Hub's existing public HTTPS address with no new infrastructure.

**What's genuinely new here, unlike every prior internal route:** authentication can't be `CRON_SECRET`, because Latchel — not this codebase — controls the request format. Latchel's own mechanism is a `secret` field in the JSON body plus a duplicate `x-api-key` header, both account-specific UUIDs **that are not self-serve** — obtaining them means emailing `tech@latchel.com`, a new step this project hasn't taken yet (confirmed: `.env`/`.env.example` define only `LATCHEL_API_KEY` today, nothing webhook-related). This is Section 0's second reason for the Core governance track, restated concretely: `LATCHEL_WEBHOOK_SECRET` is a new credential this codebase has never held, verifying a caller this codebase does not control the traffic shape of. **No IP allowlist exists on Latchel's side** (confirmed across every doc source checked) — the "signature" is a repeated shared token, not a cryptographic signature over the specific payload. Flagged plainly for Sentinel's review, not a build blocker on its own, but a real limitation the endpoint's own code should account for (rate-limit the endpoint itself, log every rejected verification attempt, never trust the body's `secret` field alone without also checking the `x-api-key` header matches).

A sandbox account (`latchel-demo.com`) exists if Q wants to prove out the actual dashboard registration flow before touching Rincon's live webhook settings.

### 3.4 Idempotency

A single real approval event can plausibly generate more than one webhook delivery (a `created` event immediately followed by an `updated` event as Latchel finishes writing the record, or Latchel's own undocumented retry behavior — see 3.5). The receiver must be idempotent on `(latchel_job_id, entered_needs_approval_at)` — an already-existing `approval_briefings` row for the same job that hasn't since resolved (per `resolved_at IS NULL`) means "already gathering or already sent," and the delivery is acknowledged and discarded, not double-processed.

### 3.5 The backstop: nothing here is delivery-guaranteed

The webhook research is explicit and unusual in how it frames this: not "couldn't find documentation," but **an actual, confirmed absence** — three separate official Latchel doc sources (the payload-format reference, the dedicated webhooks OpenAPI spec, the dashboard setup walkthrough) were checked and none of them state a retry policy, a backoff schedule, a delivery guarantee, or what happens if this receiver 4xx/5xxs or is simply down for a minute. This directly corroborates the reasoning the existing `maintenance-history` build already used to choose nightly polling over webhooks entirely.

The design doc's own idea #5 ("speed should scale with urgency") is the reason this domain doesn't make the same all-polling choice maintenance-history did — a webhook genuinely matters here, specifically for the emergency-tagged cases idea #5 calls out. So: **webhook is the fast path, a periodic reconciliation poll is the backstop, not a fallback that only matters if the webhook is never set up.** The poll — an hourly `GET /jobs?in_states=27`, following the same `getAllPages()` fix `latchel-connector.js` already has for the confirmed pagination-drops-the-date-filter bug — catches anything a silently dropped delivery missed, on the same idempotency key as 3.4, and also does double duty as the "did anyone act on this" check for Section 9's reminder logic.

### 3.6 What happens on receipt — the pipeline, end to end

1. Verify `x-api-key` + body `secret` against `LATCHEL_WEBHOOK_SECRET`. Reject and log (not to `audit_log` — no real event has happened yet — a plain application log) anything that fails.
2. Discard anything where `object_type !== "Job"` or `object.state_id !== 27`.
3. Idempotency check (3.4). Discard if already tracked and unresolved.
4. Insert the new `approval_briefings` row with what the payload already gave us (job id, trigger_reason, entered_needs_approval_at if present).
5. Kick off the gather step (Section 4) — synchronously if fast enough, otherwise queued; this spec doesn't prescribe which, that's Q's call once real latency is measured.
6. Risk assessment (Section 5) — generated, then content-checked once, unconditionally, before the result is stored anywhere; a flagged result is held on the row, never written to `risk_assessment_text` and never passed downstream. Emergency match (Section 6), cost benchmark (Section 7) — all read-only against Latchel/AppFolio/Supabase, nothing written to either external system.
7. Generate and send the PM email — reading the risk assessment only from `risk_assessment_text`, rendering "Risk assessment pending review" if Section 5 held it (Section 8); generate (never send) the owner draft, same rule (Section 8). This step never runs ahead of step 6's content check — a flagged result cannot reach either email, by construction, because the field it would read from isn't populated until the check passes.
8. Write the `audit_log` entries (Section 10).

## 5. Risk Assessment

The one component of this feature that becomes a `claims` row (Section 2.1). The design doc's requirement is exact: *"cited and explained, not a silent yes/no."*

**Design, reusing `extract-claims.js`'s proven discipline:**
- Input: the job's free-text fields only (`description`, `vendor_description`, `estimate_note`) plus the structured context already gathered (Section 4) — never a raw dump of everything, the same bounded-input discipline `extractAIClaims()` already uses.
- The prompt asks for a **qualitative risk level** (e.g., low / moderate / elevated — exact labels are a build-time decision, not specified here) plus a plain-English, cited explanation — never a bare numeric score standing alone, matching idea #3's requirement that a judgment call must visually and structurally read differently from a fact.
- The same self-check discipline `extract-claims.js` already asks of the maintenance extractor: `protected_class_flag`/`protected_class_category` (Layer 2), generated alongside the risk-assessment text itself.
- `source_reference`: structural only ("Latchel job 716584, description field + estimate_note field") — never the ticket's own wording.
- `claim_text`: the model's own cited reasoning in plain English — a distilled statement, not a quote of the tenant's or vendor's words.
- **Property/situation framing, not tenant framing — an explicit prompt instruction, per Mason's Fair Housing review (`compliance/approval-briefing-fair-housing-review.md`, finding 2).** The protected-class self-check above catches protected-class-coded language, but not general tenant-characterization drift that can get carried over from a vendor's or PM's own free-text ticket notes — "tenant wouldn't let vendor in," "tenant is difficult to schedule with," or similar routinely appear in `description`/`vendor_description`/`estimate_note` and trip no protected-class flag, because they aren't protected-class language. The prompt must explicitly instruct the model to frame its assessment in terms of the property or situation, never the tenant. Acceptable: *"risk the property incurs further water damage if not addressed within [timeframe]."* Not acceptable, even if the source ticket text uses this framing: *"tenant is negligent," "tenant failed to report promptly," "tenant caused the damage," "tenant has been uncooperative."* If a vendor's or PM's free text itself characterizes the tenant, the model should extract the underlying property-risk fact it supports, if any, and leave the characterization out — the same discipline `extract-claims.js` already applies to Latchel's `max_cost` field (report the number, strip the source's own framing around it).

**The content-check gate runs once, unconditionally, immediately after generation — and it gates everything downstream, not just the `claims` insert.** The two-layer check (`content-check.js`: Layer 1 keyword scan + Layer 2 AI self-check via `protected_class_flag`/`protected_class_category` above) runs on the freshly-generated risk-assessment text every time an instance is gathered — regardless of whether `property_id` has resolved (Section 2.4), and regardless of whether a `claims` row will ever be written for this instance. This is a deliberate correction to an earlier version of this design, which described the check only as running "before insert" into `claims`. Because that insert is itself conditional on `property_id` resolving — and `property_id` is confirmed at 0% resolved today (Section 2.4) — describing the check that way left it reading as optional for exactly the cases this pipeline exists to still handle: `risk_assessment_text` lives directly on `approval_briefings` regardless of the `claims` copy (Section 2.4), so the emails go out either way, which means the filter has to run either way too. It is not optional, and it runs first, before the text is used for anything else:
- **If both layers pass:** the text is stored in `risk_assessment_text`/`risk_assessment_confidence` directly on `approval_briefings` (always — this is the self-contained copy Section 2.3 requires to exist independent of the `claims` mirror), and mirrored into `claims` (`domain='approval_briefing', claim_type='risk_assessment'`) whenever `property_id` has resolved — `review_status` defaults to `unreviewed`, same as every other claim in this system; nothing here auto-promotes past a human.
- **If either layer flags the content:** `risk_assessment_text` is **not** populated with the flagged text, and no `claims` row is written for it. The row instead records that a risk assessment was attempted and is held (a flag/hold status — Neo's exact column, Phase 1), the same way a flagged claim is never silently included anywhere else in this project. This hold is what Section 8's email generation step must check for before building the PM briefing or the owner draft — see Section 8.

**What this is not:** a decision. The PM briefing presents the risk read as a labeled, cited inference, visually distinct from the deterministic facts around it — never as a recommendation to approve or deny.

## 6. Emergency Matching

### 6.1 Design

Per the design doc's ground rule: *"matched against a fixed, human-maintained list, not an open AI judgment call."* Two signals, kept structurally separate and never conflated (idea #3, again):

1. **The maintained list itself** — a config asset (a code file, mirroring `protected-class-terms.js`'s own "a maintained, reviewable code asset, not a database table" pattern, versioned the same way), matched against Latchel's own `issue_id`/category taxonomy (282 issues across 31 trade categories, confirmed live per the benchmark research — `GET /issues`/`GET /categories`, changes rarely, worth caching the same way the benchmark work already needs to).

Per the design doc's own resolved finding on the maintenance-limit mismatch, Latchel's internally-set values have already been shown to drift from what's actually configured correctly on a given property — so this system treats Latchel's own emergency flag as *a fact about what Latchel says*, not as ground truth this pipeline adopts silently.

## 7. Cost Benchmark

**Scoped to exactly what the benchmark research proved achievable — an assembly job on data that already exists, not a new categorization project.**

Confirmed live: Latchel's `issue_id` field (populated on 70.0% of 5,200 real jobs pulled — 3,639 tickets) is a real, structured, already-used-internally taxonomy, not something this feature has to invent. A job's own `estimate` field is **not reliable for a historical benchmark** — it reverts to `null` on all but 2 of 85 real completed water-heater jobs checked; the real final cost lives on the separate `GET /invoices` object (`total` field), joined back to jobs via `relation_id` + `relation_type = "Latchel\Job"`.

**Real numbers proven against Rincon's own history** (not estimates): garbage disposal repair/replace, n=8, $250–$580 (median $298); clear drain, n=23, $110–$2,320 (median $290); repair toilet, n=20, $80–$1,622 (median $240); water heater repair, n=20, $125–$3,750 (median $825).

**The honest limitation, carried into the design:** only 18–26% of jobs in a given category have a matched invoice (40% of the account's full history is `Cancelled`, and some completed jobs were paid outside Latchel's invoice object entirely) — real sample sizes run single-to-low-double-digits, not hundreds. **Every benchmark shown must display its sample size next to the range** ("based on 8 past jobs") — never a bare number implying a large-market survey, per the design doc's own idea #4 and idea #3.

**Build requirements:**
1. Pull and cache `GET /issues`/`GET /categories` (282/31 rows, changes rarely) — a small reference table, one-time-ish refresh.
2. Capture `issue_id` on the job at gather time — not stored anywhere in Supabase today; one additive field on `approval_briefings` (Section 2.3), not a schema change to `maintenance_requests`.
3. Add a `listInvoices()`-style function to `latchel-connector.js` — new, GET-only, following the file's own hard rule (no generic request helper; a narrowly-named function calling `latchelGet()`, matched to jobs via `relation_id`/`relation_type`).
4. Compute the benchmark at gather time (or a periodic rollup, Q's call): group past invoiced totals by `issue_id`, trim extreme outliers, show median + range + sample size.
5. Where `issue_id` is missing (30% of jobs) or the sample is too thin, the briefing says "not enough history for a benchmark yet" — never forces a comparison, matching the standard the rest of this feature already holds itself to.

## 8. Email Generation

**A hard prerequisite for both 8.1 and 8.2 below, not a separate check to remember to run at send time: the content-check gate (Section 5), which now covers two fields, not one.** Section 5's design means `approval_briefings.risk_assessment_text` is only ever populated once the two-layer content check (`content-check.js`: Layer 1 keyword scan + Layer 2 AI self-check) has cleared it — flagged text is held on the row instead, never written to that field. Section 4.4's access-instructions gate applies the identical discipline to `access_instructions` before it's rendered into either template. Both templates below must read the risk assessment **only** from `risk_assessment_text` and the entry instructions **only** from the checked copy of `access_instructions`; neither may re-derive a risk read, or an access instruction, from the raw Latchel ticket fields (`description`, `vendor_description`, `estimate_note`, `access_instructions`) directly as a shortcut or fallback, which would recreate exactly the unfiltered-second-copy risk `PROPERTY-BRAIN-ARCHITECTURE.md` §1.2.1 already named for email citations elsewhere on this platform (Section 2.3 makes the identical point about the structured-fields snapshot). Read this way, email generation cannot put flagged AI or tenant/vendor free text in front of a PM or owner — there's nothing to read yet if the check hasn't passed.

**What email generation must still do explicitly: check for and render the held state, not skip past it — for either gated field.** If a given instance's risk assessment is on hold (Section 5), the PM briefing generates with the risk-assessment block rendered as **"Risk assessment pending review"** instead of silently omitting that section — per idea #4 below, missing or held content says so, loudly, the same standard every other confirmed-gap field in this email already has to meet. If `access_instructions` is on hold (Section 4.4), both templates render **"Access instructions not available for this ticket"** in its place, the identical pattern. A hold on either field blocks only that field's content; it does not delay or block the rest of the briefing (Section 4's deterministic facts, the emergency match, the cost benchmark) and does not block the reminder/escalation timer in Section 9 — an urgent case (idea #5, Section 3.5) still needs the facts it has, fast, even while one AI-generated or tenant-authored component is held for review. The owner draft (8.2) follows the same rule for both fields: if the risk assessment or the access instructions are held, the draft either omits that content entirely or notes it's pending — never built from an unchecked fallback source.

### 8.1 The PM briefing

Structured around Section 4's five categories, with three of the design doc's raising-the-bar ideas built in as requirements, not nice-to-haves:

- **Idea #1 — lead with what matters.** One line at the top, before the full detail: the two or three facts that actually drive the read (e.g. "$340 repair, $90 over this property's limit, first time this issue's come up here"). Built from whatever of Section 4's fields actually resolved for this instance — if the cost benchmark or maintenance-limit fields are unavailable (Section 4.2's confirmed gaps), the lead line is built from what's real, never padded with a placeholder.
- **Idea #3 — fact vs. judgment must look different.** The risk assessment (Section 5) and the emergency match (Section 6) are visually distinguished — a labeled, bordered, or otherwise structurally separate block — from the deterministic facts around them (dates, dollar amounts, ticket history). This is a rendering requirement for whoever builds the email template (Q or Tron, per how this Hub's other tools split that work), not just a data-shape suggestion.
- **Idea #4 — missing data says so, loudly.** Every field from Section 4 marked as a confirmed gap in this spec (maintenance limit, owner approval history, vendor track record) renders as an explicit "Not available" in the email, never a quiet blank. This is directly testable against Section 4's own tables — nothing there should silently disappear from the rendered email just because the underlying data doesn't exist yet. The same standard applies to a held risk assessment (Section 5, and the content-check gate above) even though it isn't a Section 4 field: it renders as "Risk assessment pending review," never a silent drop. A held `access_instructions` field (Section 4.4) renders as "Access instructions not available for this ticket," the same pattern.
- **Fourth hard requirement — tenant-context fields render as bare facts, per Mason's Fair Housing review (`compliance/approval-briefing-fair-housing-review.md`, finding 3), restating Section 4.4's own rule as a template-rendering requirement, not left to the template author's discretion.** Tenant-context fields (maintenance-request count, tenure, access notes) render as bare facts in both templates — a number, a date, or a literal instruction string, never an adjective or a framing that implies a pattern of behavior ("frequent," "demanding," "high-maintenance," "difficult"). Section 4.4 already states this as a hard rule for the *data*; a careful data design can still get eroded by ordinary copywriting once someone is actually drafting sentences for a PM to read quickly — "3 requests in the last 6 months" is one stylistic choice away from "this tenant submits maintenance requests frequently." This requirement exists so Q or Tron doesn't make that choice.

### 8.2 The owner draft

**V1 = the PM copies and pastes it themselves**, per the design doc's explicit resolution — no send path to the owner exists in this system. The draft is generated from the same gathered data, in owner-appropriate language (no internal jargon, no raw Latchel field names), and is never auto-sent under any configuration this spec proposes. A fully auto-drafted, ready-to-send flow is named in the design doc as a possible future upgrade, explicitly not part of this build.

**Mechanism, clarified per Mason's Fair Housing review (`compliance/approval-briefing-fair-housing-review.md`, finding 4):** "owner-appropriate language" here means **AI-authored rephrasing**, not a fixed template filling in pre-vetted strings — the model takes the same gathered facts (Section 4), `risk_assessment_text`, and the checked `access_instructions` copy, and writes owner-facing prose that strips internal jargon and raw Latchel field names. This is the more conservative reading of the two, and the one this spec commits to, precisely because the owner draft is the one output in this entire feature that's designed to leave the building — the PM copies it into an email to a third party, so any characterizing language that slipped through wouldn't just sit in an internal Hub record, it would reach an owner who might act on it. Because it's a genuine generation step and not a fill-in, it carries the same obligations as Section 5's risk-assessment generation, not a lighter version of them:
- The prompt is subject to the same property/situation framing instruction added to Section 5 above — never characterizing the tenant, only the property or situation, with the same acceptable/not-acceptable examples.
- Its output is content-checked (`content-check.js`, both layers) before being written to `owner_draft_text` — the same gate `risk_assessment_text` passes through before either template can read it (Section 5). A flagged draft is held, not written; the owner-draft view renders "Owner draft pending review" instead, matching the missing-data pattern used everywhere else in this section.
- It reads `risk_assessment_text` and the checked `access_instructions` only in their already-checked form (Section 8's opening paragraph, above) — it never re-derives either from raw Latchel fields as a shortcut.

### 8.3 Delivery mechanism — reuse, don't reinvent

`projects/hub/insurance/router.js` already has a working, in-production nodemailer pattern (`createMailer()`, gated on `GMAIL_USER`/`GMAIL_APP_PASSWORD` both being set, degrading to a no-op with a warning log if either is missing — exactly the pattern `server.js`'s own help text documents as "degrades gracefully if unset"). Approval Briefing's PM-email send reuses this pattern directly, not the separate OAuth2/`googleapis` Gmail pattern `appfolio-sync/sync.js` uses for its own alert emails — the nodemailer pattern is the one already proven for a Hub-tool-to-human notification, which is exactly this use case.

## 9. No-Response: Reminder, Escalation, and "Who Is the Backup"

### 9.1 Timer design

The design doc resolves the shape ("a reminder goes out after a set time, then it escalates to a backup if it's still untouched") but not the exact durations — **left as an Open Item for Peter**, not guessed at here. The reconciliation poll (Section 3.5) is the natural place this logic runs: on each hourly pass, for every `approval_briefings` row with `resolved_at IS NULL`, check elapsed time since `pm_briefing_sent_at` against the (Peter-confirmed) reminder and escalation thresholds.

### 9.2 Detecting "was it acted on" — a real, grounded signal, not a guess

There is no clean in-Hub signal that a PM has "handled" a briefing — the actual approval/decision happens inside Latchel or in a conversation with the owner, outside this tool. The reconciliation poll already has to re-check `GET /jobs/{id}` for the reminder logic above; the same call answers this question directly: **if `state_id` has moved off 27, the job has left "Needs Approval" by some path, and this instance is resolved** — no reminder or escalation fires, `resolved_state_name`/`resolved_at` get set (Section 2.3, and Section 4.2's forward-looking owner-history note). This is a real, low-cost, already-necessary check, not new machinery invented just for this purpose.

### 9.3 Who is the backup — reusing an established, Peter-already-accepted pattern

**There is no existing per-property PM assignment anywhere in this schema** — checked directly: `team_members` carries no `pod` column at all (only the older, likely-legacy standalone `users` table does), and `properties.pod` only distinguishes two broad groupings (`Solimar`/`Faria`), with no table anywhere mapping a specific property to a specific responsible PM. This is a real, confirmed gap, not an oversight in this research.

**The exact same gap already existed for Security Deposit's reminder system, and Peter already accepted the same answer there** — `security-deposit/router.js`, verbatim: *"Every active pod_lead role holder gets every reminder in v1 — no per-property pod routing yet (SPEC.md Deferred list / Open Item #2, Peter confirmed 'fine' as the v1 starting point)."* This spec proposes the identical v1 answer for both halves of Approval Briefing's own recipient logic, rather than inventing a new pattern for a problem this codebase has already solved once and had explicitly accepted:
- **PM briefing recipients:** every active team member holding role `property_manager` for a new `approval_briefing` tool value in `team_member_tool_roles` — broadcast, no per-property routing, v1.
- **Escalation backup:** every active team member holding role `pod_lead` (or `admin`) for the same tool value — same broadcast pattern, same precedent.

If per-property PM routing is wanted later, it needs a genuinely new piece of infrastructure this schema doesn't have today (a property→PM assignment table) — flagged here as a real future need, not proposed as part of this build.

## 10. Audit Logging and the Feedback Loop

### 10.1 Audit log entries (GOVERNANCE.md Rule 1)

Following `PROPERTY-BRAIN-ARCHITECTURE.md` §2.6's own established per-event-type guidance format, generalized to this domain. Every entry sets `privacy_category`, `actor_type`/`actor_id`/`actor_version`, `risk_level`, and a content-free `event_data`, per the same discipline already proven for `claims.extraction_run`/`claims.reviewed`/etc.:

1. **`approval_briefing.triggered`** — one per new `approval_briefings` row. `actor_type = 'system'` (webhook) or `'system'` (poll) — never `'ai_agent'`, since nothing has read or interpreted content yet at this point. `event_data = { latchel_job_id, trigger_reason, trigger_source }`.
2. **`approval_briefing.risk_assessed`** — `actor_type = 'ai_agent'`, mirrors `claims.extraction_run`'s shape exactly when a claim was written; `risk_level = 'medium'` by default (an AI read ticket free text to produce a judgment a PM will act on), matching the same reasoning `PROPERTY-BRAIN-ARCHITECTURE.md` §2.6 #4 already applied to its own AI-reads-content entry.
3. **`approval_briefing.pm_email_sent`** — `actor_type = 'system'`. `event_data = { recipients, briefing_id }` — never the email body itself (that's already durable on `approval_briefings.pm_briefing_body`, no need to duplicate content into `audit_log`'s `event_data`, which this schema's own convention keeps content-free).
4. **`approval_briefing.owner_draft_generated`** — `actor_type = 'ai_agent'`. Logged the moment the owner-facing draft (Section 8.2) is generated, not deferred until any later action. This is the first Property Brain output whose eventual destination is outside the building — an owner, once the PM copies, edits, and sends it themselves — even though this system itself never sends it, so the moment it's drafted gets its own audit record rather than being folded silently into #3 above. `event_data = { briefing_id }` — same content-free discipline as every other entry here; "capturing what it said" means what it already means everywhere else in this schema: the generated text itself is durable and queryable on `approval_briefings.owner_draft_text` (Section 2.3) from the moment this event fires, not that the draft gets duplicated into `event_data`.
5. **`approval_briefing.reminder_sent`** / **`approval_briefing.escalated`** — same shape as #3.
6. **`approval_briefing.pm_feedback_recorded`** — `actor_type = 'human'`, `actor_id` = the PM's email. `event_data = { pm_risk_feedback, briefing_id }` — never the free-text notes verbatim, same discipline as every other `reviewer_notes`-adjacent field in this schema.

### 10.2 The feedback loop — and a real gap in the existing vocabulary

Idea #6 asks for two things: a record of what a briefing said (Section 2.3 already covers this — `approval_briefings` is self-contained), and whether the PM agreed with the risk call.

**This second half is genuinely not the same question `claims.correction_reason_code` already answers, and conflating them would be a mistake worth avoiding explicitly.** `correction_reason_code`'s existing controlled vocabulary (`WRONG_SOURCE`, `HALLUCINATED_DETAIL`, `WRONG_SUBJECT`, `WRONG_CLAIM_TYPE`, `MISSED_NUANCE`, `STALE_ON_ARRIVAL`, `PROTECTED_CLASS_MISS`, `OTHER`) is aimed at **extraction accuracy** — was the claim's *content* right. A PM disagreeing with a risk call is a different kind of signal: they can agree the claim accurately reflects what the ticket said, and still disagree that it amounts to real damage risk — a professional-judgment question, not a factual-accuracy one. Two options were considered:

- **(a)** Widen `correction_reason_code`'s vocabulary with a new value (e.g. `PROFESSIONAL_JUDGMENT_DIFFERS`), using the schema's existing DROP-then-ADD CHECK-widening convention.
- **(b)** Keep the two questions structurally separate: `claims.review_status`/`correction_reason_code` continues to answer "was this claim accurate" for the `risk_assessment` claim type same as any other; `approval_briefings.pm_risk_feedback`/`pm_risk_feedback_notes` (Section 2.3) answers "did you agree with the call" as its own, purpose-built field.

**This spec recommends (b).** Reusing `correction_reason_code` for a question it wasn't built to answer would blur the monthly quality-drift query `PROPERTY-BRAIN-ARCHITECTURE.md` §6 already runs across every domain (grouping corrections by `domain + claim_type + source_type + correction_reason_code + extracted_by` to spot accuracy problems) — mixing "the AI got a fact wrong" and "the AI's judgment call didn't match a PM's" into one bucket would make that query's output harder to read for every domain, not just this one. Keeping them separate costs one small field, already planned into Section 2.3's table, and keeps both signals individually meaningful.

**The loop, concretely:** a monthly query (same cadence as §6's existing feedback loop) aggregates `pm_risk_feedback = 'disagreed'` rates by property, by risk-assessment prompt version, and cross-references against `resolved_state_name` where available (Section 4.2) as a rough later-outcome check. Owned by whoever ends up reviewing this domain's claims queue, escalated the same way §6 already escalates a `PROTECTED_CLASS_MISS` — immediately, not held for the monthly rollup, if a disagreement pattern looks systematic rather than case-by-case.
