On every run: read the actual complaints created, and check specifically for (1) the one non-negotiable — did anything that's actually a big deal get filed as routine and buried; (2) tone-signal false positives; (3) whether "needs a human call" is being used sensibly; (4) any duplicate-merge suggestion is a real duplicate; (5) any owner-instruction draft note goes through the existing Operational Notes approval, never auto-posted. Cost is cents-to-low-dollars per run (order of magnitude smaller than the separate 254,000-conversation historical scan) — not a budget concern at this volume.

- [x] **13. Severity scoring — the fix for "2,733 complaints is not possible."** Done 2026-10-02/03. The count was inflated because `shouldCreateComplaint()` made a complaint out of every `owner_instruction` and `legal_exposure` conversation with no severity check, and `is_big_deal` was true on 2,732 of 2,733 rows. Replaced with a four-tier AI severity score (`urgent` / `worth_a_look` / `just_a_record` / `no_issue`) whose only test is *is there an active dispute* (obstruction, refusal, explicit legal/leave/agency threat) — not how bad the underlying problem sounds, since maintenance severity is already owned by the Maintenance Department. The rubric was calibrated in three rounds against Peter's own calls on 46 real complaints (39% → 57% → 70% exact agreement; none of Peter's "urgent" calls was ever buried). Ran for real against the whole backlog (Message Batches API, run on Sally) and is now on for every new complaint (`SEVERITY_LIVE_PIPELINE_ENABLED=true`). `no_issue` rows are kept, never deleted — just excluded from every default view, count, and tile. Result as of 2026-10-03: 1,024 unresolved items need attention (urgent + worth_a_look), down from 2,733; 932 of those show in Property 360 and the home tile (that view also drops complaints whose tenant's lease has ended). Dashboard stat tiles and lanes now use severity, not `is_big_deal`. Code: `archive-search/lib/severity-rubric.js`, `severity-batch.js`, `run-severity-batch.js`, `significance-pass.js`; schema: migrations `20261002010000`, `…020000`, `…030000`, `…040000`, `…050000`.
- [x] **14. Fair Housing safety floor — the thing severity is never allowed to hide.** Done 2026-10-02/03. Asimov and Mason's reviews found the dispute-only test could bury a quiet, unresolved disability-accommodation request (an unreasonably delayed accommodation can itself be the violation, and it never reads as a "dispute"). A database rule (`complaints_no_issue_excludes_protected_signals`) now makes it impossible for any code to mark a complaint `no_issue` if it is `accommodation_related`, `legal_exposure`, protected-class-flagged, flagged `needs_human_call`, or has an owner-instruction rejected/uncertain finding; the application applies the same floor first so the database never has to reject a write. Mason's three conditions were built: (1) `accommodation_related` now always creates a complaint (it previously didn't unless something else also tripped — a pre-existing gap Mason found, not one this work created); (2) the floor was widened to `legal_exposure` and rejected/uncertain owner instructions, and 306 existing rows that violated it were re-scored; (3) the 663 historical urgent/worth_a_look complaints that had no human owner were assigned the Director of Operations, matching what live mail already got. The constraint was validated against all existing rows on 2026-10-03. **Governance record:** Asimov approved building but not activating until Mason's scoped review; Mason cleared with those three conditions; Peter explicitly overrode the hold on running the batch before the conditions were built (2026-10-02, after being told what was at stake), and they were built and deployed the same day. Peter also changed CLAUDE.md rule 3 that day so Asimov/Mason review can be overridden only by his explicit say-so.
- [x] **15. The email-matching fix (AppFolio).** Done 2026-10-02. ~70% of complaints could not be matched to a tenant/owner. Part of the cause was data loss, not AI: the AppFolio sync kept only the first of a tenant's email addresses and stored an owner's several addresses as one unusable comma-joined string (132 of 394 owners). Now every address is stored (`tenant_emails`, `owner_emails`; 867 tenant addresses recovered, 132 owner records fixed) and the matcher checks all of them. No AI involved and no change to what the matcher is allowed to do. Code: `appfolio-sync/sync.js`, `complaint-tracking/lib/subject-match.js`; schema: migration `20261002000000`.
- [x] **16. Name-based matching, human-confirmed only.** Live 2026-10-02; retroactive run 2026-10-03. For complaints email can't match, the AI may suggest a tenant/owner from a name in the thread — **only** when the name also agrees with a property the system can already verify, and **never** writes the match itself: staff see every real candidate with its property and must confirm or reject (`match_method = content_extracted_human_confirmed`, with who/when recorded). **Governance record:** Asimov did NOT approve the originally proposed fully-automatic version (it reverses a four-times-documented Fair Housing firewall: identity only ever from a verified address); Mason independently recommended dropping automatic resolution outright and found the narrower human-confirmed, property-corroborated version viable (on current data none of the 13 tenant name-collision groups share a property). Peter chose the narrower version, declined outside-attorney review and the 7-day shadow period, and accepted the residual risk in writing — see `compliance/complaint-tracking-name-match-owner-risk-acceptance.md` (the unanswered attorney question is saved beside it). The retroactive tool (`archive-search/run-name-match-backfill.js`, gated by `NAME_MATCH_BACKFILL_GOVERNANCE_CLEARED`) checked all 1,922 unmatched complaints: 92 suggestions (90 tenant, 2 owner, none with competing candidates), 0 errors, nothing written as a real match. About 95% of the old unmatched backlog stays unmatched by design — no property to corroborate against, no guess.
