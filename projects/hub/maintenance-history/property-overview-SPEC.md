## What This Does

Today, Maintenance History (the tool just built from Latchel) shows one ticket at a time — good for "what happened on this specific work order," useless for "what's this property's whole deal." If a new team member picks up 751 Warwick Ave on their first day, they have no fast way to learn: this property has a known fire-hazard electrical panel still pending an owner decision, three separate mold/moisture visits in the same unit that never fully resolved, and a garbage disposal nobody ever sent a plumber for. Right now, learning that means opening every ticket for that address one at a time and reading all of them.

This feature adds a second way into the same data: **type an address, get a one-screen brief.** It pulls together every maintenance ticket ever logged for that property, groups them by what part of the property they're about (electrical, plumbing, etc.), calls out anything still open or unresolved first, and summarizes older closed-out history briefly instead of listing it all. It's a reading layer on top of data that already exists — it doesn't pull any new information from Latchel or AppFolio, and it doesn't hide anything the per-ticket view already shows. It's a faster way in, not a different set of facts.

## The Synthesis Design — How Years of Tickets Become a One-Minute Brief

This is the real design problem, so it gets worked through in full rather than asserted.

**The raw material.** A property can have dozens of `maintenance_requests` rows going back years, and each Latchel-matched one can have a dozen or more `maintenance_claims` rows (event/decision/outcome/recurrence, per SPEC.md's existing model). Reading that flat, in ticket order, is exactly what the existing per-ticket dashboard already does well — and exactly what Peter said this new view should *not* be ("we don't need every little detail about all the steps"). Dumping 200 claims onto one page in date order is not a brief; it's the same problem in a longer scroll.

**Step 1 — Group by system, not by ticket.** The two extractions read for this spec make the case concretely: ticket 17432-1 (566 N Ventura) touches the kitchen cabinets/moisture, the clothes dryer and its venting, the crawl space, and the A/C unit — all one ticket, four different systems. Ticket 17445-1 (751 Warwick) touches the oven receptacle, the main electrical panel, bedroom outlets, a garage photocell, and a garbage disposal — one ticket, five different systems, only some of them actually electrical. A property-level brief organized by *ticket* would repeat "751 Warwick, 17445-1" five times with no throughline; organized by *system*, it reads as "Electrical: 3 issues, including a known fire-hazard panel still pending replacement" and "Plumbing: 1 unresolved item (garbage disposal, referred to a plumber, no follow-up ticket found)" — which is what actually orients someone in a minute.

This requires a new, small classification step that doesn't exist yet: a **component categorizer** — a maintained code asset (same pattern as `protected-class-terms.js`: reviewable, editable, not a database config table because it's a taxonomy, not a numeric threshold) that keyword-matches each `maintenance_requests.title`/`description` into one of a small fixed set of buckets: **Electrical, Plumbing, HVAC & Moisture/Mold, Appliances, Structural & Exterior, Pest Control, Locks & Security, Other**. Deterministic, cheap, auditable — not a per-claim AI classification pass, which would be a second AI judgment call layered on top of the extraction's own judgment calls for no real gain here (a ticket titled "(URGENT) Oven plug and outlet mismatch" doesn't need an AI to know it's electrical). A ticket can land in more than one bucket if its claims clearly span systems (17432-1 would show under both HVAC & Moisture and, more lightly, Appliances for the dryer) — better to show a real cross-reference than force a single wrong bucket.

**Step 2 — Split each bucket into "still open" vs. "resolved," and lead with open.** Peter's brief calls this out specifically: surface anything currently open/unresolved. This is not a new judgment — it's already sitting in data this tool built: `maintenance_requests.status` (open/assigned/in_progress vs. completed/closed, synced nightly from AppFolio) plus the existing outcome-ladder claims (`claim_type = 'outcome'`, level 1-5). A ticket with no outcome claim at level 3+ and a non-closed status reads as unresolved. Ticket 17445-1 is the exact case this needs to handle well: Latchel and AppFolio both show it "Completed," but the claims say the originating item (the oven outlet) was explicitly *not* done, and a $4,500 panel replacement was still awaiting the owner's final go-ahead as of the last claim. The synthesis has to be able to say "marked complete, but the actual problem wasn't fixed and there's a bigger unresolved item behind it" — which means the open/resolved call is made from the claims' own outcome evidence, not just the AppFolio status field, exactly the discipline the per-ticket view already applies.

**Step 3 — Surface recurrence prominently.** Any `claim_type = 'recurrence'` row, or any component bucket with two or more tickets, gets a visible "recurring" marker on that component card. This is free — the data already exists (SPEC.md's recurrence claim type) or is a trivial count; nothing new to compute beyond what's already there.

**Step 4 — Recent gets detail, old gets compressed.** Within a component bucket, order tickets by recency. Anything still open, or resolved within roughly the last 12 months, gets a real sentence or two. Anything older and resolved with no recurrence gets folded into a single line — "Also resolved, no recurrence since: kitchen faucet leak (Mar 2024), garbage disposal jam (Jan 2023)." This is the mechanism that keeps a property with eight years of history to a one-minute read without deciding any of that history doesn't matter — it's still there, just compressed, and every compressed item still links through to its ticket.

**Step 5 — One short AI-written paragraph per component, built only from claims that already exist, with citations preserved.** This is the one genuinely new AI step in this feature, and it's worth being precise about what it does and doesn't do. It does **not** re-read raw tickets, invoices, or PDFs — that already happened once, correctly, in the existing extraction pipeline, with its own "cite a source, say unknown rather than guess" discipline. This step's only job is to take the already-extracted, already-sourced claim sentences for one component bucket and compose them into a short flowing paragraph instead of a bullet list — compression and ordering, not new fact-finding. The prompt requires structured output: each sentence (or clause) in the paragraph must carry the `claim_id`(s) it's built from. Before anything is shown, Q's code checks that every cited `claim_id` in the model's output actually exists and actually belongs to that property's claim set — if it doesn't, that sentence is dropped rather than shown, the same "don't show what you can't back up" rule the original extraction used. This keeps the same citation discipline the 10-ticket experiment was graded on (0% wrong-source), just applied one layer up.

**Nothing here is new database schema by default.** All of steps 1-4 are computed at request time from tables and views that already exist (`maintenance_requests`, `maintenance_claims_decision_safe`). Step 5 is the one new moving part, and even it doesn't require a new table for v1 — see "What's Genuinely New to Build" below for why request-time generation (no caching table) is the right size for how this tool will actually get used.

**A completeness point worth being explicit about, because gliding past it would repeat exactly the "gloss over relevant facts" mistake this whole feature exists to avoid:** not every ticket on a property has been matched to a Latchel job, and Latchel-matched claims only go back as far as Latchel's own history. Older tickets, or ones the nightly matcher hasn't linked yet, still exist in `maintenance_requests` with real AppFolio fields (title, status, vendor, cost, completed date) even with zero `maintenance_claims` rows. The categorizer runs against *every* `maintenance_requests` row for the property, Latchel-matched or not — a matched ticket gets the full synthesized treatment; an unmatched one still gets a minimal one-line entry sourced straight from AppFolio's own fields ("Kitchen faucet repair — completed 2019-03-14, $180, vendor: ABC Plumbing — no detailed Latchel history available"). Silently dropping pre-Latchel or unmatched history from "everything that's going on" would be exactly the failure mode Peter flagged when he said unreviewed facts should never be glossed over — the same principle applies to facts that simply haven't been enriched yet.

## Page Layout and Data Flow

**Entry points — plugging into what already exists, not duplicating it:**
1. **Hub-wide search** (`GET /api/hub/search-properties?q=`, `projects/hub/lib/property-search.js`) is already live and already returns, per matching property, whether that property has `maintenance_history` data. Its own UI widget isn't built yet (that's the separate parallel task Peter mentioned). This spec doesn't touch that endpoint — it just gives it somewhere real to send someone: once the widget exists, a property result with `tools.maintenance_history: true` links to this new page. No new search endpoint is built here.
2. **Inside Maintenance History itself**, a new third tab — "Property Overview," alongside the existing "Tickets" and "Needs privacy review" tabs — with a small search box that calls the same already-built `/api/hub/search-properties` endpoint (not a new one) and lists matches; clicking one opens the overview.
3. Property names in the existing ticket list (`dashboard/index.html`'s ticket table) become clickable through to this same page — the fastest path for someone who's already looking at a ticket and wants the bigger picture.

**The page itself** (`GET /maintenance-history/property/:property_id`, reusing the existing single-page dashboard's tab pattern rather than a separate app):
- **Header** — property name/address/city, unit count, current owner (name/contact), and per-unit tenant/lease status (occupied + lease end date, or vacant) — all read directly from `properties`, `units`, `leases`, `owners`, and `property_owners`, already populated nightly by `appfolio-sync/sync.js`. No new AppFolio connection. One honest limitation to show alongside it: `property_owners` only ever holds the *current* owner-property link (no start/end date in that table today), so this shows current ownership, not ownership history.
- **Spend rollup** — total `maintenance_requests.cost` for this property, trailing 12 months and all-time, both shown. Pure SQL sum over already-synced data — not itemized invoice reconciliation, matching Peter's "light context, not full financial reconciliation" instruction. Caveat shown inline: this is only as complete as AppFolio's own `amount` field on each work order, which is not always populated.
- **Currently Open / Unresolved** — pinned at the top, above the component breakdown: every ticket across every component that's still open by the Step 2 test above. This is the single most important section per Peter's brief and it's deliberately not buried inside the per-component cards.
- **By System** — one card per component bucket that actually has data for this property (empty buckets don't show). Each card: system name, ticket count, date range, a "recurring" badge where it applies, the synthesized paragraph (recent items detailed, older resolved items compressed per Step 4), and the AppFolio-only minimal entries for any unmatched tickets in that bucket.
- **Review-status markers, never gating** — exactly Peter's instruction. Every sentence in a synthesized paragraph carries the same lightweight visual marker the per-ticket view already uses for `review_status` (unreviewed / confirmed / corrected / rejected — rejected claims are already excluded upstream by `maintenance_claims_decision_safe`, so they never reach this page at all). Nothing is hidden or gated behind a review state; the marker is informational only, exactly like today's ticket view.
- **Drill-down** — every cited sentence and every component card links to the existing per-ticket detail view (unchanged, already built). This page never tries to be the detailed record; it's the map that tells you which ticket to open.
- **Flagged content** — never enters this page at all, at any stage, because the synthesis reads only from `maintenance_claims_decision_safe`, which already structurally excludes `flagged_protected_class = TRUE` rows before this feature's code ever sees them. This is the same exclusion the base tool already built and already relies on elsewhere — nothing new to implement, and no separate exclusion logic to get right or wrong a second time.
- **No data yet** — a property with no Latchel-linked tickets at all shows the AppFolio header/spend info plus a plain "No maintenance ticket data synced for this property yet" message, mirroring the existing dashboard's empty-state pattern, instead of an error.

## What's Genuinely New to Build vs. Already There

**Already there, reused as-is:**
- `maintenance_claims_decision_safe` (excludes flagged + rejected, keeps unreviewed visible) — exactly the read path this feature needs, no changes.
- The per-ticket detail view/route — the drill-down target, unchanged.
- `GET /api/hub/search-properties` — the search entry point, unchanged.
- `properties`, `units`, `leases`, `owners`, `property_owners`, `maintenance_requests` — all already synced nightly from AppFolio; the header and spend-rollup sections need zero new data connections.
- Hub login + `team_member_tool_roles` (tool = `maintenance_history`) — same access gate as the rest of the tool, no new roles needed.

**New:**
1. **Component categorizer** (`projects/hub/maintenance-history/lib/component-categories.js`) — a maintained keyword-match code asset, same pattern as `protected-class-terms.js`. No migration.
2. **The aggregation/synthesis endpoint** (`GET /api/maintenance-history/property/:property_id/overview`) — the real engineering core: resolve property → units → tickets → claims, categorize, apply the open/resolved and recency rules above, call Claude once per non-empty component bucket (not per ticket, not per claim, to keep cost and latency bounded), validate every returned citation against the real claim set before returning it.
3. **The synthesis prompt** — reuses the existing extraction pipeline's citation discipline, applied to already-extracted claims instead of raw source text.
4. **The property overview page/tab** (Tron) — new HTML/JS added to the existing dashboard, reusing its existing badge/claim visual language rather than inventing a new design system.
5. **Wiring**: the new "Property Overview" tab, the clickable property links from the existing ticket table, the new route mounted on the existing router.

**Deliberately not built for v1:**
- **A caching table for the synthesized paragraphs.** This is a "someone's first day, or someone about to make a decision" lookup tool, not a high-traffic dashboard — request-time generation (a handful of short Claude calls per page view) is cheap and always current, and skips inventing a cache-invalidation policy for no proven need. If usage patterns later show this is slow or expensive at the full 150-500 unit portfolio scale, add a cache keyed on the property's claim set at that point — not before, per the same "don't build ahead of a proven need" approach the rest of this codebase already follows.
- **A new confidence-threshold config table.** Nothing here skips human review based on a score — every underlying claim keeps its own real `review_status`, visible via the per-sentence marker. The synthesis paragraph is presentation, not a gate, so GOVERNANCE.md Rule 5 doesn't apply here any more than it applies to the base tool's ticket view.
- **New audit-log writes for viewing a synthesis.** Precedent: viewing a ticket in the existing dashboard (`GET /api/maintenance-history/tickets/:id`) isn't logged either — only ingestion, protected-class exclusion, and human review actions are. Generating and showing a summary of already-logged, already-reviewed-or-marked data is a read, not a new action, by the same logic already applied elsewhere in this tool.

## Governance

This sits on top of an already-governed table and reuses its exclusion view wholesale, so the lift is much lighter than the base Maintenance History build (no new external credential, no new PII field, no new content-check needed). It is not, on that basis, automatically cleared — per CLAUDE.md's own rule, anything unsure should be treated as a compliance build. Concretely, this should still get a quick pass in front of Asimov before Neo/Q build it, focused on one specific new risk that has no precedent in the base tool: **the synthesis step is a new AI-authored layer sitting on top of already-reviewed-or-not claims.** The citation-validation step described above (reject any sentence whose claim_id doesn't check out) is this spec's answer to that risk, but it's a new mechanism, not a reused one, and deserves a second set of eyes before it ships — a much narrower ask than the base tool's six-condition review, not a repeat of it.

## AppFolio Attachments Research (kept separate, per the parent task's instruction, so this can be relayed on its own)

**The question investigated, as corrected mid-task by Peter:** not a general inbox/communications-log feature (confirmed AppFolio does not have one, and that angle was dropped) — specifically, does AppFolio's real API expose a way to *retrieve files/attachments already linked to a specific record* (a work order, lease, property, owner, or tenant), the same way Latchel's `GET /jobs/{job_id}/files` already does? Some of those attachments could plausibly be saved emails, the same way several of Latchel's own "files" turned out to be PDF-exported email threads in the original 10-ticket test.

**What was checked, directly:** AppFolio's Reports v2 API (the one Rincon's own `appfolio-sync/sync.js` already authenticates against today, confirmed from its real, already-working code) and AppFolio's separate "Stack" partner API (`https://www.appfolio.com/stack/partners/api`, AppFolio's own official page, plus a third-party catalog of the same spec at `jentic.com/apis/appfolio`).

**Finding 1 — the API Rincon already has working credentials for (Reports v2) has no attachments capability at all.** A full pass through the real reports documentation turned up no report or field involving files, documents, or uploads of any kind. The only communications-adjacent report that exists in this API is "Email Delivery Errors" (`/email_delivery_errors.json`) — that's bounce/delivery-failure tracking (did an email fail to send), not the content or attachments of any email. Not useful for this purpose.

**Finding 2 — a separate, newer AppFolio API ("Stack") does document an attachments capability, and it's a real, concrete answer.** AppFolio's own page confirms attachments can be linked to (among other record types) a work order, a property, a unit, an owner, or an occupancy/tenant, with a `File` and a target-object ID (e.g., `WorkOrderId`). AppFolio's own page documents this from the *upload* direction clearly; the *read/list* direction and exact field shape (`GET /v1/attachments?workOrderId=<id>`, returning fields including `file.fileName`, `file.contentType`, `file.signedUrl` — a downloadable link — `userName` who uploaded it, `createdAt`, and `sharedWith`) is corroborated by a third-party integrator (Skywalk) that documents its own product built on top of this same underlying AppFolio API — good supporting evidence a read path exists, but it's one step removed from AppFolio's own primary documentation, worth flagging honestly rather than presenting as a direct AppFolio-published field list. This is a materially better-documented finding than "nothing exists," and if it holds up under a direct account check it's exactly the mechanism Peter described: whatever's already attached to a work order or lease (including a staff member's saved copy of an email, a signed estimate, a photo) becomes readable.

**What's still unconfirmed, and needs a direct answer rather than another web search — same category of open item as the Latchel read-only-key question in the base spec:**
- **This is a different API from the one Rincon already uses.** `sync.js` authenticates to the Reports v2 API with `APPFOLIO_CLIENT_ID`/`APPFOLIO_CLIENT_SECRET` via HTTP Basic Auth. The Stack API's access model isn't stated on AppFolio's own page — whether it's self-serve with the same credentials, a separate credential, or requires applying and being approved as an integration partner (a heavier, possibly-gated process, not confirmed either way) is unknown from what's publicly documented. This needs a direct question to AppFolio (or a check inside Rincon's own AppFolio account settings, the same place the existing Reports API credentials were generated) before any build work assumes access exists.
- **No live test was run.** Rincon's real `APPFOLIO_CLIENT_ID`/`APPFOLIO_CLIENT_SECRET` exist in the project's `.env` (confirmed present, not read), but this was a documentation-research pass only, consistent with the task's explicit "do not connect anything live" instruction — unlike the base Maintenance History spec's Latchel section, which did make real read-only calls. If this feature moves forward, the very first step should be one real, read-only `GET /v1/attachments?workOrderId=` call (or the Reports-API equivalent, if one turns out to exist under a different name than found here) against a real Rincon work order, the same live-verification discipline already proven valuable for the Latchel side of this project.

**The governance note, stated plainly rather than implied as already cleared:** even narrowed to "attachments already tied to one record," this is still email-adjacent content. A saved PDF of a tenant's email about a health issue, a dispute, or an active code-compliance matter is exactly as sensitive sitting inside an AppFolio work-order attachment as it was inside a Latchel invoice PDF in the original 10-ticket test (the "Tenant is complaining of health concerns" example is exactly this pattern). Narrower scope than a shared inbox makes this a smaller, easier governance conversation than the full inbox idea Mason already looked at once — it does not make it a non-issue. If this is ever built, it needs the same two-layer content check already built for `maintenance_claims` (keyword scan + model judgment, quarantine, audit log) applied before any attachment content is summarized or shown, not a new, separate policy. Not proposed for v1 of this spec — this section is research to hand to Peter and Asimov, not a build item.

## Size Estimate

Grounded against this project's own comparable work, not a guess: the base Maintenance History (Latchel) build — new external API connector, a from-scratch AI extraction pipeline with its own content-check and review gate, a brand-new Hub section — ran roughly Neo 1-2 sessions, Q 3-4 sessions, Tron 1-2 sessions, plus a full multi-specialist governance gate.

This feature is smaller on almost every axis that made that build take what it took: no new external credential, no new extraction-from-raw-documents pipeline, no new content-check (the existing exclusion view is reused wholesale), no new review-queue UI pattern (the existing claim-marker styling is reused). The one genuinely new piece of engineering — cross-ticket aggregation, the component categorizer, and a citation-preserving synthesis prompt with its own validation step — has no precedent to reuse and is where real build and test time goes.

Rough shape: **Neo — 0-1 session** (likely zero new tables, since v1 skips caching; revisit only if a cache table proves necessary later). **Q — 2 sessions** (categorizer, aggregation/open-resolved/recency logic, the synthesis prompt and its citation-validation step, the new route). **Tron — 1 session** (one new page/tab, reusing the existing dashboard's visual language). **Governance/QA — a lighter pass than the base build**, focused specifically on the new synthesis-citation risk described above, not a repeat of the full six-condition review. Overall: roughly a third to half the size of the base Maintenance History build, not a comparable-sized build in its own right.
