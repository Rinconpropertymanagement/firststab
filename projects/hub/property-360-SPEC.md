Three corrections to what the research passes assumed, found by reading the actual code rather than the research summaries — noted here because they change what this spec proposes:

2. **The Overview endpoint's citation ("both validate the param as a real UUID") is correct only for the API, not for a page.** Fixed above.
3. **`property-search.js`'s Security Deposit fallback comment is stale, not dead weight.** Its header says the `security_deposit_cases` migration "has NOT been applied to the live database yet." The migration file (`20260813000002_security_deposit_cases.sql`) exists and the Security Deposit tool is fully built and in active use (3,268-line router, real case data flowing through it) — so the comment describes a moment that has passed. The defensive try/catch itself is harmless to leave in (it just means one Supabase error can't take down the rest of search results), but the comment should be corrected as routine cleanup whenever someone is next in that file. Not blocking, not part of this build.

## What This Is — and Isn't

**Is:** one new page. Peter searches for a property (the same search box that's already on every Hub page today), picks a match, and sees a header, two small link-out cards (Insurance, Security Deposit), and a Maintenance section that lives natively on this page rather than linking out — see "Revision, 2026-09-02" immediately below for why Maintenance is different from the other two.

**Isn't:**
- **Not a rebuild of Insurance or Security Deposit.** Those two cards are a glance, not a replacement for Insurance's review queue or Security Deposit's case detail. Clicking through is the answer to "I need more," not a bug.
- **Not a second search.** It reuses `GET /api/hub/search-properties` (`lib/property-search.js`) exactly as built — same matching, same 10-result cap, same tools it already knows how to check.
- **Not a new permission tier.** Explained in full below, but stated up front because it's the most important design decision in this document: nobody sees anything on this page they couldn't already see by opening that tool directly.
- **Not a Call Stats feature.** Call Stats is organized around a staff member in a pod, not a property — it has no `property_id` anywhere in its schema, sync code, or dashboard, and its own SPEC.md says so in its own words: *"This data has no natural property to hang off of; it's organized around a person, within a pod, which is a genuinely different axis than anything else in the Hub today"* (`call-stats/SPEC.md:103`). This isn't a gap to close later with more engineering — the underlying calls simply aren't tied to a tenant or property today (confirmed: zero references to a phone number, contact, or Aircall line object anywhere in `call-stats/lib/`). Property 360 has no Call Stats card, full stop — not a greyed-out placeholder, not a "not available" line inside a card. One quiet sentence at the bottom of the page explains why, so it reads as a deliberate design choice instead of a missing feature: *"Call Stats tracks staff phone activity by pod, not by property, so it isn't part of this page."*

### Revision, 2026-09-02 — Maintenance History is being retired as a standalone tool, folded into this page

Real-time decision from a live conversation with Peter, after this spec was first drafted: the standalone Maintenance History tool (its own page, its own four tabs) goes away entirely. Everything it did that's worth keeping moves onto this page instead:

- **The Tickets tab is removed, permanently, everywhere — not carried onto this page in any form.** Peter's own reasoning, verbatim in spirit: raw ticket-by-ticket browsing isn't something anyone acts on, and AppFolio/Latchel already do that job, natively, better than a second copy inside the Hub ever would. The Hub's value is the synthesis (Overview), not a rebuilt list of the raw source data. Anyone who needs ticket-level minutiae goes to AppFolio or Latchel directly.
- **Overview** becomes the small Maintenance summary card on this page — same shape as the Insurance and Security Deposit cards.
- **Budget** and **Needs Privacy Review** become full sections on this same page, not links out to somewhere else — Peter's framing: "keep the info in the 360 tool and not have a separate maintenance tool." Unlike Budget's dollar figures, Privacy Review is a real workflow (an acknowledgment gate, a review action, an audit trail) — it moves here as-is, not shrunk to a glance.
- This changes the shape of the page for Maintenance specifically: Insurance and Security Deposit stay small-card-plus-link-out; Maintenance becomes small-card-plus-two-full-sections, all on one page, because there's no longer a separate Maintenance History page to link out to.
- The underlying data and backend routes are **not** being rewritten — `maintenance_requests`, `maintenance_claims`, the nightly Latchel ingest, the AppFolio budget/actuals sync, and the existing `/api/maintenance-history/...` routes for overview, budget, and the flagged queue all stay exactly as they are. What changes is which page calls them and which tab (Tickets) stops being rendered at all.

## What You'll See

**Revised 2026-09-02 — fully updated after Asimov's review and the world-class review pass; this is the current, final layout, not the original three-card version.**

The blank landing page (`/property-360`, no property picked yet) shows the same search box that's on every Hub page, plus **a "Recently viewed" strip** of the last 5-8 properties you've opened — stored only on your own device, nothing new on the server. You pick a match (or one of the recent ones). The page that opens has:

- **A header** — property name, address, city; real occupancy ("4 of 6 units occupied," not the always-wrong `units.status` field) and the nearest upcoming lease-end date; the property owner's name, phone, and email. All three of the header additions reuse math already correct and already computed elsewhere in the codebase — nothing new to build, just newly surfaced here.
- **A "needs attention" line**, directly under the header, whenever anything actually needs it — e.g. "2 things need attention: insurance expires in 12 days · deposit deadline in 5 days." Built from data every card below is already fetching; no new query, no AI. This is what makes the page answer "does this property need anything from me right now" in one glance instead of making you read every card and do the math yourself. **Cards below are ordered by the same urgency logic** — whatever's most wrong (or soonest due) renders first, not a fixed Insurance→SD→Maintenance→LeadSimple order regardless of what's actually happening.
- **Two small link-out cards**, each shown only if (a) this property has data in that tool and (b) you're already allowed to see it there:
  - **Insurance** — compliance status (a colored badge: compliant / expiring soon / expired / needs review / etc.), days until the policy expires, coverage amount against the $500K minimum, whether additional-insured is verified, and the insurer's name. A "View in Insurance Compliance" link.
  - **Security Deposit** — the status of the most recent case (pending review / escalated / reviewed, or "no open case"), days left until the 21-day deadline if one's running, whether it's escalated, how many open flags it has (missing photos, unconfirmed deposit amount, etc.), and whether it's a full move-out or a partial one. A "View in Security Deposit" link. **Rendered adjacent to the LeadSimple card below when both are present** — they're often the same real-world event (a move-out) seen from two systems.
- **A LeadSimple card**, shown only to people with real LeadSimple access (see "Access control" in the LeadSimple section — a dedicated permission, not Maintenance History's role): open stage, if any, for Delinquency, Lease Renewal, and Move Out — stage name only for v1 (e.g. "Eviction," "Backlog"), no custom-field detail. No drill-through link for v1 — LeadSimple's own web app isn't confirmed to support a stable per-record URL; Q confirms this at build time and adds a link only if one exists.
- **A Maintenance section**, shown only if you have Maintenance History access at all, made up of three parts, all on this same page — nowhere else to click through to:
  - **A small summary** — same shape as the cards above: open/unresolved ticket count, trailing-12-month spend, date of most recent activity, and how many vendors have worked here and the most recent one (name resolved and stored at nightly ingest, never fetched live). If you're one of the specific people already allowed to see flagged privacy-review content (`admin`, `reviewer`, `director_of_operations`) and this property has any, a small "N items need privacy review" note as well — jumping straight to the Privacy Review section below, on this same page. Nobody else sees any hint that field exists.
  - **A Budget section** — AppFolio's real budgeted-vs-actual figures for this property, the same data and math the old Budget tab already computed: headline number up top (this year's total budgeted vs. actual so far), full category-by-category breakdown underneath, maintenance ticket costs shown alongside for context. **Collapsed by default, expandable in place** (added 2026-09-02 for phone-friendliness — Peter mostly checks this Hub from his phone between calls) — the full content is still one tap away, not hidden behind a second page.
  - **A Privacy Review section** — the actual review workflow for this property's flagged claims: real claim text, Confirm / Correct / Reject actions, the acknowledgment gate for `director_of_operations`. Reviewed items (confirmed, corrected, or rejected) drop out of the default view; a "Show reviewed items" toggle (default off) reveals the full history — see the Privacy Review section above for Mason's approved design and conditions. Only rendered for people with a real role in Maintenance History; nobody else sees this section exists. **Also collapsed by default on the page, same phone-friendly treatment as Budget.**
- **A Maintenance Users section** (admin-only) — grant/revoke `admin`/`reviewer`/`director_of_operations` for Maintenance History, the exact content of today's standalone "Users" tab, folded into this page rather than kept as a separate destination. Visible only to `admin`.
- **A tool you have no role in simply has no card or section.** No lock icon, no "ask for access" message — the same way that tool's own page would just 403 you if you tried to load it directly, this page just doesn't show you that it exists.
- **A tool with no data for this property has no card either** — same convention the search widget already uses ("No records yet").
- **If nothing exists anywhere yet**, the page says so in one plain line rather than showing empty cards.
- **If any one card's data fails to load**, that card alone shows "Couldn't load this right now" — the rest of the page still works (see "Partial-failure handling" in How It Works).

## How It Works

1. Peter types into the hub-wide search box (already on every page). It calls `GET /api/hub/search-properties?q=` exactly as it does today — no changes to that route.
2. Each result already carries a real `properties.id` (`property-search.js:156`, returned but currently unused by anything — see `global-search-widget.js:54-57`, `toolLink()`, which discards it and builds every existing tool link from a text name/address instead). Property 360 becomes the first thing in the Hub that actually uses that id.
3. The widget gets one more link per result, alongside the existing Insurance / Maintenance History / Security Deposit links: **"Property 360"**, pointing at `/property-360?property_id=<id>` — the real id, not a text label. Shown whenever a property matches at all (even one with no data anywhere yet — "nothing here yet" is itself a useful, honest answer, matching the search widget's own existing empty-state line).
4. The Property 360 page (`GET /property-360`, a new Hub-level route — see "Where it lives") reads `property_id` from the URL and calls one new endpoint: `GET /api/property-360/:propertyId/summary`.
5. That endpoint does four things, entirely server-side, in one request:
   - Looks up the property's own header info directly from `properties` (id, name, address, city, unit_count) — same table every other tool already reads this from.
   - For each of the three tools, runs that tool's **own, unmodified** access-check function (see "Access Control" below) against the logged-in user. If it says no, that tool's card is left out of the response entirely — not included-but-blank, not a 403 for the whole page, just genuinely absent, the same way `flagged_review_count` is already omitted rather than zeroed for ungated roles on Property Overview (`maintenance-history/router.js:807`).
   - For each tool that says yes, calls that tool's own new, small summary function (see below) to get the 3-5 facts for that card.
   - Returns one combined JSON object: the header, plus whichever of the three cards the viewer is allowed to see and that have data.

   **Partial-failure handling — added 2026-09-02 by the world-class review, not in the original design.** Each card's data-fetch must run independently (all in parallel, each in its own try/catch), never as a chain where one failure takes down the whole response. The closest existing precedent in this codebase (`maintenance-history/router.js`'s own multi-source Overview route) fails the *whole* request on the first sub-query error — the wrong pattern to copy here, since this page pulls from four independent sources including one external API (LeadSimple) with no SLA Rincon controls. A card whose fetch fails should render "Couldn't load this right now," distinct from "no access" and "no data" — three different, already-real states this page needs to tell apart, not collapse into one.
6. The page renders the header, the two link-out cards, and the Maintenance section. Insurance's and Security Deposit's "View in ___" links use the existing, already-working text-label handoff (`?property=<name>`) each of those dashboards already reads today — no changes needed there, because neither has tabs; landing on either one already shows the right filtered view. Maintenance has no "View in ___" link at all — see next section for why.

### Drill-through links

Insurance and Security Deposit each already read `?property=<name or address>` on page load and pre-filter their single list view to it (`insurance/dashboard/index.html:1107-1120`, `security-deposit/dashboard/index.html:812-816`) — a Property 360 card's "View in ___" link works today, unmodified, for both.

**LeadSimple has no drill-through link for v1** — added 2026-09-02, closing a gap the world-class review found (this section originally covered Insurance/Security Deposit/Maintenance and never mentioned LeadSimple at all). LeadSimple's own web app isn't confirmed to support a stable, linkable URL per process record; Q confirms this at build time and adds a "View in LeadSimple" link only if one genuinely exists, rather than guessing at a URL format now.

**Maintenance History has no drill-through link, on purpose.** Under the original three-card design, this section would have needed a small dashboard fix (teaching the old Tickets-tab-first `?property=` handoff to instead recognize `?property_id=&tab=overview` and open Overview directly). That fix is now moot: per the 2026-09-02 revision above, Maintenance History's Overview, Budget, and Privacy Review all render natively on the Property 360 page itself — there's no separate page left to send someone to. The old `/maintenance-history` dashboard route, its Hub home page tile, and its link in the global search widget should all be retired as part of this same build (see Open Items) rather than left behind as an orphaned page nothing points to anymore.

## Per-Tool Card Content

### Insurance

| Fact | Source |
|---|---|
| Compliance status (badge) | `property_insurance.status` — `compliant / expiring_soon / expired / pending_review / escalated / no_policy / insufficient_liability / no_additional_insured` |
| Days until expiration | `expiration_date`, same math the dashboard already does client-side (`daysLeft()`, `index.html:1124-1130`) |
| Coverage amount vs. $500K minimum | `coverage_amount`; the $500K floor is already hardcoded server-side (`router.js`, `belowMin = covAmt != null && covAmt < 500000`) |
| Additional insured verified | `additional_insured_verified` (boolean) |
| Insurer name (secondary line) | `insurer_name` |

`GET /api/insurance/records` already returns all of this, joined to `properties`, but for **every** property at once with no filter (`router.js:280-295`) — the dashboard filters client-side. A property-scoped card needs a small new route.

**New:** `GET /api/insurance/property/:propertyId/summary`, added to `insurance/router.js`, gated by the same `requireInsuranceAccess` every other read route in that file already uses. Same query as `/records`, `.eq('is_current', true)`, with `.eq('property_id', propertyId)` added. One real gap to close here that the base tool already lives with: `property_id` is a real FK but is nullable, and the tool's own current-policy uniqueness constraint is actually enforced on `appfolio_property_id`, not `property_id` (`property_insurance` migration, `idx_pi_one_current_per_property`) — a row saved through an older or batch path could in principle carry only `appfolio_property_id`. The new route should query on `property_id` first and, if nothing comes back, fall back to `.eq('appfolio_property_id', properties.appfolio_id)` for that property — a couple of extra lines, not a redesign — so a real policy doesn't silently disappear from the card because of which path it was originally saved through.

### Security Deposit

| Fact | Source |
|---|---|
| Case status | `security_deposit_cases.status` — `pending_review / escalated / reviewed` (no "closed" state exists; the actual deposit return happens outside this tool) |
| Days until the 21-day deadline | `disposition_deadline` (a generated column, `move_out_date + 21`) |
| Escalated | `status === 'escalated'` |
| Open-flags count | The `flags[]` array the case-detail route already computes at read time (no property address, no move-in/move-out photos, no deposit on file, etc.) |
| Tenancy status | `full_tenancy_ending` vs. `partial_co_tenant_move_out` vs. unconfirmed |

No property-scoped route exists today — `security_deposit_cases` has no `property_id` column at all; every route is case-id or lease-search based. The join is real and guaranteed, just three hops: `security_deposit_cases.lease_id → leases.id`, `leases.unit_id → units.id`, `units.property_id → properties.id` — every hop `NOT NULL`, confirmed in both the initial schema and `20260813000002_security_deposit_cases.sql`, and this exact join is already performed today in `GET /cases/:id` (`router.js:919-935`).

**New:** `GET /api/security-deposit/property/:propertyId/summary`, gated by `requireSecurityDepositAccess` (the same "any of the four roles" gate `/cases` and `/cases/:id` already use). Query: `units` filtered to `property_id = X`, embedding `leases → security_deposit_cases`, the same shape `lease-search`'s own leg-1 query already uses (`router.js:1267-1270`). **One property can have more than one case over time** (a unit re-leases; each occupancy gets its own `leases` row and is eligible for its own case) — v1 shows only the single most recent case, matching "one property, one glance." A property's full case history stays inside Security Deposit itself; Property 360 doesn't try to summarize a list.

### Maintenance History — summary card, plus two full sections (revised 2026-09-02)

**The small summary card** — same glance shape as Insurance and Security Deposit:

| Fact | Source |
|---|---|
| Open ticket count | `maintenance_requests.status` for this property's units, not closed/completed |
| Trailing-12-month spend | Same sum Property Overview's own header already computes (`router.js:554-573`) |
| Last activity date | Most recent `maintenance_requests` touch for this property |
| Vendors used, most recent | Added 2026-09-02 — see "Vendor history" below |
| Flagged-review count (gated) | Same count already computed and already role-gated on Property Overview (`flagged_review_count`, omitted — never zeroed — unless the viewer's role is in `PRIVACY_REVIEW_ROLES = ['admin', 'reviewer', 'director_of_operations']`, `router.js:167,807`) — a jump link straight to the Privacy Review section below, not to a separate page |

`GET /api/maintenance-history/property/:property_id/overview` already computes most of this, but it also does the real work Overview exists for — grouping tickets by system and calling Claude once per non-empty component bucket to write the synthesized brief (`property-overview-SPEC.md`'s "Step 5"). Calling that full endpoint just to populate a summary card means paying for an AI synthesis pass every time someone glances at a property, even if they never read further — a real cost/latency regression that endpoint's own spec justified specifically for a deliberate "someone's first day" lookup, not as the backing data for a default entry point.

**New:** `GET /api/maintenance-history/property/:property_id/summary`, gated by the same `requireMaintenanceHistoryAccess` every read route in that file already uses. Pure SQL — the same open-ticket-count and trailing-12mo-spend math already written for `/overview`'s header, and the same gated `flagged_review_count` lookup already written for the same endpoint — reused as functions, not AI calls. **This route must never read `maintenance_claims` or `maintenance_claims_decision_safe` directly** — only `maintenance_requests` and the already-gated count. Keeps flagged content out of this route by construction, same as Property Overview itself.

**The full narrative brief** (what `/overview`'s AI synthesis produces) is **not** shown on Property 360 at all, in any form — not as a card, not as a "read more" expansion. It's reachable only by explicitly opening it, likely as a link from the summary card ("Read the full property brief") that triggers the real AI call on demand, the same deliberate, not-default-loaded design `property-overview-SPEC.md` already argued for.

**Budget section** — the old Budget tab's exact content, unchanged, relocated onto this page. Reuses `GET /api/maintenance-history/property/:property_id/budget` exactly as it exists today (confirmed live 2026-09-02: real data, 4,457 budgeted line items and 3,714 actual-spend records across the portfolio, synced nightly) — same route, same gate (`requireMaintenanceHistoryAccess`), no rewrite needed. Headline number (this year's total budgeted vs. actual so far) shown first; the full category-by-category table, and the maintenance-ticket-cost context table, shown underneath in the same section — not hidden behind a second click, since the whole point of moving this here is "attached to the property," not a shrunk-down teaser.

**Privacy Review section** — the old Needs Privacy Review tab's workflow, relocated onto this page and pre-filtered to this property, plus one real behavior change decided 2026-09-02. Reuses `GET /api/maintenance-history/flagged-queue` (already supports `?property_id=` — built for exactly this kind of property-scoped entry point, `shared-property-context-SPEC.md` Part 2) and `POST /api/maintenance-history/claims/:id/review`, both otherwise exactly as they exist today: same roles (`admin`, `reviewer`, `director_of_operations`), same acknowledgment gate, same audit logging.

**Resolved 2026-09-02 — reviewed items drop out of the default view.** Today, a claim stays visible in this queue forever regardless of review status — reviewing one writes an audit record but doesn't remove it from view or change what the AI can use elsewhere (confirmed live 2026-09-02, reading the actual route: `flagged-queue` has "no time bound and no review_status filter... every claim ever flagged stays visible here forever, by design"). Peter's call: the default view should only show `review_status = 'unreviewed'` items — a real to-do list that actually shrinks as it's worked. **Assumption flagged for Peter to confirm:** this spec reads his instruction as "once reviewed" broadly — confirmed, corrected, *or* rejected all drop out of the default view, not literally only the Confirm action — since a queue that keeps nagging about items already corrected or rejected wouldn't fix the complaint. Say if that's wrong.

The permanent record itself doesn't go away — a "Show reviewed items" toggle (default off) removes the `review_status` filter and surfaces the exact same full history the queue shows today, for anyone who needs to see it (an audit, a spot-check). Concretely: `flagged-queue` gets one new optional query param (e.g. `?include_reviewed=true`, default `false`), following the same additive-parameter pattern `?property_id=` already used — when omitted or false, the query adds `.eq('review_status', 'unreviewed')`; when true, no status filter, unchanged from today.

**Mason's review, 2026-09-02 — approved with conditions.** He confirmed this change doesn't touch anything he originally approved (same three roles, same acknowledgment gate, same permanent exclusion from automated use) and, on the merits, thinks a filtered queue is actually *safer* than today's unfiltered one — an ever-growing, un-triaged list is more likely to bury a genuinely new flag than a right-sized one is to cause something to be forgotten. He also confirmed reading "reviewed" broadly (Confirm, Correct, *or* Reject all count) is correct, not just Confirm. Conditions to build this to, not open questions:
1. The toggle's default (off) is a condition of this approval, not just today's implementation choice — don't let a later change quietly flip it or remove it without another Mason pass.
2. The full-history toggle must be available to all three roles equally (`admin`, `reviewer`, `director_of_operations`) — never narrowed to a subset.
3. This is a display filter only — the underlying audit trail (every Confirm/Correct/Reject, permanently) must never be touched, deleted, or overwritten by this change.
4. **Resolved 2026-09-02, by build + final review.** Confirmed directly in the ingest code (`maintenance-history/router.js`): claims are strictly insert-only — every candidate becomes a fresh row with `review_status: 'unreviewed'` always, and the nightly ingest never `UPDATE`s an existing claim row. A reviewed claim's status cannot be silently reset. **Related, pre-existing, non-blocking quirk found in the same check:** re-ingesting a ticket whose Latchel job changes creates a brand-new duplicate `unreviewed` claim rather than deduping against an already-reviewed one for the same fact — real queue noise, not a Fair Housing exposure (it re-surfaces content, never hides it), and not part of this build's scope to fix.
5. Nice-to-have, Mason's suggestion, not required: a quarterly glance at the full reviewed history (by whoever ends up owning this) as a sanity check that review decisions look reasonable over time — good practice, not a build requirement.

Either way, the underlying Fair Housing safeguard doesn't change: once flagged, a claim is permanently excluded from `maintenance_claims_decision_safe` (and therefore from Overview's synthesis and every other automated use) no matter what a reviewer decides — reviewing something never "lets it back in," it only changes whether it nags you by default.

**Tickets — retired, not carried onto this page.** Per the 2026-09-02 revision above, raw ticket-by-ticket browsing isn't part of Property 360 in any form. What still depends on ticket-level data under the hood is unaffected: the nightly Latchel ingest, Overview's synthesis, and the recurring-issue logic all keep reading `maintenance_requests`/`maintenance_claims` exactly as before — only the human-facing "browse every ticket" screen goes away.

**Budget — removed entirely, 2026-09-03.** Peter confirmed Rincon doesn't use AppFolio's Budget feature — the budgeted-vs-actual comparison section (sourced from `annual_budget_forecast`/`appfolio_property_budgets`) was pure noise from a feature nobody maintains, so it's gone from this page. The real AppFolio *actual* spend data (`appfolio_property_actuals`) is a separate report/table and was NOT removed — it's the source behind the Maintenance summary card's "AppFolio repair/maintenance spend" line (see below). The old standalone Maintenance History Budget tab still technically exists in code but is unreachable now that `/maintenance-history` redirects — dead, not deleted, low priority to clean up.

## Access Control

This is the most important design decision in this spec, so it gets its own section rather than a paragraph inside "How It Works."

**The rule:** Property 360 must never let anyone see more than they could already see by opening that tool directly. Composing three tools onto one page must not become a fourth, broader way in.

**The mechanism, confirmed by reading all three routers, not assumed:** all three tools (Insurance, Security Deposit, Maintenance History) implement the exact same three-function pattern, independently but identically shaped —

- `attach<Tool>Role(req, res, next)` — looks up `team_members` by `req.user.id` (already set by the hub's shared `requireLogin`), then `team_member_tool_roles` filtered to that tool's `tool` value, and sets `req.<tool>Role` to the result or `null`. Fails closed on any lookup error (`insurance/router.js:190-226`, `security-deposit/router.js:298-333`, `maintenance-history/router.js:98` — same shape in all three, confirmed by reading each).
- `require<Tool>Access(req, res, next)` — 403s unless `req.<tool>Role` is truthy. Used on every read-mostly route.
- `require<Tool>Role(...roles)` — 403s unless the role is in an explicit per-route allow-list.

None of these three functions are exported today — each `router.js` only exports `{ router, internalRouter }` (confirmed: `insurance/router.js:1398`, `security-deposit/router.js:3268`, `maintenance-history/router.js:1792`). That's the one small, additive change each tool needs: add `attach<Tool>Role` and `require<Tool>Access` to that file's existing `module.exports` line. **Nothing about the function's logic changes** — this is exporting an existing, already-reviewed function, not writing a new one.

**What Property 360's aggregation route does with that:** for each of the three tools, it imports that tool's own `attach<Tool>Role` and runs it against the same request (all three read `req.user.id`, which is already set once by the hub's shared login before any of this runs) — then checks the resulting `req.<tool>Role`. If it's null, that tool's card is skipped entirely, before its summary function is even called. If it's set, the card is built.

**Note, 2026-09-02: this holds exactly as-is even with Maintenance History folded into this page.** `attachMaintenanceHistoryRole` / `requireMaintenanceHistoryAccess` / `requireMaintenanceHistoryRole` don't change at all — they're still the real, only gate for the Maintenance summary, Budget section, and Privacy Review section, just called from `property-360/router.js` instead of from a standalone `maintenance-history/router.js` page route. **The LeadSimple card does NOT reuse this same check** — per the final decision in the LeadSimple section above, it gates through the dedicated, already-built LeadSimple access mechanism (`leadsimple_delinquency`/`leasing_reviewer`) instead of piggybacking on Maintenance History's unrelated role.

**Why this is the safer of the two options, not the two considered:**
- **Reimplementing each tool's role check inside a new combined endpoint** — the option this spec explicitly rejects — is exactly the kind of drift the research flagged as a real, recent risk in this codebase (see the CHECK-constraint history below: `director_of_operations`'s access to Maintenance History's privacy-review content was added, then had to be pulled back out and re-approved by Mason in a separate build, per `shared-property-context-SPEC.md`'s own post-build correction — a second copy of that logic anywhere is a second place for that kind of gap to reappear unnoticed).
- **A real HTTP call from Property 360's backend to each tool's own already-gated route** (`fetch('/api/insurance/records')` from inside the server) would also reuse the real gate, but adds real complexity for no real benefit here — forwarding the session cookie correctly, handling three extra network round-trips, and building a route that calls itself. Nothing in this codebase does that today, and reusing the same exported function in-process gets the identical guarantee (the exact same code decides access) without inventing a new pattern.
- **Calling the exported gate function directly, in-process, inside the same request** gets the exact same enforcement as opening that tool's own dashboard — literally the same function, called the same way, just once more per tool — with none of the added complexity of a second server call.

**No new role, and no new `tool` value.** The established pattern for adding a tool to this permission system is a new migration that does `DROP CONSTRAINT` / `ADD CONSTRAINT` on `team_member_tool_roles`'s two CHECK clauses — confirmed done, in order, for every real addition so far: `insurance_compliance` (`20260812020000`), `security_deposit` (`20260813000004`), `maintenance_history` (`20260815010000`), `call_stats` (`20260819020000`), `content_engine` (`20260821000000`), the three LeadSimple tools (`20260825000000`), and `approval_briefing` (`20260827000000`) — the current full set is visible in the last of those (`20260827000000_approval_briefing_phase1.sql:429-450`). **Property 360 should not add itself to that list.** It has no content or actions of its own to gate — every fact it shows is already gated by the tool that owns it. Anyone logged into the Hub at all can open the page; what they see on it is entirely a function of what they're already allowed to see elsewhere. This also means someone with zero roles in any of the three tools sees a real, honest "nothing to show you here" page instead of a 403 — a better experience than most of this Hub's tools give someone with no access today, and it costs nothing to build because there's no gate to write.

## What's Deliberately Out of Scope for v1

- **No portfolio-wide view.** One property at a time, exactly what was asked for. A "which properties need attention" rollup across the whole portfolio is a different, bigger feature, not a variant of this one.
- **No new AI synthesis on this page.** Every fact on every card is already computed by its source tool with plain SQL (or, for Maintenance History, is a plain-SQL subset of what `/overview` already computes) — zero new Claude calls anywhere in this build. This is also what keeps it fast and cheap to load compared to Property Overview's own page.
- **No Call Stats card**, for the structural reason explained above — not deferred, not a v2 item, a permanent no unless Call Stats itself is redesigned around a property or tenant axis someday, which is a separate, much larger build (capturing and normalizing phone numbers, matching against `tenants.phone`, handling vendor/prospect calls with no tenant match) that nothing in this spec depends on.
- **No full case/policy history.** Insurance shows the current policy (already the only thing `is_current = true` tracks); Security Deposit shows the most recent case. Full history stays inside each tool.
- **No raw ticket browsing, anywhere, permanently — added 2026-09-02.** Not deferred to v2, not a smaller version on this page — removed as a concept. Peter's own reasoning: nobody acts on a raw ticket list, and AppFolio/Latchel already do that job. If someone needs ticket-level detail, they go to AppFolio or Latchel directly, not to the Hub.
- **No new `tool` permission value, no new admin role-management screen for this page.** Explained above — there's nothing to grant.
- **No editing or actions from this page, except the Privacy Review workflow, which is native to this page (see Maintenance section above) — corrected 2026-09-02.** Approving an insurance policy or resolving a security deposit escalation still happens inside that tool's own page — this page never gains write actions for Insurance or Security Deposit, and mixing those in here would mean re-deciding each tool's own write permissions a second time, the exact duplication this spec's access-control section argues against. This bullet previously said "read-only, on purpose" without that carve-out, directly contradicting the Maintenance section elsewhere in this document — found and fixed by the 2026-09-02 world-class review.
- **No caching table.** Same reasoning `property-overview-SPEC.md` already used for its own page: this is a look-something-up tool, not a high-traffic dashboard, and three cheap SQL-only lookups per page view is well within "fine to compute at request time." Revisit only if real usage proves otherwise.
