## 1. What This Feature Does

Right now, if a property has special handling instructions on file (e.g. "Call Zack for approval on any work order"), the only place that shows up is the property's page in the Hub — someone has to think to go look. This feature makes it push instead of pull: the moment a new work order is created in Latchel for a property that has one of these notes, an email goes straight to that property's team inbox (Faria or Solimar) with the note and the basic work order info, so the right people see it immediately instead of finding out after the fact.

It is a fixed-template, plain-text email — no AI writes any part of it. It reuses Rincon's existing, already-verified Latchel webhook rather than building a new one.

## 2. Trigger and Webhook Design

### 2.1 Reusing the existing webhook, not building a new one

`POST /api/approval-briefing/internal/webhook` already receives every `Job/created` and `Job/updated` delivery from Latchel, secret-verified and rate-limited. Per the instruction for this spec, this feature adds a second, independent branch to that same handler — it does not touch, reorder, or depend on the existing "Needs Approval" (`state_id === 27`) logic already there, and it is not a new route with its own secret. Concretely: after `checkWebhookSecret()` and the `object_type === 'Job'` filter (both already in the file, both unchanged), the parsed `job` object feeds two independent branches — the existing approval-briefing logic, and this feature's new logic — in either order, since neither reads or writes anything the other touches.

Recommended file organization (Q's call on the exact layout): keep the secret/rate-limit code and the route itself in `approval-briefing/router.js` exactly where they are, and put this feature's own logic in a new sibling module (e.g. `approval-briefing/lib/work-order-notes-alert.js`) that the route calls into — the same shape `router.js` already uses to call out to `./lib/gather.js` for its own logic.

### 2.2 Verified live: a fresh Latchel Job carries what this feature needs, directly

This was the single biggest open question, and it's now resolved with real data, not assumption. Using the existing read-only connector (`latchel-connector.js`, no new methods added), I pulled 170 real jobs updated in the last 7 days and fetched full detail on 3 of them via `getJob()`.

**Both the webhook-delivery shape and the `GET /jobs/{id}` detail shape carry `property_id` — Latchel's own internal property ID — directly on the job, with no `null`s in the sample.** (Full key list, confirmed live: `access_instructions, created_at, description, enter_permission, estimate, estimate_note, is_emergency, is_mandatory, is_urgent, is_vacant, issue_id, job_id, job_rating, location_id, manually_assign_vendor, max_cost, name, order_number, pm_id, problem_id, project_id, property_id, rating_comments, ref_job_id, scheduled_end, scheduled_start, severity, slug, source, state, state_id, tenant_id, updated_at, vendor_description, vendor_id, vendor_rating`.) There is no address or unit text on the Job object itself, and no `ref_property_id` on Job (that field lives only on the separate `GET /properties` object) — `property_id` is the only, and sufficient, link.

**This means property resolution does NOT need to go through a matched `maintenance_requests` row at all** — the original concern was that this might be the only reliable link, and that turns out not to be the case, because the actual link is one level up, at the property level, not the ticket level: `job.property_id` (Latchel's internal ID, e.g. `175353`) matches `properties.latchel_property_id`, a column already populated by the existing `POST /api/maintenance-history/internal/reconcile-properties` job (matches Latchel's `GET /properties`' `ref_property_id` against `properties.appfolio_id`). Checked live today: **350 of 398 properties (88%) already have `latchel_property_id` populated** — this is current, not the 0%-populated snapshot `approval-briefing-SPEC.md` recorded a month ago; that reconciliation job has clearly been run since. The remaining 12% is a real, bounded gap, not a design blocker — see 2.4.

**No new Latchel dashboard subscription is needed either.** Approval Briefing already has both `Job/created` and `Job/updated` subscriptions registered and pointed at this exact URL — meaning every new-work-order-creation event is already arriving here today; it's just being discarded because it isn't state 27. This feature's new branch simply stops discarding it.

### 2.3 Defining "new work order" without depending on an unconfirmed field

Whether Latchel's webhook body explicitly labels a delivery as "this was a created event" vs. "this was an updated event" is not confirmed by anything in this codebase's existing research or code — the current handler never checks for such a field, because it only cares about the resulting state, not which event produced it. Rather than depend on an unverified field, this feature defines "new work order" operationally: **the first delivery this system ever sees for a given `latchel_job_id` is what triggers the one-time notification** (see Section 4 for the dedup mechanism that makes this safe). In practice this is equivalent to "the job was just created," since a job's creation event will essentially always be the first delivery Latchel sends for it — and it has the added benefit of still working correctly even in the rare case a `created` delivery is dropped and an `updated` delivery arrives first.

### 2.4 Backstop: yes, this needs one, and here's why

Decided, not assumed: **yes.** Two independent reasons, not one:
1. Latchel's webhook has no documented delivery guarantee — confirmed by three separate official doc sources in the approval-briefing research, and reconfirmed independently in `maintenance-history/latchel-sync-frequency-feasibility.md` ("Rincon's own working webhook build for Approval Briefing proves this, since it still needed an hourly backstop poll on top of the webhook").
2. This feature's entire purpose is "don't miss this" — an even stronger case for a backstop than approval-briefing had for itself.

Design: a new internal route, `POST /api/approval-briefing/internal/reconcile-work-order-notes`, authenticated with the same `checkCronSecret()`/`CRON_SECRET` pattern already in this file (reused exactly, not reinvented). It calls `latchel.listJobsUpdatedSince(since)` — the same connector function `maintenance-history`'s nightly ingest already uses, with the same proven pagination-safe fix already built into it — and runs every returned job through the identical resolve → check-notes → check-pod → send logic as the webhook path. This is a new route rather than an added branch on the existing `/internal/reconcile` endpoint because that endpoint pulls a structurally different query (`listJobsNeedingApproval`, state 27 only) — reusing the auth pattern, not the endpoint itself, matches this codebase's existing convention of one focused route per concern.

Because this route re-checks the same dedup table as the webhook path (Section 4), running it repeatedly or on overlapping windows is always safe — no double-sends.

**Cadence:** recommend hourly, matching approval-briefing's existing poll (Scotty already maintains a cron entry for that sibling job on the same box). One honest caveat: this repo has no crontab file anywhere in it — every real cron schedule on the production server (Sally) is configured directly there, by hand, outside version control (confirmed via `maintenance-history/latchel-sync-frequency-feasibility.md`, which describes reading Sally's live crontab directly). Scotty needs to actually add the cron entry for this new endpoint; this spec can recommend a cadence but can't confirm one exists until Scotty wires it up.

|---|---|---|
| Maintenance notes | `properties.maintenance_notes` (TEXT, nullable), synced nightly from AppFolio's `property_directory` report — mapping already shipped in `sync.js` (`if (row.maintenance_notes) built.maintenance_notes = row.maintenance_notes;`), contrary to this spec's original brief which described that mapping as still pending | **194 of 398 properties (49%) currently populated** |

Combined, of the 194 properties with a note on file: **174 also have both a pod and a resolvable `latchel_property_id` (the clean path). 20 have a note but no `latchel_property_id` yet** (the 12% gap from 2.4 — these are caught by the backstop once `reconcile-properties` catches up, not lost). **1 has a note but no pod assigned** (the unassigned-pod fallback case, Section 5.2 — real, but rare today).

**Important scope boundary (amended 2026-10-16):** the base email reads `properties.maintenance_notes` only for free text, and never reads `job.vendor_description`, `job.estimate_note`, or `job.access_instructions` in any mode. Those are the job's own free-text fields, not content-checked anywhere in this codebase for this purpose, and pulling them in would blur this feature into the much larger, still-governance-blocked "Section 8 email generation" work in `approval-briefing-SPEC.md` (explicitly out of scope per this spec's brief). The base email (the original design) is built entirely from already-synced, already-reviewed-once property data plus a handful of deterministic job fields (address, job id, ticket number).

**The one exception, added 2026-10-15 at Peter's request and rebuilt 2026-10-16, fixed in the second round:** an optional "What the work order is" block (Section 6A) that quotes the job's own title (`job.name`) and description (`job.description`) after cleaning and a REQUIRED local word-list screen. **The job's free text IS read when `WORK_ORDER_ALERT_DESCRIPTION_MODE` is `shadow` or `on`** (in `shadow` it is read, scanned and thrown away; in `on` it is also quoted in the email). It is read in full (up to a 20,000 character cap), scanned locally on the Hub server only, checked a second time in the exact 100 and 300 character pieces that would be printed, and **never sent anywhere**: not to Anthropic, not to any other processor, in any mode. Only `off` (the default, and what any unrecognised value means) reads none of it, and then the email is byte-identical to the original design. The read-only Latchel lookup (only when the job in hand has no `description` key) is asked for a plain-digit job id only, and the job it returns must carry that same id, or the block says "could not be retrieved". Section 6A lists the exact fields allowed and forbidden.

## 4. Duplicate-Notification Prevention — a small new table (Neo)

**Flagging this as a small, well-defined Neo task**, not inventing schema myself. Requirements only:

A new table — suggested name `work_order_note_alerts` — one row per Latchel job that has triggered (or attempted to trigger) a notification. Unique on `latchel_job_id`. Fields, grouped by purpose (exact types/constraints are Neo's call):

- **Identity:** `latchel_job_id` (unique, not null), `latchel_property_id` (Latchel's raw property ID as seen on the job, captured even if it didn't resolve), `property_id` (nullable FK → `properties`, RESTRICT).
- **What was resolved:** `pod` (`'Solimar'` \| `'Faria'` \| `'unassigned_both'`), `recipients` (email array — who it actually went to).
- **Content-check result** (mirrors `maintenance_claims`' existing fields, same discipline — never store the matched term text, only the category): `flagged_protected_class` (boolean), `flagged_category` (text, nullable).
- **What was sent:** `notes_snapshot` (the maintenance-notes text as actually included in the email — if the content check held it, this stores the placeholder text that was sent instead, never the raw flagged text, per this codebase's standing rule in `protected-class-terms.js`).
- **Outcome, and retry logic:** `send_status` (`'sent'` \| `'failed'`), `send_error` (nullable), `trigger_source` (`'webhook'` \| `'reconciliation_poll'`), `attempted_at`, `sent_at` (nullable).

**The logic that makes both duplicate-prevention and failure-retry work together, with one mechanism:** before sending, check for an existing row by `latchel_job_id`. No row, or an existing row with `send_status = 'failed'` → attempt the send, insert or update the row. An existing row with `send_status = 'sent'` → skip, already handled. This means a transient send failure is automatically retried on the next poll (or the next webhook delivery for the same job, if one arrives) instead of being permanently given up on after one failed attempt — which matters specifically because this feature's whole point is not missing a notification.

RLS: enabled, zero permissive policies at creation, matching every table in this schema. Not tenant PII in the SSN/financial sense, but does carry property-operational text — Neo/Asimov should confirm whether this needs a Rule 4 data-inventory addendum (likely a light one, similar reasoning to `maintenance_notes`' own migration: operational text about a property, not personal data about a person).

## 5. Recipient Resolution

### 5.1 The normal case

Resolve via `getSharedInbox('faria_pod_team')` / `getSharedInbox('solimar_pod_team')` in `lib/notify.js` — **not** hardcoded email strings. Checked live today: the `shared_inboxes` table exists, is populated, and both keys resolve correctly to the addresses Peter confirmed (`fariateam@rinconmanagement.com`, `solimarteam@rinconmanagement.com`), both marked active. This is also simply the current codebase convention — `insurance/router.js`'s pod-routing logic already migrated off hardcoded literals to this exact lookup, and a new feature should follow the pattern already in place, not reintroduce a third hardcoded copy of the same two addresses.

### 5.2 Unassigned-pod fallback

If `properties.pod` is NULL for a property with a triggering note: email **both** `getSharedInbox('faria_pod_team')` and `getSharedInbox('solimar_pod_team')` (same shape as `insurance/router.js`'s own existing "property can't be matched to a pod" fallback, lines ~989–1005 — this feature copies that pattern directly, not a new one), **and** separately write a `tasks` row (`entity_type: 'property'`, `entity_id: <property.id>`, `title: "Property missing pod assignment"`, `status: 'open'`) so the underlying data gap is tracked, not just routed around silently forever.

**One honest caveat, worth flagging rather than glossing over:** the `tasks` table exists and is written to elsewhere in this codebase (`insurance/router.js`'s batch-import summary), but there is currently no Hub page or view that lists/displays `tasks` rows anywhere — it's a write-only destination today. Writing here is still worth doing (it's cheap, durable, and matches existing convention, and a future tasks-list view would immediately pick up these rows for free) but it should not be presented as a proven "someone will see this" mechanism on its own — pair it with the audit log entry in Section 8, and treat "build a real tasks list view" as a separate, standalone gap in this codebase that this feature surfaces but doesn't need to fix.

### 5.3 Frequency

No throttling, confirmed by Peter: every new work order at a flagged property sends its own email, every time — Section 4's dedup is purely "don't send twice for the *same* work order," never "don't send again if a similar one was sent recently."

## 6. Email Content

Plain text, fixed template, no AI-generated content anywhere in this feature. Suggested fields (Q/Tron's call on exact copy and formatting):

```
Subject: Work Order Alert — [Property Address] has special handling notes

A new work order was just created for [Property Name / Address] (pod: [Solimar/Faria]).

This property has maintenance notes on file:
"[maintenance_notes text — or the held-content placeholder, see Section 7]"

Work order: Ticket #[order_number] (Latchel job [job_id])
Created: [job.created_at]

View this property: [HUB_BASE_URL]/property-360?property_id=[property.id]
```

The base template deliberately excludes the job's own `description`/`vendor_description`/`estimate_note` (Section 3's scope boundary) — it is a fixed alert that a special-handling note exists and a new work order triggered it. As of 2026-10-15 the job's own title and description can be added, behind a safeguard and a mode switch, by the optional block in Section 6A; `vendor_description` and `estimate_note` stay excluded in every mode. `order_number` (Rincon's own human-facing ticket numbering, confirmed present on every real job pulled) is included as a convenience cross-reference, not the AI-synthesized content Section 8 of `approval-briefing-SPEC.md` covers — that remains a separate, larger, still-blocked initiative, and this feature should stay clearly on this side of that line. I don't think the line is actually blurry here: this email contains zero words generated by a model, only a template filled with already-synced structured fields plus one already-existing property-level text field. That is still true with the Section 6A block: it quotes the job's text verbatim after cleaning, and the local screen that guards it only decides show-or-hide; no model reads, writes or rewrites anything.

## 6A. Optional "What the work order is" block (added 2026-10-15, rewritten 2026-10-16 for the no-AI design)

Peter asked that the alert also say what the work order actually is. Asimov's governance ruling made this an optional block behind a safeguard and a mode switch. **On 2026-10-16 Peter decided that no AI of any kind may read this text**, so the safeguard is a local word-list screen only (Asimov's re-ruling; `compliance/work-order-note-alerts-description-governance-review.md` and the decision record `compliance/work-order-note-alerts-description-decision-resolution.md`). Everything in Section 6 stays exactly as it was, in the same order and wording; the block is one contiguous segment inserted after the `Created:` line. The subject never changes and never contains any title, description or category.

```
Work order: Ticket #7001 (Latchel job 5001)
Created: 2026-10-01T15:30:00Z

What the work order is:
  Title: Kitchen faucet leaking
  Category (auto-sorted guess): Plumbing
  Priority: Urgent (flagged in Latchel)
  Description: "Tenant reports the kitchen faucet drips constantly."
  (Quoted as typed in Latchel. Not checked for names, phone numbers or access codes. Internal use only.)

View this property: ...
```

**No AI, nothing leaves the server.** The title and description are read in `shadow` and `on` mode, scanned on the Hub server only, and never sent anywhere: not to Anthropic, not to any other service, in `off`, `shadow` or `on`. No model is called, no API key is used, and the shared Tier B contextual rescue is not used (`TIER_B_CONTEXTUAL_CHECK_ENABLED` has no effect on this feature in either direction). The one outbound call in the whole feature is the existing read-only Latchel `getJob` lookup described under "Missing data". Three tests in `approval-briefing/test/no-ai-proof.js` prove it: the import graph of the alert module holds no model SDK or content-check module; with every outbound route blocked and every AI switch turned on, `off`, `shadow` and `on` make zero outbound calls over every ordinary-word term, every category and a hostile corpus; and the feature's source files contain none of the forbidden identifiers.

**Mode switch.** `WORK_ORDER_ALERT_DESCRIPTION_MODE` = `off` | `shadow` | `on`. Unset or any other value means `off`, and the email is byte-identical to Section 6 (a test proves this against output captured from the parent commit). `shadow` runs the same cleaner, screen and read-only Latchel fallback that `on` would run on every qualifying alert, builds the block in memory, writes one counts-only audit row and throws the block away; the email that goes out is byte-identical to `off` (tested for every scenario). `on` includes the block. It never defaults to on.

**The ON interlock.** `on` takes effect only when `WORK_ORDER_ALERT_INGESTION_EXCLUSION_VERIFIED` is exactly `yes`. Otherwise the code behaves as `shadow`, logs one constant line, and the audit event records `on_downgraded: true`. That variable is set only by Jarvis or Scotty, after the Hub's Missive intake has been stopped from copying "Work Order Alert" emails into Hub tables (see the ingestion exclusion note at the end of this section), a real alert has been seen to be skipped, and Peter has said yes. Reason: once the description is in the email, a copy in `missive_message_intake` / `archive_search_corpus` would be tenant-written text searchable by Archive Search users, which contradicts Asimov's storage rule.

**Allowed fields.** The title (`job.name`), the description (`job.description`), a category label chosen by the existing keyword table into the fixed 10-label list (`maintenance-history/lib/component-categories.js`; never taken from the text, and labelled as an automatic guess), and a priority line from Latchel's own `is_emergency` / `is_urgent` booleans. **Only these four keys are ever read** from the job or from the lookup result (a test wraps the job in a Proxy and fails on any other key), with one addition: the lookup result's own job id (`job_id`, else `id`) is read once, to confirm it is the job that was asked for, and is never shown. Nothing else from the job.

**Forbidden fields.** `access_instructions`, `vendor_description`, `estimate_note`, estimate / `max_cost`, `rating_comments` / `job_rating`, `tenant_id` and any tenant name, phone or email as a separate field, vendor identity, `location_id`, the AppFolio-synced `maintenance_requests` title/description/tenant data, and any AI-written summary or rewrite of the description.

**Cleaning, before anything is checked or shown** (`lib/work-order-text-clean.js`). Strings only (null or missing is "no text"; any other kind of value is a scanner error and holds the block). Characters are normalised (NFKC) so look-alike forms (full-width letters, circled letters, ligatures) become ordinary ones, **except** a short list of numerals and measurement marks that are shown exactly as typed because NFKC would change what they say: fractions (2½ stays 2½, not 21/2), superscript and subscript digits (5² stays 5², not 52), circled digits, the trademark and micro signs, the Spanish ordinal marks and prime marks; the screen folds its own copy, so what it checks is still what is shown. **Invisible characters are removed, not replaced by a space** (zero-width and joiner characters, variation selectors, Hangul fillers, bidi marks and overrides, the soft hyphen, tag characters, control characters, private-use characters, unassigned code points and noncharacters, U+2800, U+FFFC), so a word split by an invisible character is whole again and gets caught. ("Unassigned" is decided by the Unicode tables inside the server's Node version: a character added to Unicode after that version is treated as unassigned and removed from the quoted text; Scotty checks the production Node version before deploy.) Removing the joiner U+200D splits emoji "ZWJ" sequences into separate emoji; this is accepted. Removing also glues the words on either side of an invisible character or an inline tag together, and the NFKC step turns a symbol that stands for letters (the numero sign becomes "No", the care-of sign "c/o", a squared unit sign "kg") into letters that glue the words on either side. So the cleaner hands over **four readings** of the same text, each cleaned by the same rules: the one that is shown; a "spaced" one in which each removed character or tag became a space; a "symbols" one in which each punctuation, symbol or space character that NFKC would turn into letters became a space (315 characters, plus the ordinal indicators, the micro sign and the superscript n by name; digit-like marks such as superscripts, fractions and circled digits are NOT changed, so they keep reading as digits for the notice and Social Security patterns, and circled, parenthesised and squared single letters are NOT changed because they are letters); and a "both" one. A reading that would equal the shown text is not computed. The screen reads all four and holds if any one hits (the displayed text is never changed by this, and only the shown and spaced readings can ask for the missing-space hold below). Six HTML entities are decoded, HTML is stripped (script and style blocks dropped with their contents), and links are replaced with `[link removed]`: scheme links from an explicit denylist (http, https, ftp, ftps, sftp, file, mailto, tel, sms, javascript, data, vbscript, blob, ws, wss, ssh, smb, intent, plus skype, facetime, callto, sip, maps, geo, imessage, cid, about, view-source, ms-msdt, search-ms, magnet, whatsapp, tg, zoommtg, zoomus, itms, itms-apps, itms-services), `//host`, `www.` hosts, bare domains with a path, query or port, bare domains ending in one of about 380 top-level domains (the common and abuse-prone ones, most country codes and many newer ones), multi-part country domains, hosts with a leading dot, underscore or at-sign or a trailing hyphen or underscore, known link shorteners, IPv4 and IPv6 hosts, and punycode. **A missing space after a full stop holds the block, because it cannot be told apart from a brand-looking address:** "Leaking.Info needed" and "8:30.Today only" look, to a program, exactly like "Chase.Bank" or "Paypal.Support". So a Title-case word whose ending is one of about 100 everyday-word domain endings (Info, Support, Today, Work, Site, Bank, Shop, Click ...) directly after one plain word, with nothing after it, is replaced with `[link removed]` and also makes the cleaner ask for a hold: the whole block is held (cause `local_screen`, no category) and the text is never shown as typed. The same Title-case shape on an everyday two-letter ending after a hyphenated word ("up-to-date.In the garage") is treated the same way, and so is text that is not a link as typed but is one in its NFKC reading (a Spanish ordinal mark standing for a letter). The same words in lower case ("rincon.support"), upper case, in a longer chain or with a path, port or query are plain links and are replaced. Measurements written like domains (5.mm, 6.ml, 2.5.mm) are left alone, but only a short list of measurement endings (mm, cm, km, kg, lb, ml, mg, ma, mv, mw, kw) after a number of one to four digits; any other ending after a number (a number-only name on a free or abused domain) is a web address and is replaced. Five of those eleven endings (ml, ma, mw, mv, kw) are also real country domains, so a number-only name on one of them is shown as typed although it is a legal web address; this is recorded as an accepted residual (governance review, Section 9). The two-letter country codes that are everyday words (in, to, is, it ...) are left alone after a plain word, but a hyphenated word right before such an ending (word-word.xx) is a link. Plain e-mail addresses and phone numbers are left alone, but an at-sign with no name in front of it, or a doubled at-sign, is not an e-mail address and the domain after it is replaced; and a web-like word in front of an at-sign ("support.name" before "@") is left alone only when what follows the at-sign is itself a host with a dot and a listed ending (name@example.com is an address; a web address followed by an at-sign and a single letter, a number or an unlisted ending is not, and the web-like word is replaced). A host ends at the first character after its ending that is not an ASCII letter or digit: a superscript, fraction, circled digit, other-script digit, ordinal sign or accented letter right after the ending does not hide it (the host is replaced and that character stays; the cost is that a Spanish word that begins with a listed ending and continues with an accented letter, typed with no space after a full stop, is also cut there). All whitespace, newlines included, becomes single spaces so text cannot forge extra lines. The five steps repeat until nothing changes (at most six passes), so the cleaner is idempotent and its output never matches its own link detector; ordinary double- or triple-escaped text settles. Text that will not settle (six or more levels of nested entities or tags: five settle, because the cleaner makes at most five changing passes and one passes that changes nothing), or that blows the cleaner's time budget, holds the block under its own cause, `unsettled_text`, with one constant log line; it is reported on its own line and is NOT counted as a scanner error. The screen reads exactly the string that would be displayed (checked equals shown), up to the 20,000-character cap.

**Limits.** Title 100 characters, description 300 (up to 500 may be revisited after the shadow week), counted in code points, cut at a word boundary where one falls in the last quarter, ending " ..." plus " (shortened; full text is in Latchel)". A title that is just the start of the description is not repeated. The block ends with one fixed line, "(Quoted as typed in Latchel. Not checked for names, phone numbers or access codes. Internal use only.)", so the email never implies a clearance that does not exist. **The honest block length:** Peter's "about 600 characters" was a soft target and nothing has been cut to meet it. The longest possible block (100-character title, 300-character description, the two longest category labels, "Emergency / Urgent" and the fixed last line) is **733 characters over 6 lines** (706 to 733 with two category labels, 694 to 710 with one, about 606 with none, depending on which labels the keywords pick); a typical block is about 330; the fixed last line alone is 104. Every limit is a constant at the top of `lib/work-order-summary.js` (`TITLE_MAX`, `DESCRIPTION_MAX`, `SHOWN_FOOTER`), and the test that works out the longest block (`fix-round-tests.js` R18) computes it from those constants, so changing one changes the reported number. **Checked again after the cut:** the exact strings that will be printed are run through the link detector again, and when either was cut, through the screen again (a cut can end a word as a shorter listed word or a web-like fragment that the whole text did not have); any hit holds the block. **Quotes:** the description is wrapped in straight double quotes, and a straight double quote typed inside the title or description is shown as the double prime (the inch mark, so a 3/4" valve stays a 3/4-inch valve), so the text can never close the quote early and imitate the last line; the length arithmetic does not change.

**Missing data.** No title and no description: one explanatory line. Description blank: "(none was entered in Latchel)". **Owner switch: the content screen off (added 2026-10-17; an owner override, never a met condition).** Peter decided, in chat on 2026-10-17 after Jarvis showed him in plain words what the screen does, what no screen means (every word a tenant types goes word for word to the two shared pod inboxes, where it stays in the inboxes, Missive and the sent folder and cannot be unsent) and what the options were, that nothing is to be held and nothing is to be told to go back to Latchel (as relayed by Jarvis; the decision record, with his exact words and the risks he accepted, is `compliance/work-order-note-alerts-description-decision-resolution.md`, section "Peter's decisions of 2026-10-17", and is not part of this SPEC; Asimov's conditions for deploying and for switching on, including the exact steps and the emergency switch-off, are in `compliance/work-order-note-alerts-description-governance-review.md`, Section 19). This section describes only what the code does.

*The variable.* `WORK_ORDER_ALERT_DESCRIPTION_SCREEN`. **Only the exact lowercase value `off` turns the content screen off.** Unset, empty, `on`, `ON`, `Off`, `OFF`, ` off`, `off ` and any other value leave the screen ON, and then the behaviour is byte-identical to the commit before this switch existed (c781a1b) in every mode (a fixture of 42 cases in shadow, on and on-without-interlock, with the audit rows and log lines, proves it for nine different values). It is independent of `WORK_ORDER_ALERT_DESCRIPTION_MODE` and of the ingestion interlock, and changes neither: with the mode `off` (or unset or unrecognised) nothing in this block runs, whatever this variable says, and the email is byte-identical to the parent; in `shadow` the whole pipeline runs, one counts-only audit row is written and nothing is added to the email; `on` without the interlock stays `shadow`; `on` with the interlock puts the block in the email. It is read at the moment of each alert, never cached. It is set only by Jarvis or Scotty after Peter's explicit yes; `.env.example` names it and sets no value. To turn the screen back on: unset it (or set anything but `off`) and restart the Hub.

*What it disables.* Nothing from `work-order-text-screen.js` or its terms is consulted: not the word and phrase lists, the pair rules, the squashed-phrase rule, the notice patterns, the Section 8 rule, the unfamiliar-language ratio, the look-alike-letter, script and pictograph rules, nor the shared `scanText()`. So nothing is held for what the text says, for any pod. In particular: an unassigned pod is no longer pointer-only (nothing was read, so nothing was withheld); the text goes to both inboxes like any other pod's, the read-only Latchel lookup is made if the job has no `description` key, and the missing-pod task and its audit row are unchanged. The three holds the cleaner could ask for by itself are not holds either: a sentence typed with no space after its full stop (`Leaking.Info`) has the web-like token replaced by `[link removed]` and the rest shown; a web-like fragment left by the 100 / 300 character cut is replaced the same way (and if the replacement would push the text over the limit, the cut is made a little shorter, so the limits hold); a link that exists only in the NFKC reading (the Spanish ordinal marks fold to letters) is replaced after folding, which in that rare case also shows the other kept-as-typed numerals in their folded form.

*What it keeps (hygiene that protects the email itself, not a content screen).* HTML and tag stripping, entity decoding, removal of control, invisible and bidi characters, whitespace and line-break collapse (a description cannot forge a line), the cut to 100 (title) and 300 (description) code points at a word boundary, the unforgeable quote wrapper (a straight double quote is shown as the inch mark), the header, subject and recipient isolation (job text never reaches the subject, a header or the recipients, and the recipients are resolved before the text is read), link neutralisation to `[link removed]`, and the same four allowed job fields only (`name`, `description`, `is_emergency`, `is_urgent`). No AI, no network (apart from the existing read-only Latchel lookup), nothing from the text stored or logged.

*The safety fallback (not a content hold).* Text that cannot be made safe to print (the cleaner cannot settle it within its passes, a value that is not text, an internal error) is not held: the block is the existing neutral line `What the work order is: (could not be retrieved, see Latchel)`, the alert is still sent, and one constant log line is written (no text). The audit row says `result` `unavailable` with `cause` `unprintable_text` (or `summary_error` for an unexpected internal error), `risk_level` medium. It is rare: 1 string in 5,000 hostile generated strings (`unscreened-tests.js` U16). The wording says "retrieved" because it is the existing wording for the unavailable state.

*The never-store mask (`maskNeverStore` in `lib/work-order-text-clean.js`; a replacement, never a hold; a best effort, not a guarantee).* Peter's standing rule is that no Social Security number, bank account number or password is stored in any file or table, and the sent email is a copy that lives in the inboxes. So inside the quoted title and description, and after the cleaner, these known shapes are replaced by `[removed]` and the rest is shown. **A Social Security number** written `###-##-####` (dashes or spaces), or nine digits after `ssn`, `social security`, `social` or `seguro social`. **A payment card number**, in **any grouping**: 13 to 19 digits with at most one space or dash between any two digits, whose digits pass the card check digit (Luhn). There are two readings of a run of digits. The first is the old content screen's own card test (`CARD_PATTERN` plus `luhnOk`), read the way the screen read it: a run is taken from its start, one longest window of 13 to 19 digits (ending at the end of a group) at a time, and when a window fails the check digit the next window starts after it. A test (`mask-tests.js` C2) pins the mask to the screen: the check digit routine gives the same answer for 20,000 random strings, the screen's pattern lines are still the ones this rule was written against, and on 40,000 random strings of digit groups every string the screen's SSN and card test flags is masked, and every other change is explained by the second reading. The second reading looks for a number written the way cards are written (one group of 13 to 19 digits, 4-4-4-1 to 4-4-4-4-3, or the American Express 4-6-5) wherever it starts inside a longer run, so a card number written straight after another number (`apt 12 4111 1111 1111 1111`, `ticket 4455 4111 1111 1111 1111`) is found; it needs the check digit too. Measured (`mask-tests.js` C1): 300 of 300 random numbers with a valid check digit are masked for each of 24 groupings, each tried with a space and with a dash between the groups (4-4-4-4, 4-5-5-2, 5-5-5-1, 3-3-3-3-3-1, 2 x 8, American Express 4-6-5, 4-4-8, 8-8, 4-12, 6-10, 3-3-3-3-4, one group of 13, 16 or 19, 4-4-4-4-3, 1 x 16 and others), 3,000 of 3,000 random groupings, and 2,400 of 2,400 cards in the usual layouts with an ordinary number (12, 204, 4455, 88213, 2026 ...) before or after them. **One pass for the Social Security number and the card (round 6; TARS bug 1, Judge fix 1, Asimov U-2a).** The separated Social Security number and the card number are found in ONE pass over each run of digits, so that neither rule can cut the other: a Social Security number is three groups of 3, 2 and 4 digits, its span and every card window of the run are united, and every group that touches a united span is replaced with it. The card readings are made on the whole run (a card number that has a 3-2-4 stretch inside it is masked whole) and again with the SSN left out and with it taken in (a card may start at the run's start or right after an SSN, and stop at the run's end or right before one). *The audit row.* Exactly the same eleven keys plus `trace`; no text, no length, no hash, no matched word and no category name (a test checks the key list and that no category name or job text reaches any write, log or failure email). **Counts-only review (shadow week and the first 30 days).** The audit events hold no text, so these queries read none. They count attempts (one row per try); a job whose send keeps failing is tried again on each pass, so read `attempts` together with `distinct_jobs` (query 2) before judging a rate. There is deliberately no query by category: no category name is stored. Jarvis runs them and explains the results in plain English; the first review is after day 3 and the final one at day 7 or later.

```sql
-- 1. Results by day, mode and cause
select date_trunc('day', created_at)::date as day, details->>'mode' as mode,
       (details->>'screen_version' = 'unscreened-owner-override') as unscreened,
       details->>'result' as result, coalesce(details->>'cause', '-') as cause, count(*)
from audit_log
where action = 'work_order_note_alert.description_checked'
  and created_at > now() - interval '7 days'
group by 1, 2, 3, 4, 5 order by 1, 2, 3, 4, 5;

-- 2. Screened attempts, hold rate, errors, unsettled text, unavailable share, and the share of holds that were only ordinary words
select count(*) as attempts,
       count(*) filter (where details->>'result' in ('shown', 'none') or details->>'cause' in ('local_screen', 'link_shape')) as screened,
       count(*) filter (where details->>'cause' = 'local_screen') as held_by_screen,
       count(*) filter (where details->>'cause' = 'link_shape') as held_by_link_shape,
       round(100.0 * count(*) filter (where details->>'cause' = 'local_screen')
             / nullif(count(*) filter (where details->>'result' in ('shown', 'none') or details->>'cause' in ('local_screen', 'link_shape')), 0), 1) as hold_rate_pct,
       count(*) filter (where (details->>'common_word_only')::boolean and details->>'cause' = 'local_screen') as common_word_only_holds,
       round(100.0 * count(*) filter (where (details->>'common_word_only')::boolean and details->>'cause' = 'local_screen')
             / nullif(count(*) filter (where details->>'cause' = 'local_screen'), 0), 1) as common_word_only_pct,
       count(*) filter (where details->>'cause' in ('check_error', 'summary_error')) as scanner_errors,
       count(*) filter (where details->>'cause' = 'unsettled_text') as unsettled_text,
       count(*) filter (where details->>'result' = 'unavailable') as unavailable,
       round(100.0 * count(*) filter (where details->>'result' = 'unavailable') / nullif(count(*), 0), 1) as unavailable_pct,
       count(distinct details->>'latchel_job_id') as distinct_jobs,
       count(distinct (created_at at time zone 'UTC')::date) as days_with_data
from audit_log
where action = 'work_order_note_alert.description_checked'
  and details->>'cause' is distinct from 'pod_unassigned'
  and details->>'screen_version' is distinct from 'unscreened-owner-override'   -- unscreened rows are counted in query 5, not here
  and created_at > now() - interval '7 days';

-- 3. Twenty random jobs the screen let through, for the human second look (job ids only; includes jobs shown with the screen off)
select details->>'latchel_job_id' as latchel_job_id
from audit_log
where action = 'work_order_note_alert.description_checked'
  and details->>'result' = 'shown'
  and created_at > now() - interval '7 days'
order by random() limit 20;

-- 4. After ON: the same counts, week by week, for the first 30 days
select date_trunc('week', created_at)::date as week, details->>'mode' as mode,
       (details->>'screen_version' = 'unscreened-owner-override') as unscreened, details->>'result' as result,
       coalesce(details->>'cause', '-') as cause, count(*)
from audit_log
where action = 'work_order_note_alert.description_checked'
  and created_at > now() - interval '30 days'
group by 1, 2, 3, 4, 5 order by 1, 2, 3, 4, 5;

-- 5. Unscreened attempts only (the owner's content-screen-off switch): what happened, by day. 'shown' is text emailed with no screen;
--    'unavailable' with cause 'unprintable_text' or 'summary_error' is the neutral fallback; no text and no category is in these rows.
select date_trunc('day', created_at)::date as day, details->>'mode' as mode, details->>'result' as result,
       coalesce(details->>'cause', '-') as cause, count(*) as attempts, count(distinct details->>'latchel_job_id') as distinct_jobs
from audit_log
where action = 'work_order_note_alert.description_checked'
  and details->>'screen_version' = 'unscreened-owner-override'
  and created_at > now() - interval '30 days'
group by 1, 2, 3, 4 order by 1, 2, 3, 4;
```

## 7. Compliance — PENDING ASIMOV REVIEW

`properties.maintenance_notes` has been scanned for protected-class content exactly once — manually, by Peter, plus a one-time keyword pass, on 2026-09-06, against the 194 values that existed that day (`supabase/migrations/20260906000000_add_maintenance_notes_to_properties.sql`). This codebase has an established two-layer pattern for exactly this situation:
- **Layer 1 — `scanText()` from `maintenance-history/lib/protected-class-terms.js`.** Deterministic, fast, free, no network call, already proven on this exact field once. Recommend: run unconditionally, at send time, every time (not stored-and-reused from the 2026-09-06 scan, which is now stale by construction).
- **Layer 2 — an AI self-check**, the pattern `owner-tenant-notes/lib/note-content-check.js` layers on top for tenant-authored free text reaching a comparable audience. Not a direct drop-in (that module's Layer 2 is built for a different table/purpose), but the same pattern could be replicated for this field if Asimov/Mason want the extra coverage.

**What this spec recommends, marked as a recommendation for Asimov to confirm or override, not a decision already made:** run Layer 1 unconditionally. Whether Layer 2 is also warranted here is a proportionality call — this field already got one human review plus one keyword pass with zero matches, and it's property-level operational text (vendor contacts, approval routing) rather than tenant-narrative text, which is a materially different risk shape than the free-text fields Layer 2 exists to catch elsewhere in this codebase. Asimov should decide.

**If Layer 1 (or Layer 2, if adopted) flags the note:** the recommendation is to hold the note text specifically, not the whole email — send the rest of the alert (property, work order, link) with the note line replaced by a fixed placeholder ("Maintenance notes on file — flagged for review, see Property 360 for details"), mirroring the established "missing/held data renders as a labeled placeholder, never a silent drop, never blocks the rest of the message" pattern from `approval-briefing-SPEC.md` Section 8. ## 8. Failure Visibility

This feature's whole point is "don't miss this," so a failure that only shows up in a server log defeats the purpose. Two layers, kept deliberately simple:

**1. Every attempt is durably recorded** (Section 4's table) — a Supabase write, which doesn't depend on email working at all, so this layer can't fail for the same reason an email send would.

**2. Surfaced somewhere a human actually looks.** Recommend adding a small "Work order alerts" line to Property 360's existing Maintenance card (`property-360/router.js`'s `fetchMaintenanceCard`, which already renders `maintenance_notes` for this exact property today) — showing the outcome of the most recent alert attempt for that property. This is cheap specifically because that card and its data-fetch path already exist and already surface this same field.

**One honest, current gap worth flagging rather than assuming away:** this codebase's established "something is fundamentally broken, tell Peter no matter what" fallback (`sendFailureAlertEmail`, in `security-deposit/router.js` and `archive-search/router.js`) is deliberately built on a *separate* credential from the normal send path (`nodemailer` + `GMAIL_USER`/`GMAIL_APP_PASSWORD`, not `lib/notify.js`'s Gmail-API path) — specifically so a bug in one can't silence the alert that the other is broken. **Checked live today: `GMAIL_USER`/`GMAIL_APP_PASSWORD` are not set in this project's `.env`, and `.env.example`'s own comment states they're also not set on the production server.** That means this established fallback pattern, if reused as-is, would itself be a silent no-op right now — the code already says as much in its own comments. (For contrast: `lib/notify.js`'s Gmail API credentials — `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`HUB_NOTIFY_REFRESH_TOKEN` — **are** all set and working today, which is why the primary send path in this spec is designed around it.)

Recommendation: this feature's primary send goes through `lib/notify.js` (confirmed working). For the "tell Peter no matter what" layer specifically, either (a) get `GMAIL_USER`/`GMAIL_APP_PASSWORD` actually configured in production so the existing `sendFailureAlertEmail` pattern is real rather than theoretical — worth doing regardless of this feature, since it's silently non-functional for the tools that already have it — or (b) accept layer 1 + 2 above (durable row + Property 360 card) as the v1 safety net and revisit a true independent-credential fallback once (a) is resolved. This spec doesn't decide between those two — flagging it for Peter, since it's a real, currently-true fact about the codebase, not a hypothetical.

## 9. Audit Logging (GOVERNANCE.md Rule 1)

Following this codebase's established per-event-type convention, content-free `event_data` throughout:

1. `work_order_note_alert.triggered` — a qualifying job was seen (notes present, property resolved). `actor_type: 'system'`.
2. `work_order_note_alert.sent` — `actor_type: 'system'`, `event_data: { latchel_job_id, property_id, pod, recipients }`.
3. `work_order_note_alert.send_failed` — same shape, `risk_level: 'high'` (matching this codebase's convention of elevating risk_level for a failure that could mean something real got missed).
4. `work_order_note_alert.protected_class_excluded` — fires only if Section 7's check flags the note. Same shape and same restraint as `maintenance_claims.protected_class_excluded` — category only, never the matched text.
5. `work_order_note_alert.pod_unassigned_flagged` — the both-inboxes fallback fired.
6. `work_order_note_alert.description_checked` — one per attempt when the optional description block is in `shadow` or `on` (Section 6A). Counts only: no text, term, length, hash or per-word count.
